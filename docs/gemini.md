# Gemini CLI as a relay target (API key only)

Relay 1.0 adds Google's Gemini CLI (`gemini`, npm `@google/gemini-cli`, tested 0.64.0 and 0.65.0) as an ACP target, driven over `gemini --acp`. It is off by default, and qualified for 1.0 (the maintainer, 2026-10-22), with the residuals of §8's verdict accepted. It was qualified with a real key ([record](qualification/gemini-0.64.0.md)):
- **2026-10-21:** no model reply, since the key's project had no credit left.
- **2026-10-22:** with credit. Every check of §8 that concerns relay passed.
- **2026-10-22:** relay's tools through Gemini's tool discovery (below), on 0.64.0 and then 0.65.0. The maintainer then qualified Gemini (§8, verdict).

Since those runs, a Gemini agent gets relay's tools, through Gemini's own command-based tool discovery (§3.8), while it still runs in an untrusted folder; §8, items 12-17, record the runs that checked it.

The target builds on earlier research into ACP harnesses (not published). This note records what relay does and why, where it departs from that research, and what is left to verify. It is written to be attacked in review, the key handling (§2) most of all; §9 lists the points to attack first.

Marks used below:

- **(seen)**: observed on 2026-10-17 by running the real `gemini --acp` 0.64.0 from a scratch npm prefix, never with a real key and never with a prompt: first with a scratch `GEMINI_CLI_HOME` and `HOME` under a Seatbelt profile that denied all outbound network; then through relay's own launch path (this profile, relay's sandbox and its boundary probes, 76 with the key directory denied, relay's proxy admitting only a host that cannot resolve), with no key and with a made-up one, stopped before any prompt.
- **(source)**: read in the 0.64.0 package (`bundle/`), the function named.
- **(unverified)**: waits for the qualification run (§8).

## 1. Why an API key

Google's server refuses Gemini CLI's consumer "Login with Google" for every version since 2026-06-18. The maintainer saw "This client is no longer supported for Gemini Code Assist for individuals". Workspace login needs a Gemini Code Assist Standard or Enterprise subscription, which Google stopped selling on 2026-10-09. What still works is a Gemini API key, which Google's own FAQ calls "the supported and secure method" for third-party agents.

So Gemini is relay's one key-only target (`capabilities.login: "key-only"`). That is an exception to relay's rule that launched agents run on the person's own account logins, and relay takes it only on an explicit per-target opt-in (§2.7).

## 2. The key

### 2.1 Requirements

1. The person alone controls the key. They create it, store it, rotate it and revoke it; relay only reads it.
2. It is never in relay's config, which may be synced: `~/.config/relay/config.json` may be a link into a synced folder (a dotfiles repository, say).
3. Relay never logs, prints, stores or passes it on: not in a log, a transcript, the registry, a command line or an error message.
4. It goes to Gemini's process and to nothing else: no other target, no other process relay starts, and none of the commands Gemini runs for the agent.
5. Relay uses it only when the person opted in for Gemini by name.

### 2.2 Where relay reads it from

A single-line file the person writes. The default is **`~/.config/relay-keys/gemini-api-key`** (directory 0700, file 0600). It sits beside `~/.config/relay`, not inside it, so nothing that syncs or backs up relay's config directory carries it. The coordinator decided this location.

The path can be changed per target in relay's **local config**, a machine-local file that is never synced:

```json
{ "targets": { "gemini": { "api_key_file": "~/somewhere/else/gemini-api-key" } } }
```

- It lives at `~/.config/relay/local.json`. `~/.config/relay` is expected to be a real directory, even where `config.json` in it is a link into a synced folder. Its place does not follow `RELAY_HOME` or `RELAY_CONFIG`, which nested relays and tests set, so every relay process on the machine reads the same one.
- It is read in the worker that launches the turn, every turn, and by `relay doctor`. It is never copied into the run's config snapshot in the registry, as `config.json` is.
- It is validated strictly, as `config.json` is. It may hold only `targets.<id>.api_key_file`, and only for a key-only target. The path must be absolute or start with `~/`.
- It decides which private file relay reads and sends to a vendor, so it is held nearly to the key file's standard. Whoever can write it could point relay at another one-line secret of the person's (an OpenAI key, a token file) and have relay send it to Google. Relay refuses it when it is a link, is not a regular file, has a second name (a hard link, through which another file could change it), is not the person's, or can be written by anyone else. It opens it as it opens the key file (never through a link, a FIFO not waited on) and checks and reads that one descriptor, so what it checks is what it reads (review round 4). It may be readable by others, since it holds a path, not a secret.
- Relay also refuses it when it lies in relay's synced directory: where `config.json` leads when `config.json`, or its directory, is a link, and the git work tree that directory is in (§2.3). A local config there would itself be synced.
- It is one of relay's own files for relay's config protection (`localConfigPath` is named in `src/core/protected-config.ts`, beside `config.json`, `install.json` and `install-backups`): protected itself, even before it exists, in grants, file approvals, Claude's write denials and relay's own sandbox, and counted as relay's when relay decides whether `~/.config/relay` is relay's alone. Before review round 3, writing it made relay protect only the files in that directory, and doctor warned so.
- `api_key_file` is not a key of `config.json`. Putting it there gets the error relay gives for any unknown key, so a secret's path never enters the synced file by mistake.

### 2.3 What relay checks before it reads

The file is opened with `O_NOFOLLOW | O_NONBLOCK`. Relay checks the open descriptor, not the path, so nothing can be swapped in between the check and the read. A FIFO left in the file's place is opened at once and refused; relay does not wait for a writer.

Relay refuses, naming the path and the problem but never the content, when:

- the file's directory is a link, is not a directory, is not the person's, or can be written by group or others (whoever can write it can swap the key);
- the file's directory is in relay's synced directory, or in the git work tree that directory is in: what a sync job commits and pushes is the whole work tree (the maintainer's `~/dotfiles`, auto-pushed), not the folder `config.json` leads to. A work tree that is or holds the home folder or relay's own directories is left out, since refusing it would refuse every place a key could be (review round 3);
- the file's directory is or holds the home folder or relay's state, worktrees or confined agents' homes (a key file directly in `~`, say): relay keeps jobs from writing in the key's directory (§2.9), which it cannot do for one that holds their work;
- the file's directory is where agents relay launches write without any grant: a temporary directory outside the person's home (`os.tmpdir()`, `/tmp`, `/var/tmp`), which Claude's and Codex's own sandboxes leave writable, or relay's state directory, its worktrees or its confined harnesses' homes. Ownership and mode do not stop those agents, which run as the person: a Claude or Codex child could write a key of another account there, and the file would pass every check below. A directory under the person's home is not refused on these grounds however the home is placed (the grant check keeps jobs out of the key directories, §2.9);
- the file is a link (`O_NOFOLLOW` fails), or not a regular file;
- the file is not owned by the person running relay;
- the file has any group or other permission bit set (`mode & 077`; 0600 and 0400 are fine);
- the file has more than one name, so another file could be the same file under a second name;
- the content, after one trailing `\n` or `\r\n` is removed, is not one line of 20 to 512 characters from `A-Z a-z 0-9 . _ ~ -`, or the file is over 1 KiB. Google's keys are 39 such characters;
- the content has the published shape of another vendor's secret: Anthropic's and OpenAI's `sk-` keys, GitHub's tokens (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`), xAI's `xai-`, GitLab's `glpat-`, Slack's `xox…-` and AWS access key ids. The refusal names the vendor, not the content.

The narrow alphabet has two jobs. A file that holds something else (a JSON service-account credential, `GEMINI_API_KEY=…`, two lines) is refused rather than sent to Google. And the key is spelled the same raw and inside JSON, which the redaction in §2.5 relies on. The alphabet still admits many one-line secrets; the prefixes catch the likeliest ones (a local config pointed at the wrong key file). Relay does not insist on Google's own shape (39 characters, `AIza…`), which nothing guarantees will last, so the check is not the barrier against sending another secret to Google: that is that only the person can write the local config (§2.2), that no job can be granted its directory, a key directory or a directory holding `config.json` (§2.9), and that the key file is in no place a launched agent writes without a grant (above).

The file is read in the worker, in Gemini's `prepareState`, just before the launch. By then every refusal that can come earlier has passed: the per-target opt-in (§2.7), the target being on, the version, the harness binary, and the environment's endpoint check. The key lives in that worker's memory for the turn and is never written anywhere by relay. `relay doctor` makes the same checks to report them, and reads the content (never printing it) only with the per-target opt-in; without it, it checks only where the file is and its status.

### 2.4 How the key reaches Gemini: in ACP `authenticate`, never in an environment

Relay hands the key to the Gemini process it starts for the turn in one ACP request, right after `initialize`: `authenticate` with `{"methodId": "gemini-api-key", "_meta": {"api-key": "<key>"}}`. Gemini's `initialize` advertises exactly that (its `gemini-api-key` method carries `_meta: {"api-key": {"provider": "google"}}`, seen), and it keeps the key in memory for every session of that process (source: `GeminiAgent.authenticate`, and `AcpSessionManager.newSession`'s `authDetails.apiKey`). Seen through relay's launch path: with a made-up key handed over this way and none in its environment, `session/new` made a session; with none, it failed "Gemini API key is missing or not configured." This is the generic hook `PreparedState.authenticate` (§6).

**Why not `GEMINI_API_KEY`.** The brief fixed `GEMINI_API_KEY`, and this lane built it first. Its end-to-end test then showed that a command the agent runs can read the key: relay's sandbox opens process information to the turn's own processes (`(allow process-info* (target same-sandbox))`), so a turn's own commands can read the environment each process was started with. The profile denies process-info except for same-sandbox processes and does not allow sysctl `kern.procargs2`; another sandbox cannot inspect that environment. A shell command Gemini ran read Gemini's own start-up environment, `GEMINI_API_KEY=…` included, although Gemini's redaction had kept the variable out of the command's own environment. That would hand the key to anything that can steer the model (a prompt injected through the repository, say), which could write it into the worktree or send it through Google's own API host to a project of its own. The test now keeps that read as its control: the command can still read Gemini's start-up environment, and the key is not in it. Gemini's memory is another matter: reading it needs Gemini's task port, and `task_for_pid` on another of the person's Node processes failed for an ordinary process on this Mac even outside any sandbox (2026-10-17, Developer Mode off; seen for both Node from fnm, which has the hardened runtime, and Homebrew's ad-hoc signed one). **(unverified)** with Developer Mode on.

The cost of `authenticate`, each checked in the source:

- In Gemini, `authenticate` also writes `security.auth.selectedType` into the user settings. In relay's read-only home that write is refused, and Gemini ignores the failure (`saveSettings` catches it; seen: "Failed to save settings: Operation not permitted" on its stderr, and the sign-in went on); relay's own settings already name the method.
- On a change of method it deletes cached OAuth credentials (`clearCachedCredentialFile`). There is no change (relay's settings name the same method), and relay's home holds none.
- It accepts a gateway base URL in `_meta.gateway`, an endpoint redirect. Relay never sends one.
- It verifies nothing: it returned `{}` with no key at all (seen). Without a key, `session/new` fails with -32000 "Gemini API key is missing or not configured." (seen), and relay fails the turn on that error. A key Google refuses fails the first prompt.
- `_meta["api-key"]` is what `initialize` advertises to clients, not a documented setting, so a minor release could drop it. Relay would then fail the turn plainly at `session/new` ("Gemini API key is missing"), never send the key elsewhere.

What else keeps the key in Gemini's process alone:

- **One source.** Relay removes from Gemini's environment every `GEMINI_*` variable it inherits (`GEMINI_API_KEY` included), `GOOGLE_API_KEY`, every `GOOGLE_CLOUD_*` and `GOOGLE_GENAI_USE_*` variable, `GOOGLE_APPLICATION_CREDENTIALS`, `CLOUDSDK_*` and `CLOUD_SHELL`. This holds even under `child_auth: "any"`, which would otherwise pass a target's own credentials through. Relay also sets `GEMINI_FORCE_FILE_STORAGE=true`, so Gemini never looks in the keychain for a stored key (relay's sandbox denies the keychain anyway). Gemini's home is relay's own and holds no stored key. A repository's `.env` is not read (§3.2).
- **Its tools see no secret in their environment.** Relay's settings turn on `security.environmentVariableRedaction`. With that on, the commands its shell tool runs, its hooks and its MCP servers get an environment without any variable whose name matches `KEY`, `TOKEN`, `SECRET`, `AUTH` and the like, or whose value looks like a Google key or a URL with credentials in it (source: `sanitizeEnvironment`, used by `ShellExecutionService.prepareExecution` and the hook runner). The key is not in Gemini's environment to begin with; this keeps out the proxy URL with relay's per-turn token, which a command can still read from Gemini's start-up environment (the residual every relay-enforced harness has, README "What it does not do").
- **Nor from the file.** Relay's sandbox denies the default key directory, `~/.config/relay-keys`, to every agent it confines, whatever its target (a generic change to `acp.ts`, §6): reading the key is refused, and so is listing the directory or testing which names exist in it. A key file the local config puts elsewhere is denied too, the file alone (`keyPathsToDeny`, `src/core/api-keys.ts`): its directory may hold anything else of the person's, and a denied directory above a worktree would leave a turn nothing to work in, but relay's denied list takes a single file as it takes relay's config files, and the boundary probes check it (a read, a test for its name, an open for writing that writes nothing). Before review round 4 such a file was not denied at all, so the commands Gemini ran could read it. `relay doctor` says which case applies.
- **Not logged.** Relay's agent log records what the agent writes, not what relay sends it, so the `authenticate` request is in no log; the launch line records the command and arguments, which hold no key. Should Gemini quote the request back (it prints a failed request's parameters to stderr, or puts them in an error), relay's redaction (§2.5) replaces the key; the tests check it on a refused sign-in whose error quotes the key.

### 2.5 Redaction

The model never needs the key, and nothing above gives it one. Should the agent print it anyway (an error message that quotes a request, a debug line), relay replaces it with `[redacted]` in everything it reads from the agent before using it. That is the generic `PreparedState.secrets` hook (§6).

- Each line of the ACP stream is redacted before it is parsed. The agent log, progress lines, approval requests and error messages all come from that redacted text.
- stderr is redacted a whole line at a time, so a key split across two reads of stderr is caught. The tail of stderr that a failure message quotes is built from redacted lines and the redacted partial last line, cleaned as every diagnostic tail of relay's is (`diagnosticTail`, which also cuts credentials of a shape relay knows) and cut to 2000 characters.
- The reply is redacted again once it is assembled. Models stream text in pieces, and a piece boundary can split the key.
- The agent log does the same for the streamed text (review round 4; `secretSafeLog`, `acp.ts`). For a turn with secrets, relay queues what it writes to the log in order, and reads the text of the message, thought and replayed user chunks as one stream, whatever lines come between them. A chunk's line is written once the stream has run on past it by one character less than the key, or when the turn ends. By then a key it holds a piece of is whole in the stream, and relay cuts it out of every line it spans: `[redacted]` where it starts, nothing where it continues. Only the log waits; what relay does with each line does not. Before round 4 the two pieces of a key split across two chunks stayed in the log as they came.

Not caught:

- An encoded form of the key (base64, reversed, spaced out), or one the agent splits across lines other than streamed text (two tool calls' titles, say).
- A key the agent writes into a file in its worktree: relay does not rewrite files.

### 2.6 Other agents

- The key never enters relay's own environment, so no agent relay launches can inherit it from relay.
- `GEMINI_API_KEY`, `GOOGLE_API_KEY` and Google's other credential overrides are in Gemini's `credentialEnv`. Relay removes them from every other target's environment, as it removes every vendor's keys, except where the legacy global `child_auth: "any"` applies to that target (no `targets.<id>.child_auth` of its own): there every vendor's keys pass through, Google's included (`scrubbedCredentials`, `src/backends/env.ts`). This changes Claude's, Codex's and Copilot's environments too, even while Gemini is switched off: a `GOOGLE_API_KEY` in relay's environment no longer reaches them. Gemini's own environment never has them, under any setting (§2.4).
- `GEMINI_FORCE_ENCRYPTED_FILE_STORAGE`, in the research's `credentialEnv` for Gemini, is left out of it: it is a switch for where Gemini keeps a stored OAuth login (`packages/core/src/code_assist/oauth2.ts`, `mcp/oauth-token-storage.ts`), not a credential, and means nothing to another agent. Gemini's own scrub removes it (every `GEMINI_*` variable, §3.1).
- Every agent relay confines itself (Copilot, Gemini, Grok) is denied the default key directory and a moved key file (§2.4).
- Claude's turns may not read them either (review round 4): every Claude turn that is not dangerous gets the default key directory and a moved key file in its sandbox's `filesystem.denyRead`, for the shell, and as `Read(//…)` deny rules, for its file tools (`backends/claude.ts`, from the same `keyPathsToDeny`). Relay does not hand Claude the key; this keeps a Claude turn steered by what it reads from taking it.
- **Not covered: Codex.** Codex can deny reads: relay now gives every Codex turn its sandbox as a permission profile of its own (`backends/codex.ts` `codexPermissions`), and a profile's `deny` entries refuse reads. Relay's profile denies none (`":root" = "read"`): its policy is still to let Codex read what the person can. So a Codex agent relay launches can read the key file, as it can read `~/.ssh` or `~/.claude`. A `deny` entry for the key paths would also change how Codex runs an approved escalation: with any read denied, Codex runs the approved command inside its sandbox with the profile's restrictions, not unsandboxed (`core/src/tools/sandboxing.rs`, `sandbox_override_for_first_attempt`, `unsandboxed_execution_allowed`). Writes are another matter: no job may write the key directories or the local config (§2.9). Whether that read access is acceptable, or Codex needs read confinement (permission profiles, or relay's own sandbox), is for the coordinator to decide (§7).

### 2.7 The opt-in

Relay launches Gemini only with all of these in `config.json`:

- `targets.gemini.enabled: true` (off by default);
- **`targets.gemini.child_auth: "any"`**, the per-target setting. The global `child_auth: "any"` does not count: that is the legacy setting that hands every vendor's keys to every target, and Gemini's key must be opted into by name. A per-target `"login"` is refused too, with the reason.

Gemini is qualified, so it needs no `targets.gemini.experimental`. A config written while it was experimental may still set it: that is accepted and changes nothing.

None of these is secret. `targets.gemini` is a key that only 1.0 and later know, so keep it out of a config file an older relay also reads ([UPGRADING](UPGRADING.md#your-config-across-versions)).

### 2.8 Residual risks

- **The key goes to Google with every request**, which is its purpose. The endpoint is fixed:
  - relay refuses to launch Gemini with any variable that redirects it (`GOOGLE_GEMINI_BASE_URL`, `CODE_ASSIST_ENDPOINT`, `CODE_ASSIST_API_VERSION`, `GOOGLE_VERTEX_BASE_URL`, `GOOGLE_GENAI_API_VERSION`, `GCE_METADATA_HOST`, `GCE_METADATA_IP`), checked on the whole environment the harness gets, the profile's own variables included;
  - relay never uses the ACP `gateway` method;
  - relay runs Gemini in an untrusted folder (§3.2), where the repository's `.gemini/.env` and `.gemini/settings.json` are not loaded;
  - in a turn without a network grant, only `generativelanguage.googleapis.com` is reachable, through relay's proxy.
- **A turn with network access** can be steered into sending out whatever the agent can read. The key is not among those things for a Gemini, Copilot or Claude agent: it is in no environment and its file is denied, where relay keeps it and where the local config moves it. It is in Gemini's own process memory, which the agent's commands cannot read (§2.4). A Codex agent can read the file (§2.6).
- **The free tier** may use prompts to improve Google's products. Use a paid key for real code.
- **Rotation** is the person's: replace the file. Relay reads it afresh on every turn.

### 2.9 Grants, file requests and Claude's sandbox

A write job can be granted extra directories (`grant.write_paths`), and a Claude or Codex job's own sandbox then lets it write there; it can also ask to write a file outside its worktree (a Claude edit, a Codex patch), which the root or the person may approve. Relay keeps the directories that decide which key it hands Gemini, or whether it hands one at all, from every job by each of these routes, as it keeps its control directory (`keyAuthority`, `src/core/api-keys.ts`, shared as relay's config protection is; review round 3 found the grant check alone covered them):

- a grant that overlaps one is refused (`checkGrant`, `src/core/caller.ts`);
- so is continuing a session with a grant it keeps that overlaps one now: one given by 0.9.x, before the check, or one the local config has since moved a key file into (`admitWork`). Given a new grant that leaves it out, the session goes on;
- a file request for a path in one is refused without anyone being asked (`requestApproval`, `src/core/approvals.ts`), as one for `config.json` is;
- Claude's turns deny writing all of them in its sandbox (`backends/claude.ts`), whatever the job holds.

While the local config is there but cannot be loaded (a link, a mode others can write, invalid JSON or schema), relay cannot be sure where it would move a key. It then grants no write path, lets no session go on with one it keeps, and approves no file outside the job's worktree, until it is fixed: a grant given meanwhile would outlast the fix and could cover the directory the fixed file names. The key files it names are still read from it as best relay can, for Claude's denials. Before review round 3, such a local config silently dropped the moved directory from the grant check.

The directories:

- `~/.config/relay`, holding the local config (§2.2);
- `config.json` itself, which holds the opt-in of §2.7: a job that could rewrite it could switch on `targets.gemini.child_auth: "any"` for later runs, and every other setting with it (the global `child_auth`, `same_family`). Review round 2 found that only the path `~/.config/relay` was covered, while the maintainer's `config.json` is a link into the synced `~/dotfiles/relay`. Relay's config protection (DM8, `src/core/protected-config.ts`, merged from a private branch) now refuses a grant of any directory holding the configured file or the file a link leads to, and the whole directory where it is relay's alone, so a grant of `~/dotfiles/relay` or `~/dotfiles` is refused, and one of a directory beside it is not. This lane had first protected the whole directory the file is in; that is withdrawn, since `RELAY_CONFIG` or a link can put the file in a project or the home folder;
- the default key directory;
- the directory of a key file the local config moves elsewhere.

Otherwise a job granted `~/.config` could swap in a key of another account, or point the local config at a file of its own, and later Gemini turns would send the repository to that account. A place no grant is needed for, a temporary directory, is refused as the key file's location instead (§2.3). Not covered: Codex's sandbox has no write denial inside a directory it may write, so for Codex these rules rest on the grant and file-request checks; nothing Codex may write without them holds a key directory.

## 3. The profile (`src/backends/gemini.ts`)

### 3.1 Launch

- **Command:** `gemini --acp --policy <home>/relay-policy.toml [--include-directories <dir>]… [--model <id>]`. Gemini has no reasoning-effort flag, so effort is not applied: relay takes `effort` and `targets.gemini.default_effort` for it and drops them (README says so). The policy is relay's (§3.2).
- **Granted directories.** Gemini's own file tools (`write_file`, `edit`) write only inside its workspace (`config.validatePathAccess`, `packages/core/src/config/config.ts:3379-3438`), which is the working directory and the directories `--include-directories` names; without them a write grant would serve only shell commands, and Gemini would refuse a command with a `dir_path` outside the workspace. So a write turn passes one `--include-directories` per granted directory (`geminiIncludeDirectories`). Gemini reads the flag from the process's arguments for every ACP session (`acpSessionManager.ts newSessionConfig`, `loadCliConfig(…, this.argv, …)`; `cli/src/config/config.ts:637-640`), in an untrusted folder too (`core/src/config/config.ts:1459-1461` adds them with no trust check) (source; seen 2026-10-22: `write_file` wrote a granted directory, and Gemini's refusal of another path named the granted directory among its workspace directories). It splits the value at commas and trims each part (`coerceCommaSeparated`, `cli/src/config/config.ts:119-129`), so a granted directory whose path has a comma, or starts or ends with a space, is left out; relay's sandbox still lets its shell commands write there. Neither changes the boundary: relay's sandbox decides what is writable.
- **Its commands.** Gemini runs a prompt whose trimmed text starts with `/` or `$` and names one of its ACP commands (`memory`, `extensions`, `init`, `restore`, `about`, `help`) as that command, and the model never sees it (`acpSession.ts:347-371`, `acpCommandHandler.ts:25-30`). Relay's first prompt of a turn starts with its own preamble, but a resume message or a follow-up goes as the caller wrote it, so the profile puts a line in front of one that starts so (`geminiPromptText`, through the generic `AcpProfile.promptText`, §6).
- **Its Node.** npm installs Gemini CLI as a script that starts with `#!/usr/bin/env node`. Relay's sandbox runs executables only from its fixed list and those a profile names, so the profile names the first `node` on the PATH Gemini is given (`execPaths`): a Node from a version manager (fnm, nvm) is on no fixed list. A turn given relay's tools (§3.8) also names their shim, by its path alone. Gemini's pseudo-terminal helper (`@lydell/node-pty-darwin-arm64/spawn-helper`) is on no list: the sandbox refuses it, and Gemini runs its shell commands without a pseudo-terminal, which worked (seen 2026-10-22).
- **What it did at start under relay's sandbox** (seen, made-up key, stopped before a prompt): it wrote only under `<home>/.cache/.gemini` (its project registry, history and two session files) and tried one write in `.gemini/` (the settings write above), refused; it made no connection at all (relay's proxy recorded no request); its other refusals were the keychain services (`com.apple.securityd.xpc`, `com.apple.SecurityServer`), `com.apple.SystemConfiguration.DNSConfiguration` and disk-space queries, none of which stopped it. It also prints "Error authenticating: … you must specify the GEMINI_API_KEY environment variable" before ACP starts, from a check of the configured method against its environment, and goes on.
- **Its home:** `GEMINI_CLI_HOME=<harness>/<run>/<node>/gemini`, one per relay session, relay's own, and read-only to the agent except `.cache/`.
- **`SANDBOX=sandbox-exec`.** With it, Gemini keeps its runtime state under `<home>/.cache/.gemini`: its project registry, `tmp/<project>/chats` with the sessions, and `history/`. Its configuration stays under `<home>/.gemini` (seen; source: `Storage.getGlobalRuntimeDir`, `packages/core/src/config/storage.ts`). That lets relay keep the configuration read-only and only the runtime state writable. It also tells Gemini it is already inside a Seatbelt sandbox, which is true (relay's), so it never starts its own (`packages/cli/src/config/sandboxConfig.ts`), and its system prompt says so (`getSandboxMode`, `packages/core/src/prompts/promptProvider.ts`). The research advised against `SANDBOX` because it moves the state; for relay, moving the state is the point.
- **Also set:**
  - `GEMINI_CLI_NO_RELAUNCH=true`: the pid relay watches is the agent, not a supervisor that relaunches it;
  - `GEMINI_SANDBOX=false`;
  - `GEMINI_FORCE_FILE_STORAGE=true`;
  - `GEMINI_CLI_TRUST_WORKSPACE=false` (§3.2);
  - `GEMINI_CLI_SYSTEM_SETTINGS_PATH` and `GEMINI_CLI_SYSTEM_DEFAULTS_PATH`, pointed at files that do not exist in relay's read-only home, so no administrator settings under `/Library/Application Support/GeminiCli` are read. Gemini reads system settings only from a path that passes its own security check (source: `isFileAndDirectorySecureSync`), so relay could not use that layer for its own settings anyway.
- **Removed from its environment:**
  - every `GEMINI_*` and `OTEL_*` variable;
  - `SANDBOX`, `SEATBELT_PROFILE`, `BUILD_SANDBOX`, `OAUTH_CALLBACK_*`, `DEBUG`, `DEBUG_MODE`, `NO_BROWSER`;
  - Google's credential and project variables (§2.4).
- **Refused (not launched with):** the endpoint variables in §2.8.
- **Confinement:** relay-enforced (`src/confine`), with a temporary `HOME`, no keychain, and no certificate-trust daemons (Node's TLS does not use them).
- **Refused before anything starts:**
  - without the per-target opt-in (§2.7);
  - when `/Library/Application Support/GeminiCli/policies` holds a policy file. Administrator policies outrank relay's and cannot be moved (source: `Storage.getSystemPoliciesDir`).

### 3.2 Untrusted folder: the deciding trade-off

In a trusted folder, Gemini 0.64.0 loads three things from the repository (source: `findEnvFile`, `loadEnvironment`, `_doLoadSettings`):

- its `.gemini/settings.json`, over the user settings (relay's);
- the `.gemini/.env` of the working directory or of the first directory above it that has one, with any variable in it;
- with `ignoreLocalEnv` off, a plain `.env` the same way.

One `GOOGLE_GEMINI_BASE_URL=` line in a committed `.gemini/.env` would send the person's key to someone else's server. `advanced.ignoreLocalEnv` does not stop that: it skips plain `.env` files only. Nor can relay outrank workspace settings: the one layer above them, system settings, must pass Gemini's security check.

So relay runs Gemini in an untrusted folder (`GEMINI_CLI_TRUST_WORKSPACE=false`, which wins over every trust setting; source: `checkPathTrust`). Workspace settings, `.gemini/.env`, workspace hooks and workspace skills are then ignored (seen: "Project hooks disabled because the folder is not trusted"; source: `SkillManager.discoverSkills`, `packages/core/src/skills/skillManager.ts:81-99`). Three more stay out whatever the trust (source, re-read 2026-10-22):
- **Workspace policies** are off in 0.64.0 for every folder: `disableWorkspacePolicies` is `true` (`packages/cli/src/config/policy.ts:42`, checked at `:108`), and it still is in 0.65.0 and the nightly of 2026-10-22.
- **Project commands** (`.gemini/commands`) are never loaded over ACP. `FileCommandLoader` serves only the terminal interface (`ui/hooks/slashCommandProcessor.ts:332-337`) and non-interactive runs (`nonInteractiveCliCommands.ts:43-47`); ACP has its own fixed commands (§3.1).
- **Project agents** (`.gemini/agents`) are not even looked for: relay's `experimental.enableAgents: false` (§3.3) returns before the trust check (`agents/registry.ts:167-169`, the check at `:174-232`). So "Skipping project agents due to untrusted folder", which an earlier version of this note gave as seen, cannot appear under relay's settings.

In an untrusted folder Gemini still reads a plain `.env` for four variables (`GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`), and then only those not already set. `ignoreLocalEnv` stops even that.

This costs three things, each checked in the source:

1. **No MCP server connects**, not even the bridge relay passes in `session/new` (source: `McpClientManager.startConfiguredMcpServers` returns at once in an untrusted folder, `packages/core/src/tools/mcp-client-manager.ts:576`, and so does `maybeDiscoverMcpServer` for each server, `:461`; unchanged in 0.65.0, 0.66.0-preview.0 and the nightly of 2026-10-22). Relay's tools reach a Gemini agent another way: Gemini's command-based tool discovery, which has no trust check (§3.8). Approvals do not need relay's tools: they come over ACP.
2. **The approval mode is forced to `default`**, which asks before every edit and command (source: `loadCliConfig`). Relay instead writes a policy of its own, `<home>/relay-policy.toml`, read-only to the agent, and hands it to each of its turns with `--policy`. In 0.64.0 that flag takes the place of the user policies directory and its rules keep the user tier, which outranks the default tier's questions (source: `getPolicyDirectories` and `createPolicyEngineConfig`, `packages/core/src/policy/config.ts`). It is never in `<home>/.gemini/policies`, the user policies directory Gemini loads by itself (`Storage.getUserPoliciesDir`): a native resume in the person's terminal (§3.5), outside any sandbox, would then run every tool unasked. Relay withholds that command. The policy allows every tool, as Copilot runs with `--allow-all-tools`, because relay's sandbox is the boundary and nothing approved lifts it. The shell rule sets `allowRedirection`, so a command with `>` is not downgraded to a question. Denied, each with a message to the agent:
   - `save_memory`, a tool 0.64.0 no longer has (its memory is a file, item 3), denied should a release bring it back;
   - `invoke_agent`, Gemini's subagents, which relay's settings also switch off (§3.3);
   - without a network grant, `google_web_search` and `web_fetch`. Both reach the web through Google's API host (search grounding and URL context run at Google). The denial is defence in depth, not what keeps the turn off the web: any command the agent runs can reach that host through relay's proxy, and with a Gemini API key of its own (one planted in the repository, say) call the same server-side tools, which fetch any URL, or store data under that key's project. The proxy sees only the host. README, "What it does not do", says so.

   Gemini still asks, over ACP, about shell commands its own checks single out. The source names git in an untrusted folder and commands it rates dangerous (`PolicyEngine` shell heuristics). Relay reads those requests as Gemini sends them (§3.6) and handles them as it handles Copilot's. Git reads work inside relay's sandbox; writes to `.git` do not.

   Seen in the qualification run of 2026-10-22, a write job:
   - The user-tier `allow` takes effect in `default` mode: `write_file`, `update_topic` and `mkdir -p scratch-tmp && rm -rf scratch-tmp` ran without a request.
   - The one request that reached relay was `git status --short`, in the shape §3.6 reads. The sandbox then refused git's write of `index.lock` in `.git`.
   - A `dir_path` outside the workspace is not asked about: Gemini refuses it itself ("Path not in workspace …"), and nothing reaches relay.
3. **The repository's `GEMINI.md` is not loaded**, since Gemini loads project memory only in a trusted folder. The task relay sends carries what the agent needs. Gemini's *private* project memory is another matter (review round 4): 0.64.0 loads `<runtime>/tmp/<project>/memory/MEMORY.md` into every session whatever the folder's trust (source: `MemoryContextManager.discoverMemoryPaths`, its `userProjectMemory`, `packages/core/src/context/memoryContextManager.ts:49-64`), and its system prompt tells the model to keep notes there with its file tools ("Private Project Memory", `packages/core/src/prompts/snippets.ts`; "There is no `save_memory` tool"). That directory is in the runtime state relay keeps and the agent can write (§3.3), so relay removes it before every turn and after it (`clearGeminiMemory`), without following a link. Otherwise what a turn wrote there would come back as standing instructions in the session's later turns, and in the person's own resumed session (§3.5).

The research proposed `GEMINI_CLI_TRUST_WORKSPACE=false` as well, without noticing the first two consequences.

### 3.4 Family and model

- `vendor: "google"`. On this path Gemini CLI talks only to Google's Gemini API, and every endpoint redirection is refused, so every model it can reach is Google's (Gemini, Gemma). The family logic is the generic driver's: a fixed-family target's family is its vendor whatever the model.
- **The session's model list is a menu, not the set of models it takes.** 0.64.0 builds it from feature flags (source: `buildAvailableModels`); under relay's sandbox it listed `auto`, `gemini-3.1-pro-preview-customtools`, `gemini-3-flash-preview`, `gemini-2.5-pro`, `gemini-3.8-flash` and `gemini-3.5-flash-lite` (seen, made-up key). `--model` takes any id, which the API then serves or refuses: Gemma 4, Gemini 3.6 Flash and others are not on the menu. Relay's driver refuses a model a session does not list (a check made for Copilot Free, whose list is what the account may use). Gemini's profile says its list is a menu (the generic hook `AcpProfile.acceptsUnlistedModels`, §6), so relay runs a model the list leaves out. The model the session reports must still be the one relay asked for (seen: with `--model gemini-3.8-flash` it reported `gemini-3.8-flash`).
- With `--model <id>`, the session reports that id as `models.currentModelId`, and relay checks it before the prompt, as it does for every ACP target. Without one, Gemini reports `auto` and routes between Pro and Flash itself. `auto` is the target's `autoModel`: like no model, it is not a pin, so whatever Gemini routes to is what it chose, recorded with no note, under either `same_family` setting (the coordinator's decision, `f33ca20`). Gemini's other aliases (`pro`, `flash`, `flash-lite`, and the deprecated `auto-gemini-3` and `auto-gemini-2.5`) count as pins: the model they resolve to gets the within-Google note below.
- Which models Gemini used is reported only in the prompt's response, `_meta.quota.model_usage[].model`. Gemini's profile reads it through the generic `AcpProfile.servedModels` hook (§6), with `geminiServedModels`. Read in the 0.64.0 source (tag `v0.64.0`, commit `4a0749a`), that list is:
  - **The main loop only.** It is built from `modelUsageMap` alone (`packages/cli/src/acp/acpSession.ts:379-409`), filled from the `Finished` events of `geminiClient.sendMessageStream` (`:576-584`), the stream of the main chat (`turn.run` with `LlmRole.MAIN`, `packages/core/src/core/client.ts:832-836`). Gemini's helper calls, Flash-Lite among them, go through `BaseLlmClient`, whose calls yield no event into that stream, and so never enter it: the router's classifier (`packages/core/src/routing/strategies/classifierStrategy.ts:171-178`, `LlmRole.UTILITY_ROUTER`), the next-speaker check (`client.ts:909-913`, `utils/nextSpeakerChecker.ts:113-119`), loop detection (`services/loopDetectionService.ts:704-712`) and chat compression (`context/chatCompressionService.ts:595-639`). Nor do the web tools' own model calls (`geminiClient.generateContent`, `tools/web-search.ts:95`, `tools/web-fetch.ts:475`, `:806`), nor its subagents, which relay switches off (§3.3). This settles the question raised in review: `model_usage` does not name same-family helper calls, and `geminiServedModels` assumes it does not. Checked again on 2026-10-18 at the same commit: `GeminiEventType.ModelInfo` is yielded only at `client.ts:826` and `Finished` only by `Turn.run` (`core/turn.ts:408`), and every `Turn` is made on the main chat (`client.ts:652`, `:775`, `:970`, `:976`, `:991`).
  - **One entry per model, in order of first use**, keyed by the round's `turnModelId`: the configured id, `config.getModel()`, at the start of each round (`acpSession.ts:427`), replaced by the model the stream says it routed to (`ModelInfo`, `:494-495`).
  - **The routed model for the first round only.** `ModelInfo` is yielded only while no model is fixed for the prompt (`client.ts:825-828`), which is reset only for a new prompt id (`:953-958`), and ACP keeps one prompt id for every round of a prompt (`acpSession.ts:326`, `:434-437`). So every round after a tool call is listed under the configured id, though the routed model answered it: `auto` with no pinned model, or the pin itself where Gemini resolved it to another id (it promotes `gemini-3.5-flash` to `gemini-3.8-flash`, say, `packages/core/src/config/models.ts:311-317`; the pin is resolved in `routing/strategies/overrideStrategy.ts`).

  - **The model Gemini selected for each round, not always the one that served it** (review round 4). An availability fallback happens inside a round: GeminiChat's retry calls `handleFallback` (`packages/core/src/core/geminiChat.ts:1191-1194`), a silent policy action switches the model (`fallback/handler.ts` `processIntent` → `config.activateFallbackMode` → `setModel`, `config/config.ts:1945-1951`), and the round's next API call goes to it (`geminiChat.ts:1018-1030`). That round is still listed under the model that failed (its `turnModelId`), and the fallback shows only from the next round, under `config.getModel()`, which `setModel` changed. So a one-round prompt that fell back lists only the model that failed, and a longer one also lists the failed model as having served.

    Over ACP, such a fallback is rare (0.64.0 source; seen 2026-10-22):
    - `retryWithBackoff` hands a quota or not-found error to `handleFallback` (`packages/core/src/utils/retry.ts:346-418`). Only the interactive CLI sets a fallback handler, so a policy whose action is `prompt` (the default) ends in the error. A pinned model that Google does not serve (`gemini-1.5-pro`, retired) failed the turn with `ModelNotFoundError`, and no fallback followed.
    - The fallbacks that do happen are silent, and in two places only (`availability/policyCatalog.ts`): the Flash-Lite chain (Flash-Lite, then Flash, then Pro), and under `auto`, Pro to Flash on a transient failure.
    - A pinned model outside the default chains has nothing to fall back to (`availability/policyHelpers.ts`, `applyDynamicSlicing`).

  So a second model of the same family in the list is not a helper: it is a model the first round was routed or promoted to, an availability fallback seen from the round after it, or the configured id standing in for the routed one. `geminiServedModels` drops every alias, and the model the session reported (its configured id, which the driver now hands the hook) after the first entry. What is left is a model Gemini selected, and a model report like any other: logged, recorded with the item's served models and its family label, and, where relay pinned a model, one other than that is a switch. For a fixed-family target such as Gemini every such model is Google's, so a switch is always one within the pinned model's family: one note for the turn ("switched within Google; same_family policy unaffected"), and the turn goes on, under `"allow"` and `"refuse"` alike (the coordinator's decision, `f33ca20` and `8899b13`). The family label stays Google's.
- With a free key, name a Flash model (`targets.gemini.default_model: "gemini-3.8-flash"`). `auto` may pick Gemini 3.1 Pro Preview, which has no free tier.

### 3.5 Sessions and resume

Gemini has `session/load` but not `session/resume` (seen: `initialize` reports `loadSession: true` and no `sessionCapabilities`). Relay continues a session by loading it. ACP v1 has the agent replay the conversation before it answers `session/load`; Gemini answers first and streams the replay afterwards (source: `packages/cli/src/acp/acpSessionManager.ts:284` calls `session.streamHistory(messages)` without waiting for it, then returns the answer at `:294`; `streamHistory`, `acpSession.ts:249-315`, awaits each update in turn). At runtime (2026-10-22, three loads), the whole replay reached relay's pipe before the answer did, but nothing in the source guarantees that. Relay's driver took everything after the answer for the new turn, so a resumed turn's reply could begin with the previous one (review round 2). Gemini's profile now says so (`replaysAfterLoad`, §6): relay sends the prompt only once the session has sent no update for 300 ms, and fails the turn if the replay is still going after 30 s. Gemini sends nothing of a new prompt before the prompt, and its first words wait on a round trip to Google, so the quiet separates the two; the replay itself is local history written as fast as its pipe takes it. Should a replayed user message (`user_message_chunk`, which Gemini sends only in a replay) come after the prompt all the same, the turn's result carries a warning that its reply may begin with part of an earlier one.

**Gemini's own session cleanup is off.** 0.64.0 runs a session cleanup at every start, ACP included, unless the settings turn it off. It is on by default, with a `maxAge` of 30 days. It deletes:
- every session idle past `maxAge`;
- every session file with nothing resumable in it, such as one whose only prompt failed before the model answered.

The sources are `packages/cli/src/gemini.tsx:786`, `utils/sessionCleanup.ts:116` and `:302-311`, `utils/sessionUtils.ts:295`, and `config/settingsSchema.ts:389-437`. `session/load` itself loads a session by its id, reply or none (`acp/acpSessionManager.ts:216-219` passes `allowEmpty`; `utils/sessionUtils.ts:513-547`). So the cleanup was what failed relay's resume.

It was seen in the qualification run (2026-10-21, [record](qualification/gemini-0.64.0.md)): a key with no credit got a 402 at the first prompt, and the next turn's Gemini deleted the session before relay loaded it. Every follow-up then failed with "Internal error", and with "Invalid session identifier" in its data.

Relay's settings now turn the cleanup off (`general.sessionRetention.enabled: false`, §3.3). With that off, the cleanup returns before it looks (`sessionCleanup.ts:116`), and relay's user settings outrank the schema's default (`config/settings.ts:255-280`). This was checked with the real 0.64.0 binary, under a Seatbelt profile denying outbound network, with a made-up key and no prompt, on a copy of the run's session that got no reply:
- with the schema's default, Gemini deleted it at start, and `session/load` failed as above;
- with relay's settings, it was kept, and `session/load` loaded it and replayed it.

The cost:
- Gemini's start-up session files, one per turn, and its tool outputs are no longer deleted by Gemini. They stay in the item's Gemini home until relay's retention removes the run's harness state (`core/retention.ts`).
- A session that is gone all the same (removed by hand, say) is not replaced. The turn fails, with Gemini's reason (§6, ACP errors).

Relay withholds the native resume command, as it does for Grok. `status` and `result` return `resume_natively: { command: null, note: ... }`, with the reason: continue the session with relay's `resume`, which loads it inside relay's sandbox with the turn's current grant checks.

A native `gemini --resume` on relay's Gemini home would run outside relay's sandbox, with relay's settings rather than yours, and replay chats that anything in a confined turn could write, read jobs included (`.cache/.gemini/tmp/<project>/chats`). A turn steered by a prompt injection could leave instructions there for the unconfined session. Only Gemini's own approval prompts would stand between those instructions and your machine: relay's allow-all tool policy is handed only to relay's own turns (`--policy`, §3.2), never left where Gemini loads policies by itself. That is why relay offers no native command.

The `SANDBOX=sandbox-exec` needed to locate those sessions (`Storage.getGlobalRuntimeDir`) would start no sandbox of its own (`packages/cli/src/config/sandboxConfig.ts`), though Gemini's system prompt would tell its model it runs under macOS Seatbelt (`packages/core/src/prompts/promptProvider.ts`, `snippets.ts`). Pointing `GEMINI_CLI_HOME` at `.cache` instead would find the session without that variable, but would load configuration from the directory the confined agent can write. Neither is a confined continuation. Relay removes Gemini's private project memory after every turn (§3.2, item 3); the chats needed for resume remain writable, so that removal does not make a native resume safe.

### 3.6 Approval requests

Gemini 0.64.0 sends no `rawInput` with a tool call (source: `Session.runTool`). A shell command's call has kind `execute`, the command itself as its title (`ShellToolInvocation.getDisplayTitle` returns `params.command`), and one text content saying where it runs and why: `[in <dir_path>] (<description>)`, or `[current working directory <cwd>] (…)`. Relay's generic reading needs `rawInput.command` and would refuse every such request as unclear, so Gemini's profile reads the title as the command and the text for the directory and the reason. Edits carry their paths in `locations` and their diff, which the generic reading takes. Relay answers with the request's `allow_once` or `reject_once` option only, never an "always" one, which relay's settings also switch off. Whatever is approved, relay's sandbox stays on, and the request says so.

A `dir_path` that itself contains `] (` would be split in the wrong place; the command shown is still the one Gemini runs.

### 3.7 Network

The API host for relay's per-turn proxy is `generativelanguage.googleapis.com` only. Gemini routes its requests through `HTTPS_PROXY` with undici's `EnvHttpProxyAgent` (source). undici sends `Proxy-Authorization` only when the proxy URL has both a user and a password; relay's proxy URL is `http://relay:<token>@127.0.0.1:<port>`, which has both. Seen with a real key on 2026-10-21: relay's proxy admitted Gemini's tunnel to that host, which it refuses without the token, and Google's answer came back through it ([record](qualification/gemini-0.64.0.md), 4). Left out, and so refused: Clearcut telemetry (`play.googleapis.com`, off in relay's settings anyway), the Code Assist and OAuth hosts of the Google-login path, and the npm registry (its update check runs only in its terminal interface).

### 3.8 Relay's tools, through Gemini's tool discovery

Added after the first two qualification runs. It was seen with the real binary on 2026-10-22, at `072c34b` (§8, 12-17; [record](qualification/gemini-0.64.0.md), third run). Everything below is source, read in 0.64.0 (tag `v0.64.0`, commit `4a0749a`) and checked unchanged in 0.65.0, 0.66.0-preview.0 and the nightly of 2026-10-22, or relay's own tests against the stub.

**Why this route.** In the untrusted folder relay runs Gemini in, no MCP server connects (§3.2, item 1), and nothing lets a server the ACP client supplies connect while the folder stays untrusted: those servers are merged into `settings.mcpServers` with no mark of where they came from (`acpSessionManager.ts:379-424`), and the trust checks see only the folder. Trusting the folder would bring back everything §3.2 keeps out. Gemini's command-based tool discovery has no trust check at all (`packages/core/src/tools/tool-registry.ts:376-540`; the file names no trust), and it reads its two commands from the settings, which in an untrusted folder are relay's alone.

**How Gemini runs it** (source):
- `tools.discoveryCommand` runs whenever one of Gemini's configs is initialized (`createToolRegistry`, `core/config.ts:4126`): while it answers ACP `initialize`, for its start-up config (`acpRpcDispatcher.ts:81` awaits `config.initialize()`; the command comes from the same user settings, `cli/src/config/config.ts:985`), and again for each session, `session/new` and `session/load` alike. Gemini splits it into words with shell-quote and spawns it without a shell. A non-zero exit, or output that is not a JSON list, throws (`:530-539`), and `initialize` or the session fails to start. Each function declaration becomes a tool named `discovered_tool_<name>` (`DISCOVERED_TOOL_PREFIX`, `tools/tool-names.ts:237`; `tool-registry.ts:518-526`), of kind `Other`.
- `tools.callCommand` runs for each call: spawned without a shell, so a path alone; the tool's own name as its one argument; the arguments as JSON on stdin (`:76-113`). Its stdout is the result. An error starting it, a non-zero exit, a signal or anything on stderr is a failure, and the model is shown stdout, stderr, the exit code and the signal (`:157-173`).
- Both run with Gemini's environment after its redaction (`NoopSandboxManager.prepareCommand`, `services/sandboxManager.ts:296-306`), in its working directory, with no time limit; the call's abort signal is not used.
- Each discovered tool's description is relay's own followed by a paragraph 0.64.0 adds (`DiscoveredTool`, `:199-215`): it names both command strings, and then explains the output (stdout, stderr, error, exit code, signal). The model sees them.

**What relay does** (`backends/gemini.ts`, `geminiTools`):
- **When.** On every turn relay serves its tools to, one that may delegate (`ChildContext`, so one with a broker), on any Gemini version relay's general version gate runs (`tested`, 0.64.0, and later; below it, relay refuses Gemini as it refuses every target, unless `allow_untested` is set). What keeps the tools safe is relay's sandbox and broker (the secret's file readable only by its own turn among relay's sandboxes, the process-tree check, the live turn), not Gemini's version; what a version can break is whether they work. Relay cannot check that ahead of a call; what it checks at every launch, instead of keeping a list of versions, is that Gemini ran relay's discovery command for the session:
  - **The mark.** The helper's `--list` leaves a mark, `.relay-tools-listed`, in the turn's private temporary directory, which the turn may write and which goes with it, by the path `bridge.json` names (relay's Gemini home is read-only to the agent).
  - **The check before the prompt** (`geminiDiscoveryCheck`, through the generic `PreparedState.beforePrompt`, §6). 0.64.0 and 0.65.0 run discovery twice per process. First while they answer `initialize`: `acpRpcDispatcher.ts:81` awaits the start-up config's `initialize()`, whose discovery command is relay's, from the same user settings (`cli/src/config/config.ts:985`). Then while they set up each session's config, before they answer `session/new` or `session/load`: both await `config.initialize()` (`acpSessionManager.ts` `newSession`, `loadSession`). Each `initialize()` builds the tool registry (`core/config.ts:1508`; `:1510` in 0.65.0) and so runs discovery (`:4126`; `:4132`). So the mark from `initialize` would hide a session whose own setup skipped discovery: relay removes it once `initialize` (and `authenticate`) have answered and before it asks for the session (`geminiClearMark`, through the generic `PreparedState.afterInitialize`, §6), and looks for it again once the session is set up (and a loaded session's replay is over), before the prompt goes out. The mark shows only that Gemini ran relay's discovery command for the session: not that Gemini registered the tools, nor that a call will work.
  - **Where there is none**, relay puts a line before the turn's prompt, in the same message, so that the agent reads it before it acts: "[relay] Before you start: relay's tools are not available to you in this turn after all. Gemini did not run relay's tool discovery when it set up this session, so you have no discovered_tool_ tools: …; do the work yourself" (`NO_DISCOVERED_TOOLS`). The turn's warnings say that this Gemini version did not run it. The turn is not failed: Gemini works without relay's tools. A resumed turn is checked as a new one is. Discovery that runs and fails is another matter: Gemini then fails `initialize` or the session (above), and so the turn, at its start. The remedies are a Gemini version relay's tools were verified on (`toolDiscovery.versions`), or `allow_delegation: false` for the work, which sets up no discovery; relay has no switch of its own for it.
  - **`toolDiscovery.versions`** (from `VERIFIED.geminiToolDiscovery`, `targets/verified.ts`; now <!-- verified:geminiToolDiscovery -->0.64.0, 0.65.0, 0.67.0 and 0.68.0<!-- /verified -->) lists the versions relay's tools were verified on live (0.65.0: its discovery, trust gate and session code are 0.64.0's, and checks 12-15 passed on it, [record](qualification/gemini-0.65.0.md)). It is informational: `relay doctor` says whether the installed version is one of them, and a turn on another version where Gemini ran relay's discovery command gets a short note saying that it is not a verified version (the note claims no more than that the command ran), from the version Gemini reports in `initialize` (`agentInfo.version`, compared whole, so a pre-release of a listed version is not it). Nothing reads the version to decide whether to offer the tools, and the MCP server no longer reads it to write a preamble: the preamble describes the tools to every node that may delegate, and the check above corrects it where discovery did not run.
  - **A call that a new version breaks** comes back to the model as a failed tool call, with what failed in plain words: a helper run with arguments it does not take, arguments that are not a JSON object on stdin (both saying Gemini may have changed how it runs tool commands), relay out of reach, relay refusing, or the tool's own error. None quotes the secret.
- **The shim.** `<home>/relay-tools/call`, written before each such turn with the rest of the home (§3.3), read-only to the agent, one of the profile's `execPaths` (§3.1). It holds paths only: `exec /usr/bin/env -i <relay's node> --no-warnings <relay>/dist/confine/gemini-tools-main.js <home>/relay-tools "$@"`. That entry point imports `confine/gemini-tools.js` and nothing else, which imports only `node:fs`, `node:net` and `node:path`: not `cli.js`, whose import graph reaches `node:sqlite`, which before Node 24.15 (relay's minimum since 1.2.0) printed an `ExperimentalWarning` on every run, which Gemini 0.64.0 would take for a failed call. `--no-warnings` is a second guard. (`relay gemini-tools` runs the same code through `cli.js`, for a person at a terminal.) Relay's settings name it twice: `'<shim>' --list` for discovery, and the bare path for calls.
- **The list is static.** Once the turn's broker is open and before Gemini starts (`PreparedState.bridgeReady`, §6), relay asks the broker for the tools a bridge connection would be offered (`Broker.listTools`: a server made exactly as each connection's is, listed in process) and writes them to `tools.json` as Gemini's declarations: name, description and input schema, exactly as the bridge's `tools/list` gives them. The helper's `--list` prints that file, leaves the mark, and reads nothing but `bridge.json` for where the mark goes, so a broker that has gone cannot fail Gemini's session setup, and a mark it cannot leave fails nothing (relay then tells the agent its tools are unavailable, the safe side). A turn that may not delegate has no broker, and its settings name no discovery; a turn with a broker and no tool to offer discovers an empty list. A relay tool Gemini could not name, or whose discovered name a rule of relay's policy denies, fails the turn before Gemini starts (`writeGeminiToolFiles`); with the prefix no relay tool can take a denied name.
- **A call goes through the broker.** The helper with a tool's name (`confine/gemini-tools.ts`) reads the arguments from stdin, reads the turn's secret from the file `<dir>/bridge.json` names (paths only: the socket and the secret's file), presents it on the socket, as the bridge presents it, and then calls the tool over MCP: `initialize`, `initialized`, `tools/call`. The broker checks the call as it checks the bridge's: the peer's uid and its place in the launched harness's process tree, the secret, then the live turn for every request (`openBroker`'s connection handler in `confine/broker.ts`: `socketPeer`, `inProcessTree`, `handshake`; then `GatedTransport`). The result's text goes to stdout. Stderr is written only on a failure: a tool error, a refusal, or relay out of reach, in which case the agent is told to continue without relay, in the bridge's words.
- **The secret** is in the broker's own file, `bridge-secret` beside the socket in the turn's private broker directory (mode 0600; `Broker.secretFile`), inside relay's sockets directory. Every confined turn's profile denies that directory whole; this turn's alone allows reading that one file, by name, after the deny, as it allows its own socket (`ConfinementPolicy.bridgeSecret`, `confine/seatbelt.ts`; the boundary probes check that it reads, that it does not open for writing and that the directory does not list). So no other relay-confined turn can read it: one running at the same time is refused reading it, testing for it or listing beside it (EPERM, tested end to end). Claude's turns may not either: relay adds its sockets directory to every Claude turn's sandbox `denyRead` and its `Read` deny rules (`backends/claude.ts`), as it does the key directories. Codex jobs can read it, since Codex's sandbox has no read denial (as with the key file, §2.6), and so can the person's own processes, outside any sandbox, as they can read the bridge's environment. For them the gate is the broker's process-tree check: the secret alone gets nothing from a process outside the turn's own tree (tested from outside the tree, end to end). It is never on a command line, in an environment or in relay's Gemini home, since Gemini shows both command strings to its model. This turn's own commands can read it, as they can read the bridge's from the bridge's start-up environment (`kern.procargs2`, §2.4, §7 question 2): the broker serves only the turn's own process tree, for as long as the turn is live, so the secret adds nothing to what the agent can do through its tools. Relay registers the secret for redaction as it registers the bridge's; the file goes with the broker's directory when the turn ends, and `cleanup` removes `<dir>`.
- **The policy** allows them: `discovered_tool_*` match its `toolName = "*"` rule (`PolicyEngine`, `policy-engine.ts:167`), so a call is not asked about. Its denials name Gemini's own tools exactly, and none begins with the prefix.
- **The prompt** names them: "In this harness each relay tool's name starts with discovered_tool_ (discovered_tool_delegate, …): where relay's texts name a tool without it, call it with it" (`core/prompts.ts`, from `toolDiscovery.prefix`). Relay's tool descriptions, which name other tools bare (status, resume, merge), stay as the bridge gives them.
- **Still passed:** the bridge entry in `session/new`, which Gemini leaves unconnected. Should a release connect it, the agent would have both sets.

**What it does not carry over** (unlike the bridge, as Claude and Codex get it):
- **The server's MCP `instructions`** (relay's family steering, its notice rule, a gateway note) reach the model only with an MCP connection. The preamble carries the family steering for a launched agent (`crossFamily`), and `status` and `result` carry the notice rule in their descriptions.
- **Tool annotations** (`readOnlyHint` on `status`, `result` and `brief`): a discovered tool is always of kind `Other`.
- **Progress notifications** while a call waits, and cancellation: Gemini waits for the command to end, and relay ends it with the turn.

## 4. Setting it up

1. Create a Gemini API key in Google AI Studio. A paid-tier key is needed for real code: free-tier prompts may be used by Google.
2. Save it at a hidden prompt, so it never reaches the shell history or the screen:
   ```sh
   mkdir -p ~/.config/relay-keys && chmod 700 ~/.config/relay-keys
   (umask 077; printf 'Gemini API key: '; IFS= read -rs KEY; echo; printf '%s\n' "$KEY" > ~/.config/relay-keys/gemini-api-key; unset KEY)
   ```
3. Install Gemini CLI 0.65.0 (or 0.64.0) from npm (Homebrew's formula is frozen at 0.46.0): `npm install -g @google/gemini-cli@0.65.0`. Relay offers its tools on any version it runs, and checks at each launch that Gemini ran their discovery; `relay doctor` says whether the installed version is one they were verified on live.
4. In relay's config: `"targets": { "gemini": { "enabled": true, "child_auth": "any", "default_model": "gemini-3.8-flash" } }`, and `"default_target": { "claude": "codex", "codex": "claude" }` (or the defaults wanted). Gemini's family is Google's whatever the model, so with it on a Claude or Codex session that leaves `target` out has two agents of another family, and relay refuses the call as ambiguous (`resolveTarget`, `src/targets/index.ts`) until `default_target` picks one.
5. `relay doctor` says whether the key file is in place and private, and whether confined agents are kept from it, without reading it out.
