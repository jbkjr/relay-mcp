# Security model

has the summary, [Known limits](known-limits.md) the stated limits, and [SECURITY.md](../SECURITY.md) how to

## What relay relies on, what it checks, and what it does not do

- **Pinned Codex, and what a shipped pin trusts.** Relay runs Codex only from a qualified pin; a pin shipped with a release is the maintainer's qualification, taken on trust for your Mac. What that trusts, what relay checks and how to remove the trust: the README's [Pinned Codex](../README.md#pinned-codex-what-a-shipped-pin-trusts), and [docs/pinned-codex.md](pinned-codex.md).
- **Relay's config and install files.** Grants and file approvals cannot cover the configured or resolved config file, `install.json` or `install-backups`. Claude's write denies and relay-enforced confinement protect them too, including their directories where dedicated to relay. A broad directory (home or a project, for example) gets file protection only; doctor reports why, and a process allowed to write that directory could replace its protected files by renaming the directory. A Codex write job run without a sandbox (`allow_dangerous` with stage 2 off) can still write these files.
- **Commands running relay's CLI.** In every session the model's `approve` refuses to allow these, including with `user_confirmed`; it may deny them. The person can allow through the host's dialog, `confirm`, or their own terminal. Relay checks shell commands and argument vectors conservatively, including wrappers and inline scripts; an ambiguous command goes to the person. Script files, aliases and names assembled at runtime remain outside this check, so leave `relay` out of shell allow rules and auto mode's allowed commands.
- **The person's terminal.** `relay approve`, `relay cancel`, `relay adopt`, `relay clean --forget` and the `relay chat` message paths refuse to act inside a relay-launched agent's process tree, directing the caller to the person's own terminal. Relay places the caller by the environment markers it sets on launched agents (`RELAY_RUN_ID`, `RELAY_NODE_ID`, …), and, as backstops, by whether an ancestor, process group or session is one relay launched (leader ids kept for the run's lifetime); what it cannot read fails closed. `relay approve` additionally requires an interactive terminal and a one-time code the person types back before it will *allow* a request (`relay deny` needs neither). This raises the bar against a naive or accidental approval; it is **not** a security boundary. An unconfined process in the person's account can clear the markers, detach into its own session and group, present a pseudo-terminal and read the printed code back — and such a process can equally write the registry directly or decide through the root session. The real protection is confinement keeping a launched agent out of relay's state; an `allow_dangerous` or outside-sandbox command carries the person's authority over approvals. A root session's shell remains governed by its host's permission system. Design and probes: [docs/approve-boundary.md](approve-boundary.md).
- **Local IPC and loopback from a network-granted Codex job** (closed in 1.0.5 for strict mode). Codex's own sandbox, with its network toggle alone, also opens AF_UNIX sockets anywhere and all of loopback: a job could reach your terminal-multiplexer server and local login service, both acting with your authority. Since 1.0.5 relay never sets that toggle alone: a granted Codex job's shell goes through Codex's network proxy in strict mode (loopback, private and link-local addresses refused by the proxy, Unix sockets only under the turn's temporary directory and the job's worktree), verified before each turn, or it gets Codex's hosted web search only. Local mode (`grant.local_network`, your consent per job) deliberately opens all of loopback and the LAN again, for that job, through the proxy: there, a network grant gives the job the reach of your account. What strict mode still does not cover is under [Known limits](known-limits.md).
- **Claude hooks and consent.** Relay scans settings and subagent definitions, installed plugin manifests and hooks (including cached and in-place installs), and personal/repository/plugin skill frontmatter. Matching tool hooks withhold `confirm` and `adopt` permission-prompt authorization; matching elicitation hooks withhold the dialog. Any skill frontmatter `hooks` key, YAML relay does not model (anchors, aliases, tags, flow mappings, quoted keys and the like), unreadable plugin manifest or uninspectable hook module conservatively withholds both routes; ordinary values such as `allowed-tools: Bash(git add:*)` and `[Read, Grep]` lists do not. A marketplace entry that declares hooks, agents or commands withholds both. One that declares only skills, such as the `anthropic-agent-skills` marketplace, withholds only if a declared skill in some copy of the plugin on disk has a `hooks` key, or relay cannot read it, or it leads out of the plugin directory. These checks also cover extension consent and gated-tool calls. CLI-only plugins whose source cannot be established withhold consent routes too; command-line-only agent definitions remain uninspected. Terminal adoption tickets still work. [Scope and Claude Code sources](extensions.md#consent-scans-include-extension-hooks).

- **Who is trusted.** The session you start relay from, the root, is fully trusted. It can grant network access and extra write paths, merge branches into your tree, and decide approval requests. Relay does not protect you from your own root agent. Under Codex, relay's install lets its tools run without Codex asking you each time, `approve` excepted, and with `approvals_reviewer = "guardian_subagent"` Codex's automatic reviewer may let `approve` through without asking you. On unrecognised hosts, as with Claude Code's native subagents, relay cannot tell a host subagent from the main conversation. The root approval path remains available; it is not proof that a person answered. A root with a shell can also run `relay approve`.
- **What confines a launched agent.** For Claude and Codex, each harness's own macOS sandbox, as relay configures it (verified confinement): a write job can write only in its worktree, granted paths and its own private temporary directory, a read-only session only in the temporary paths its harness permits, and shell network access is off unless granted or approved. For them relay is not itself a sandbox, but it refuses a write turn whose worktree or granted directories hold a file hard-linked from outside them (the sandboxes decide by path, so writes would go through such a link; pnpm's store makes them). Reads are not confined: a launched agent can read whatever you can (a Codex or Claude agent, but the never floor's credential stores: `~/.ssh`, `~/.aws`, `~/.gnupg`, `~/.netrc`, the CLIs' logins, the keychain files and so the items in them; what the security daemons serve without a keychain file is not covered, see Known limits), and with web access it has a way to send it out. Harnesses whose own sandbox relay cannot verify get relay-enforced confinement instead (next point).
- <a id="what-a-claude-job-cannot-do-under-the-never-floor"></a>**What a Claude job cannot do under the never floor.** Its shell (Claude Code's sandbox `denyRead`/`denyWrite`) and its Read and Edit tools (deny rules) cannot reach the floor's paths, so inside a Claude job `gh` with a token in its `hosts.yml`, git over SSH (`~/.ssh`), GPG signing (`~/.gnupg`), `~/.netrc` credentials and the AWS and gcloud CLIs fail. Keychain items in the login keychain stay out of reach too, so a token `gh` keeps in the keychain and what git's osxkeychain helper stores are unreadable: Claude Code's sandbox lets commands reach the security daemons, but reading an item also needs its keychain file, which the floor denies (measured 2026-11-04; checked each release by `claude-floor`). What the daemons serve without a keychain file, such as data-protection keychain items, is not covered, nor is a copy of a keychain file kept outside the denied directories. No command runs outside the sandbox: Claude's own unsandboxed retry is off (`allowUnsandboxedCommands: false`) and relay refuses a command approval for it, so such work goes to a Codex job or the person. Relay refuses every Claude job under `child_settings: "inherit"`, `child_hooks: true` or `child_mcp: "inherit"` (global settings), and when organisation-managed Claude Code settings are on disk whatever `claude_managed_settings` says; it refuses Claude write jobs under `allow_dangerous`. With a `never.hosts` entry, Claude's WebSearch and WebFetch are denied. The floor binds the sandboxed commands and the file tools, not the Claude Code process itself, which still signs in from the keychain. The escape hatch is `never.override_builtin` (for example `credentials.files` or `credentials.keychain`, each with its acknowledgement), which removes a built-in group for new runs of every agent, Codex included, not for Claude alone; it lifts denies, not the refusals above, and `relay.config`, `relay.install` and `relay.authority` cannot be removed.
- **Turn state and grants.** Native Claude and Codex turns each receive a private temporary directory under `~/.rn`; Claude receives both `TMPDIR` and `CLAUDE_CODE_TMPDIR`. Claude Code keeps its own temporary directory to 44 bytes as written (`$CLAUDE_CODE_TMPDIR/claude-<uid>`), and beyond that gives its sandboxed commands the shared `/tmp/claude-<uid>`. So when your home folder path is longer than about 22 characters (an account name over about 15), relay gives Claude the same directory under a short name: a link, `/Users/Shared/.rn-<uid>`, to `~/.rn`. The turn's files stay in `~/.rn`, and Claude's sandbox is given their real path. That works because Claude Code measures the name before resolving links, which relay has read in Claude Code <!-- verified:claudeTempLink -->2.1.302, 2.1.303, 2.1.304, 2.1.308, 2.1.325 and 2.1.326<!-- /verified --> (not 2.1.305 to 2.1.307 or 2.1.309 to 2.1.324, which lie between versions that measure it the same way); the ceiling is <!-- verified:claudeTempLink:last -->2.1.326<!-- /verified -->. Relay's version gate is a floor and Claude Code updates itself, so on this path relay refuses a newer Claude Code, or one whose version it cannot read, unless `allow_untested` is set, and names both versions. So relay keeps Claude out of shared temp on the Claude Code versions whose code it has read, and refuses newer ones under a long home unless told to run unverified. Relay makes the link if it is missing and checks it before every Claude turn: a link (not followed), owned by you, pointing exactly at your `~/.rn`, with every directory on the way owned by root or you and writable by others only if sticky (`/Users/Shared` is root's and sticky, so only you or root can rename or remove your entry in it). Relay never replaces or removes it: if another user made `.rn-<uid>` first, it is not a link, or it points elsewhere (your home moved, say), relay does not start Claude jobs and names it; remove it (an administrator, for another user's) and relay makes its link again. On a long home `relay doctor` reports the link's state and the version ceiling (`claude temp`) without making the link, and its Claude init probe gets the same private temp as a turn (it is not run while the link is not usable). Grants covering the link (`/Users/Shared` and above) are refused like grants over `~/.rn`. With a uid over five digits even the short name does not fit, and relay refuses Claude jobs. Relay does not remove the link on uninstall. What can still change the link while a turn runs is anything that can write `/Users/Shared` itself or a directory above it (`/Users`, `/`). Root and your own processes outside any sandbox can, as they can change `~/.rn` itself. So can a sandbox of yours whose writable paths include one of those: a Claude Code or Codex session working there, or a relay Claude job under `child_settings: "inherit"` (which needs `claude_settings_env: "accept"`) or under managed settings relay was told to accept, whose settings list one in `sandbox.filesystem.allowWrite`, since Claude merges those into relay's sandbox. Give no sandbox write access to those directories. Confined turns' temporary homes and brokers live under `~/.relay-t`, outside shared temp and denied to Claude writes. Neither root nor an ancestor is grantable. Every backend rechecks each write grant's resolved directory, real path components and device/inode pin before launch; missing or changed pins refuse the turn. Shared temporary directories cannot be newly granted. Authority checks use the running turn's recorded grant, so a grant queued for a later turn does not widen one still running.
- **Relay-enforced confinement.** For a harness whose own sandbox relay cannot verify (Copilot, Gemini and Grok), relay runs the whole harness process, and everything it starts, under its own macOS sandbox (Seatbelt, through `sandbox-exec`), built for each turn. Where that sandbox is missing or does not enforce, relay refuses the harness; it never runs it unconfined. What it enforces:
  - Relay's bridge requires both the turn's secret and kernel peer authentication: the connecting process must have your uid and be the pinned, still-live harness or one of its live descendants. A process outside that tree is refused even if it holds the secret, including a process in Claude's or Codex's native sandbox. Relay reads the accepted socket's peer pid/uid through the system Perl, checks process start times freshly to reject reused pids, and logs refusals in the turn's log. If it cannot determine the peer, it refuses the connection. See [broker authentication](architecture.md#relay-owned-confinement) for the design and scratch regressions; this does not qualify a signed-in harness.
  - Writes go only to the job's worktree (write jobs), granted directories, the turn's private temporary directory, the subdirectories its profile names of state relay keeps for the harness between turns (Copilot: its sessions and a per-turn directory, in a Copilot home of relay's own under relay's harness directory; Grok: the same, in a Grok home of relay's own; Gemini: its runtime directory, with its sessions, in a Gemini home of relay's own) and the specific login token files its profile names. A target may also declare a login store, a directory of your home where its harness refreshes its login by writing a temp file and renaming it into place (Grok's `~/.grok`: `auth.json`, `auth.json.lock` and Grok's temp names, `.{pid}.{counter}.tmp`; the maintainer's decision of 2026-10-17, "Exact-name renames"). There its token and temp names can be written, created as regular files, removed and renamed onto, its lock names written and created but not removed, and the temp and token files' modes set: no link of any kind, no directory, no other name, nothing in a subdirectory. One thing Seatbelt cannot refuse there: an exchange of two names (`renamex_np` with `RENAME_SWAP`) can put a link or a directory at the token's name or a temp name, since a rename onto the token must be allowed and the two look the same to it. So relay checks the store both before and after every turn. Each of those names that exists must be a regular file with one name, yours, not executable, and under exactly that name (on a volume that ignores case, `AUTH.json` is what `auth.json` reaches). A bad store refuses a turn before it starts. If the check after a turn finds an unsafe name, relay immediately quarantines every offending entry and the token files by rename only, without following links, reading their targets, copying or deleting, before reporting the failed turn. It keeps the names under its control directory at `quarantine/<run>/<node>/<turn>/` (mode 0700); if the rename crosses volumes (EXDEV), it renames the entry inside the store to `.relay-quarantine.<turn>.<name>`, which Grok never reads and later checks leave alone. Relay checks both names with lstat after each move and reports any failed move loudly, with its name and cause. The result lists what moved and where; `auth.json` is then absent, so run `grok login` again before using Grok. Relay refuses further turns until the store passes its check and its login is restored. The boundary probes try all of it on a decoy store of relay's own under the same rules. The harness's home depends on its profile: a temporary one in the turn's temporary directory, so that it loads none of your configuration (Grok, which would otherwise also import Claude Code's, Cursor's and Codex's hooks, MCP servers and skills from it), or your own, readable and not writable, where its login is found through it (Copilot, whose keychain login needs it; relay links your Copilot `config.json` into its Copilot home, read-only). Never the worktree's `.git` or a granted repository's `.git`, relay's control directory, other jobs' worktrees, your home, the harness's own configuration, hooks or binary. Each granted directory is pinned when the grant is authorised; a grant from before pinning existed is refused until you grant it again. Harness and developer-tool configuration an agent could plant at the top of a writable root (`.claude`, `.codex`, `.gemini`, `.mcp.json`, `.envrc`, `.vscode`, the shell rc files, `.gitconfig` and the like) can be neither created, written nor removed, though a project's own stays readable. The `F_MAKECOMPRESSED` and `F_TRANSFEREXTENTS` fcntl commands, which would change a file through a read-only descriptor, are denied, as is any mutating `fsctl`.
  - With the network off, the only connection out is to relay's proxy for that turn, which carries HTTPS to the exact API hosts the target declares and nothing else (Copilot: `api.github.com` and `api.individual.githubcopilot.com`, as seen in a signed-in run; its telemetry is refused, and it works without it. Grok: `cli-chat-proxy.grok.com` and `auth.x.ai`, from xAI's documentation, and the only hosts it tried to reach in runs with a made-up login. Gemini: `generativelanguage.googleapis.com`, from its source, and the only host it asked for in runs with a real key; its two web tools, which reach the web through that host, are denied in such a turn, though that does not close the host as a way out: see "What it does not do"); the proxy's decisions are in the turn's log. The one exception is a harness whose profile takes the certificate-trust downgrade (Copilot): the system's trust daemons, outside the sandbox, fetch the URLs it supplies them, past the proxy (see "What it does not do"). Grok's profile takes it too: its 1.0.62 binary checks certificates with rustls-platform-verifier, which asks the Security framework (`SecTrustEvaluateWithError`), so it very likely needs them; a signed-in run will tell. Otherwise: no DNS from inside, no IP addresses, no private, loopback or link-local addresses, no address of this machine's own interfaces, no cloud-metadata endpoint, no plain HTTP, no other turn's proxy. A name that resolves to several addresses is tried in turn until one connects. With the network on, anything but loopback: Seatbelt's loopback rule covers 127.0.0.1, `::1` and lo0's link-local address, and any further address configured on lo0 (an alias added for a local service) is probed before each turn, refusing the launch if it is reachable. Unix sockets only of the turn's own (under its private temporary directory), its bridge to relay, and the system log's, plus the mDNSResponder resolver socket when network is on; no other turn's bridge, which it can neither list nor reach; no routing sockets; no listening on the network; no LaunchServices, AppleEvents or `launchctl` (which would start something outside); no signals to your other processes, and no inspection of them (their paths, the process list, their command lines or environment); Mach services only from a fixed list (directory lookups, preferences, notifications, logging), plus dnssd, mDNSResponder, configd, DNSConfiguration, networkd and nehelper resolver services when network is on; no XPC services, no pasteboard, no IOKit user client; named POSIX semaphores only under `/mp-`, the names Python's multiprocessing uses (any other program's are out of reach); and a pseudo-terminal only of the turn's own (and one relay hands it), never another session's.
  - With the network on, IPv4 to any host but this Mac's own addresses, and no IPv6 at all. Seatbelt's `localhost` matches this Mac's addresses but not their IPv4-mapped IPv6 spellings, loopback's apart: through 1.0.5, `::ffff:0.0.0.0` reached this Mac's loopback services and `::ffff:` followed by its LAN or tailnet address reached services listening there (review R1). The only rule that refuses those refuses all IPv6. Tools that try IPv6 first fall back to IPv4 at once (curl, git over HTTPS and Node's fetch, measured); a client that reaches IPv4 hosts through an IPv6 socket, with IPv4-mapped addresses (Java's default; `-Djava.net.preferIPv4Stack=true` changes it), is refused those too.
  - Only listed executables run: the system's, Homebrew's and `/usr/local`'s, the developer tools, the harness and its interpreter, relay's own Node, and whatever is in the writable directories (so that the agent can run what it builds). Because the writable directories are on that list and reads are broad, this stops an agent from running a program installed elsewhere in place (another agent's CLI in `~/.local/bin`, say), not from copying one in and running the copy; the file, network and service rules above apply to every process either way.
  - Before every turn relay runs boundary probes under exactly that turn's sandbox and refuses the launch, naming the probe, if one escapes: writes outside, into a sibling worktree, the `.git` pointer, a planted harness-config file or the control directory; a hard link or symlink out; the `F_MAKECOMPRESSED`/`F_TRANSFEREXTENTS` fcntl commands; direct and local connects (by every loopback name: 127.0.0.1, `::1`, lo0's link-local address, any further lo0 address, and 127.0.0.2 with the network off; and by every other address of this Mac's own, its IPv4 ones also in their IPv4-mapped and -compatible IPv6 spellings); DNS; a Unix socket in the worktree or another turn's broker; a routing socket; a named POSIX semaphore of a process outside the sandbox; inspecting or listing processes outside the sandbox (their paths, the process list, their command lines and environment); an unlisted Mach service, the pasteboard or an IOKit user client; a foreign sysctl write; another session's terminal; `launchctl submit`; `open`; an executable off the list. Each has a positive control (a thing that must still work: the turn's own temp-dir socket, its own process, an allowed Mach service, its own pseudo-terminal) so a probe cannot pass for the wrong reason. It also refuses a write turn whose worktree holds a file hard-linked from outside it (the sandbox decides by path, so such a link would let writes through; pnpm's store makes them).

  What it does not do:
  - **Reads are not confined**, except relay's control directory and sockets directory, the default API key directory (`~/.config/relay-keys`), and a key file `~/.config/relay/local.json` moves elsewhere: the agent can read whatever else you can.
  - **Credentials the harness can read are not protected.** That includes the harness's own login, and other tools' credential files under your home. With the network off they can still leave through the target's own API, which stays reachable by design: for relay-enforced harnesses "network off" means "the target's API hosts only". For Copilot those hosts include `api.github.com`, GitHub's whole REST API, and the proxy sees only the host name: with any token the agent holds or can read (Copilot's own login token is readable inside the sandbox through the keychain downgrade), it can also change things on GitHub, as far as that token's permissions allow, not only send data out. Grok's stored login (`~/.grok/auth.json`) is readable inside the sandbox, as any file of yours is, and its turns can write it through Grok's login store (above). For Gemini that host is `generativelanguage.googleapis.com`: any command the agent runs can reach it through the proxy, and with a Gemini API key of its own (one planted in the repository, say; relay's key is in no environment and its default directory is denied) it can have Google fetch any URL for it, through the API's URL-context and search tools, or store data under that key's project. Relay's denial of Gemini's two web tools does not stop that.
  - **It cannot keep the turn's own secrets out of the harness's environment where a protocol needs them there.** The proxy credentials travel in `HTTPS_PROXY` and the like, and one of your processes outside the sandbox can read another's environment; they are per-turn, other relay-enforced profiles cannot connect to this turn's proxy, and other loopback-capable processes need its token. The bridge to relay is handed none. Inside the sandbox the turn's own processes can read the environment each of them was started with, so a command the agent runs can read the harness's proxy credentials. Other relay-enforced profiles cannot inspect them: process-info and sysctl `kern.procargs2` permit inspecting same-sandbox processes only. Gemini's API key is therefore not in any environment: relay hands it over in Gemini's ACP sign-in request.
  - **Semaphores under `/mp-` are shared machine-wide.** So that Python's multiprocessing works, a confined process may use named POSIX semaphores whose names begin `/mp-`; another process's `/mp-` semaphore is then reachable by its name. Those names are random and there is no call that lists them; Codex's and Claude Code's own runtimes allow semaphores with no name limit at all.
  - **A harness whose profile takes a stated downgrade gets what that opens.** The keychain (Copilot's login is there; other items its tools are trusted for become readable), or the certificate-trust daemons (Copilot checks GitHub's certificates through them, and very likely Grok, whose certificate checks go through the Security framework, so that for Grok they also evaluate its API connections; they fetch from URLs their caller supplies, a way out that relay's proxy does not see), or a login store (Grok's, above: the harness may replace its token file there with any regular file it writes, and remove it, and an exchange can put a link at the token's name during the turn; as soon as the turn is over, relay quarantines unsafe entries and the token files by rename, fails the turn and requires a fresh login, reporting any failed move loudly). Grok's login check is "scrubbed": `cached_token` accepts any stored login, an expired one included, and reports no account, so relay cannot tell which login is stored. A Grok turn, a read job with the network off included, could replace it with another account's login, and later turns, and your own `grok`, would run on that one without relay or you being told.
  - **The keychain downgrade has had no adversarial test.** Relay's red-team before 1.0 ran its Claude and Codex attackers with no keychain access. Its keychain arm, which would test what an agent inside relay's sandbox can reach in a keychain (mainly through Copilot's downgrade), has not been run. The never floor's keychain-file denies for Claude and Codex are checked each release with a decoy keychain (Known limits); Copilot's keychain allowance is not.
  - **No escalation for Gemini, Copilot or Grok.** An approval request from one of them cannot widen its sandbox; relay reports what the agent needed instead of running anything outside. (Codex under stage 2 is different: it can ask for a new turn with more capabilities; see Approvals below.)
  - It does not see daemons the harness talks to that were started outside the sandbox; harnesses that run their tools in such a service are not admitted.

  `relay doctor` prints whether relay-enforced confinement is available on this machine and this summary.
- **How relay knows the confinement is in force.** For Codex, relay reads back the effective configuration and the login method before every turn and refuses to start unless they are what it set. For Claude, relay passes its own settings and loads none of yours (`child_settings`) except the deny rules in your user settings, which it copies in (they can only take something away), sets the sandbox to refuse to run rather than fall back when it cannot start, gives the agent a fixed list of tools, and stops it at start if it does not report its tools, MCP servers, permission mode and login, or reports a tool or MCP server relay did not give it, or a permission mode or login other than the one relay set. A tool may be missing from that list: a deny rule naming a whole tool (`WebFetch`, say) removes it. That is weaker than the Codex check, because Claude does not report its effective sandbox settings. Settings an organisation manages outrank relay's, so relay will not launch Claude where it finds such settings on disk (`claude_managed_settings`); it cannot see settings delivered from the claude.ai console, whose `env` could also point a launched Claude agent at another endpoint without relay seeing it (then only the model Claude reports tells which family answers). Settings files can also set environment variables for the session, after relay has checked the environment it passes, so a loaded settings file could point Claude at another endpoint; relay does not read their `env` (it may hold credentials). It therefore refuses to launch Claude when settings it does not vet would load (`child_settings: "inherit"`, or managed settings it has been told to accept) unless `claude_settings_env` is `"accept"`, in which case which family answers rests on the model Claude reports. Since 1.1.4 the never floor refuses relay's Claude jobs under either source first, whatever these two settings say.
- **Approvals.** A launched agent can ask to do one thing outside its sandbox. The decision belongs to the root: in practice the root agent following your instructions, or you from a terminal. A person-only request (one-turn environment disclosure, consent to extensions, a call of an extension server's tool, any request of a session holding MCP servers) is yours alone to allow, in the approval dialog or a permission prompt through `confirm`; through relay's tools and commands, the root agent, a launched agent and a terminal command can only deny it ([Extensions](usage.md#extensions)). That holds against a root agent talked into approving, not against one set on acting alone: relay does not confine the root session, whose own shell can reach relay's state and the credentials in `mcp.json` directly (Known limits). A Codex subagent thread (one an agent started with `spawn_agent`) has a relay server of its own, but no person in its conversation, so relay takes a denial from it and refuses an allowance, a grant, and extensions. **No command runs outside its sandbox on approval: relay declines a native Codex request to run one there, and refuses every Claude command request under the never floor. What can be allowed is a file change outside the job's writable places (made outside the sandbox, with your authority), an explicit access added inside the sandbox to one Codex command, and, with stage 2 on, a new turn with the capabilities a Codex job asked for through `escalate`** ([Approval requests](usage.md#approval-requests)). For an agent in relay's own sandbox, an approval lets it go ahead inside the sandbox and never widens the job's grant. On an unrecognised host relay cannot attribute a root allowance to a person or distinguish that host's subagents; no additional full-access approval guard is imposed. Use the terminal path when you need a direct decision.
- **Extensions.** A skill or MCP server is given to a launched Claude or Codex agent only when your config allows it for that target, the root session asks for it on the call, and you consent in a request only you can allow (see [Extensions](usage.md#extensions)). In this release only skills work: a job or thread given an MCP server is refused before consent and before its agent starts, since relay forwards an extension server's calls only through an adapter that screens their effects against the never floor, and none is qualified yet. Once one is, this applies: an extension MCP server runs outside the agent's sandbox, as your own process, and the agent reaches it only through relay, which puts every call the config does not allow outright to you. Such an agent can still read what you can, credentials included, so a session given MCP servers gets no network and no write paths outside its worktree, may not start or steer other relay agents, and every approval request from it is yours alone to allow. What an allowed call does is outside the worktree promise: the server acts with whatever it can reach.
- **Relay's own git.** Relay commits and merges on the agents' behalf, outside any sandbox, in trees an agent has written to. So its git runs no hooks (a hooks directory kept in the repository, as Husky keeps one, is the agent's to rewrite), no fsmonitor program, no signing, and nothing inside a nested repository; it refuses repositories whose content filters or merge drivers it would have to run on an agent's files (its own diffs and greps run no external diff or textconv), and it fetches no Git LFS objects (`.lfsconfig` is a file in the tree, and could name another server to send your credentials to). A worktree's `.git` file is in the agent's reach and tells git where the repository, and so its config, is: relay never goes by it. It finds each job worktree's git directory in the repository's own records and passes it to git explicitly, and runs no git at all for a job whose `.git` file no longer points there. Your own hooks therefore do not run for relay's commits and merges. Merging a job's branch brings its files into your tree: look at the diff first, as you would anyone's. Merge takes only the commit the job's result showed, so what you looked at is what is merged.
- **Which family answers.** Routing and labels are separate. A root's routing family is its registered host's family, believed only while the client name agrees (`claude-code` or `local-agent-mode-*` for Claude, `codex-mcp-client` for Codex; empty names stay compatible; desktop transport also keeps unknown names, while another known family or a multi-model harness contradicts it). A contradicting client name, such as opencode using a copied `--host claude` entry, makes the caller unknown for routing and labels. An invalid `--host` still refuses every call. Without `--host`, only a client name matching exactly one target supplies a family. Unknown callers name a target or use `default_target.unknown`; relay never guesses the only enabled target for them.

  The caller label combines every session that starts or continues the item. Mixed families and any unknown contribution make it unknown. Visible overrides lower that label without changing routing: Claude's `ANTHROPIC_BASE_URL` outside `api.anthropic.com` or a non-Claude model override; Codex's `OPENAI_BASE_URL`, or a per-call model outside OpenAI's id patterns. Desktop and SDK markers do not exempt these checks. Invisible configuration and client claims cannot be verified; relay does not inspect a root's Codex provider config. Claude model labels recognize Claude Code aliases, Vertex ids, and Anthropic Bedrock ids with one geographic prefix, optionally hyphenated (such as `jp.`, `au.`, `ca.` or `us-gov.`), and provisioned context suffixes such as `-v1:0:200k`, including ARNs that expose a Claude model id. An opaque application-inference-profile ARN does not reveal its model and stays unknown; relay does no provider lookup. Names such as `claude-qwen3-coder` are unknown, but any naming pattern can be imitated. Caller metadata is evidence for labels and correlation, never authentication.

  A launched agent's model and provider checks stay in force on every turn. On the targets judged per model (Copilot, Grok), a named model is read back exactly before its prompt, and so is a named effort on Grok (which would otherwise run an effort its model lacks as `high`). Copilot on `auto`, no model, or an unlisted model is labelled unknown. Grok with no model is labelled unknown; relay runs it on no model its list does not name (its settings for Grok allow only those, and the driver refuses another before Grok starts), so Grok has no `auto` or unlisted case. Under `allow`, a switch away from a pinned model continues with a warning, labels fold conservatively, and only a child with a listed pin routes nested calls by the latest model report; an explicit unknown report never falls back to the pin. Auto, absent and unlisted pins remain unknown callers even after listed reports, so those children must name target or use default_target.unknown. Under `auto` or no model, a model Copilot reports mid-turn is what it chose: recorded, with no warning. Under `refuse`, a switch to another family's model, or to one relay cannot name, stops the turn, and unknown models are refused. A switch within the pinned model's family continues with a note under either setting. `.github/allowed_models.txt` still refuses pinned models, while `auto` and no model are admitted under `allow`. Copilot remains experimental and gated by its boundary probes.

  A Claude launch is labelled unknown from the start when `claude_settings_env: "accept"` permits settings that preflight would otherwise refuse: inherited settings or managed settings found on disk. With isolated settings and no managed settings, that waiver does not apply. With `codex_endpoint_override: "accept"`, relay conservatively labels every Codex launch unknown from the start, even when no redirect is active; the note distinguishes that config-only uncertainty from a redirect actually found by preflight. Endpoint/provider refusals remain in force. The desktop or SDK host's endpoint variables are still removed from launched agents under login-only auth; that does not exempt the root's own label from doubt. Historical items without caller records read unknown. **Relation is per pair:** a cross-family item's answer can still draw on agents of the caller's family further down an A→B→A chain. Reviews disable reviewer delegation. A same-family or unknown review is reported as its `families.summary` says, never as a cross-family check.
- **Credentials.** By default relay removes every vendor's API keys from a launched agent's environment and refuses to run a turn that would sign in with an API key (`child_auth`). `targets.<id>.child_auth: "any"` lets one target sign in with its own key while every other vendor's is still removed. `COPILOT_GITHUB_TOKEN` is removed from every agent; `GH_TOKEN` and `GITHUB_TOKEN`, which would replace Copilot's stored login but which other tools use, from Copilot's environment only. `XAI_API_KEY` and Grok's own credential variables (`GROK_CODE_XAI_API_KEY`, `GROK_AUTH`, `GROK_DEPLOYMENT_KEY`, `GROK_ALPHA_TEST_KEY`, from the 1.0.62 binary, and `GROK_EXTRA_AUTH_KEY`, from the 1.0.45 source but not in that binary, removed as a precaution) are removed from every agent, and every other `GROK_*`, `XAI_*` and `OTEL_*` variable and `SENTRY_DSN` from Grok's, whose settings relay sets itself. Grok has no API-key mode under relay: its settings pin it to its stored login, which refuses a key from the environment, and under `login` relay also sets Grok's own `auth.disable_api_key_auth` (and `GROK_DISABLE_API_KEY_AUTH=1`), so that an API key Grok keeps in `auth.json` (it saves one there when it signs in with a key) is refused too. That 1.0.62 refuses a stored key with it set, and still accepts an account's login, is for the signed-in run. `targets.grok.child_auth: "any"` skips relay's login check and leaves that switch off (with a stored login, 1.0.62 then opens its session without one, seen with a made-up login; with none, it refuses the session: "Authentication required"). Under `login`, a target relay has no way to check the login of is not launched. The global `child_auth: "any"` remains accepted, but in 1.0 it permits only each target's own supported auth inputs, with the same foreign-vendor scrubs as the per-target form. It warns on root load and in doctor; prefer `targets.<id>.child_auth`. An own-target key must also be selected by `child_env`. A person-set target endpoint refuses launch under both `login` and `any`, before filtering: relay cannot tell which family answers there, and under `any` dropping it could send a credential to the vendor instead. Unset it and restart the root. A desktop/Agent SDK host's own Anthropic endpoint is removed instead under Claude's login policy. Grok's key-mode restrictions and Gemini's key-file-only handling still apply. Google's credential variables are always removed from Gemini's environment and from every other agent's, even under the global `child_auth: "any"`.
- **Tool tokens and environment.** The default `child_env.policy: "allowlist"` inherits only the exact runtime baseline, validated proxy variables and names explicitly selected in your config or approved for one turn. Unknown variables, including `GH_TOKEN`, `NPM_TOKEN` and `SSH_AUTH_SOCK`, are excluded by default. `child_env.pass` is standing consent and does not prompt; `grant.env` requests exact names from `child_env.request` for one turn through the same person-only dialog or `confirm` path as extensions. Root `approve` (even with `user_confirmed`), child tools and `relay approve` can deny, never allow, that disclosure. Without a qualified person path, relay refuses before launch and points you to config. A resume needs fresh consent. Network permission never releases a token, and releasing one never grants network. All tools and subprocesses in that turn can read a released value; even network-off turns have disclosure routes through model traffic, results and permitted API hosts. Nested relay launches use their own destination policy and receive no inherited one-turn consent. Explicit `legacy` restores other-variable inheritance with a warning on every root load and in doctor; mandatory scrubs still apply. See [Environment policy](configuration.md#environment-policy).
- **Credential access remains broader than environment filtering.** This policy does not isolate credential files or keychains. Launched tools can generally read user files such as `.npmrc`, cloud credentials and `.env`, use configured git credential helpers, or reach a login store/keychain where the harness permits it. Dropping a path or socket variable does not prevent rediscovery. Native MCP servers have separate credentials and run outside the agent sandbox. Redaction does not prevent reading, using or disclosing a credential.
- **What is kept.** The control directory holds, for every run, a copy of every prompt sent (`prompt-<n>.txt`), every agent's log (`agent.log`) and its worker's (`worker.log`), every final message (`final-<n>.md`), every discussion's transcript, every review's files (`reviews/<review_id>/`: each side's review, and `plan.md` for a plan given as text) and, for a turn in relay's own sandbox, its proxy's decisions (`proxy.jsonl`). Beside them are the registry, which holds the prompts as they were sent, the replies as relay returned them (cut of secrets, below), and the approval requests as the agent filed them, uncut, since the person deciding one must see, and confirm, exactly what it asks; relay's own diagnostic logs (`elicitation.log`, `notices.log`); the transfers of a run to another session that `relay adopt` authorized (`adoptions/`, each kept as `.used` once taken up); the login-store entries relay quarantined after a turn of a relay-enforced harness (`quarantine/<run>/<node>/<turn>/`, under "Relay-enforced confinement" above), which relay never removes; and the copies of the registry relay made before upgrading it (`relay.db.backup-v*`). They can contain anything an agent read. The directory is private to your user. By default relay deletes none of this: it is kept until you delete it.
  - **Secrets cut from what relay writes and returns.** Relay cuts the secrets it knows the shape of from the logs, final messages, replies, errors (an agent's stderr quoted in one is cut before it is clipped to its last lines), warnings, activity lines, the commands an agent was refused, prompts' copies, transcripts and review files it writes, replacing each with `[redacted]`. By value, wherever its text appears: the value of a variable in the root's captured environment or an agent's selected environment whose name ends in a secret's word (`…_TOKEN`, `…_SECRET`, `…PASSWORD`, `…PASSWD` or `…PASSPHRASE`, also glued to what it is for as in libpq's `PGPASSWORD`, `…_PWD` as in MySQL's `MYSQL_PWD` but not `PWD` or `OLDPWD`, or an API, access, private, secret, signing or encryption key, such as `AWS_SECRET_ACCESS_KEY`; at least 8 characters, not a path or a number), and of one whose name only may be a secret's (`…_KEY`, `…_CREDENTIAL(S)…`, `…_AUTH…`, or one of those words inside the name, such as `AWS_ACCESS_KEY_ID` or `GCM_CREDENTIAL_STORE`) only when its value looks like a token (below), so that a word such as `keychain` or a time such as an expiry is not cut from a reply; and a proxy URL's password and its Basic form. Such a value is cut in each form it takes: as it is, JSON-escaped once or twice, percent-encoded, trimmed of the whitespace around it (a value read from a file can end in a line break), and, for a value of several lines such as a PEM key, each of its lines of 16 characters or more with no space in it (not the `-----BEGIN …-----` armour), since an agent's log is cut a line at a time. By shape alone: Anthropic, OpenAI and GitHub credentials by their prefixes, and xAI keys (`xai-` followed by at least 20 alphanumeric characters, case-insensitive), based on the [official xAI Python SDK secret-scanning rule](https://github.com/xai-org/xai-sdk-python/blob/ddc27ddf06dd9799058c44def8818aa496ba1722/.gitleaks.toml#L7) (relay also cuts longer matches in full); a URL's password, however short (not a reference such as `${PASSWORD}` or `<password>`); an `Authorization` or `Proxy-Authorization` header's credentials, as a header line, a JSON key or a TOML assignment: after `Bearer`, `Basic` or `Token` when they are 8 characters or more, and after any other scheme (`ApiKey`, `Bot`) or none when they look like a token (Digest's parameters are not cut); and a token-like value given to a name that plainly names a secret, as `NAME=value` (also after another assignment, as in `--from-literal=API_TOKEN=…` or `--build-arg=NPM_TOKEN=…`), `NAME="value"` or `name = "value"` (shell, TOML, INI; with spaces around the `=` only when the value is quoted), `name: value` (YAML), or `"name": "value"` (JSON, a Python dict). Such a name is `…_TOKEN` (but not a paging token such as `next_page_token`), `…_SECRET`, `…PASSWORD`, `…PASSWD`, `…PASSPHRASE` (`PGPASSWORD` too), `…_PWD`, `…_CREDENTIAL(S)…`, `…_AUTH…`, or an API, access, private, secret, signing or encryption key, but not every `…_key`, which names ordinary data (`cache_key`, `primary_key`) as often; in camelCase as in snake_case (`accessToken`, `clientSecret`, `secretAccessKey`, npm's `_authToken`; not `maxTokens`). A token-like value is 16 characters or more with letters and digits, or 24 or more in both cases and no digit that is not an identifier (`getAccessToken`); not a URL, whose password the URL rule cuts, not a date or time, and not words joined by `_`, `-`, `.` or `/`, such as `oauth2_device_flow_v2` or `secrets/token_v2.json`. Workers hold the root's secret values for redaction only, including secrets the agent never receives. The owning root's broker supplies this separate set at worker startup and with each turn, checking the worker's uid, registry-pinned pid and process start time and ownership of the node's run. Workers keep it in memory only: never written, never put in agent or bridge environments, never returned in tool results. Until startup redaction is available, worker diagnostic writes are withheld, including housekeeping paths before the first turn. Relay also registers a value explicitly released through `child_env.pass` or person-approved `grant.env` for per-turn redaction when it is secret-like: at least 8 characters, not starting with `/`, `~` or `.`, and not all digits, regardless of its name or token shape. Short values, numbers and those paths are not registered by value; the existing shape and context rules still apply. It also registers the exact per-turn proxy token and bridge secret in that turn's redaction set, so a bare occurrence in its log, reply or error is cut too, as `[redacted: proxy token]` or `[redacted: bridge secret]`. These values stay private to that turn and remain known until its result is saved, after the proxy and broker close. It is a filter, not a guarantee: a secret in none of these shapes is kept as written, and the registry keeps prompts as they were sent and approval requests as they were filed. A prompt is sent to the agent as given, but what relay returns to the calling agent is cut the same way: `ask`'s reply, a job's `final_message`, an item's `error` and `blocked`, and the other side's turns in a discussion. So a calling agent can be shown `[redacted]`, and so can the other reviewer in a review's reconciliation, which is built from the review files. Read the records and cut what should not be public before attaching them to an issue.
  - **`log_max_mb`** (not set by default): each agent's log, `proxy.jsonl`, `worker.log`, `elicitation.log` and `notices.log` is rotated when it would grow past that many megabytes: moved to `<name>.1`, replacing an earlier one, so about twice that is kept of each, the newest part. An agent's log is checked before each line (a single line longer than the limit is still kept whole, alone in its file), `worker.log` when a worker starts, the diagnostic logs at each entry, at the `log_max_mb` your config says then (an agent's log and `worker.log` keep the one their run started with). A turn's `proxy.jsonl` keeps its run's limit too and is checked before each complete JSON decision record; rotation never splits a record. A diagnostic log relay cannot write or rotate is said once, in the `warnings` of the next result.
  - **`keep_records_days`** (not set by default): `relay clean`, and once a day a worker after its session's turns are done, forget each run in which nothing has happened for that many days: its rows in the registry (overwritten as they are deleted; the registry's file is then rebuilt and its write-ahead log emptied, so that nothing of them stays readable there, but only once no run is active, since the rebuild holds the registry's write lock throughout: until then `relay clean` says so in `records_left`, a worker in its `worker.log`, and a later clean or housekeeping that finds every run idle finishes it; should another relay process be using the registry for longer than that waits, the log cannot be emptied, and the same is said), its directory under `runs/`, its harnesses' state, and the transfers of it `relay adopt` authorized. Never a run still in use: one whose session is open, as `adopt` counts it (its owning connection's process still runs, or relay cannot tell that it does not); with a transfer `relay adopt` authorized in the last ten minutes and not yet taken up; with an item queued or running, or a discussion or review open (`relay cancel` closes one left open); with a worker, an agent process or a relay process of it still running; with an approval request waiting; with login-store entries relay quarantined (`quarantine/<run>/`: its records say how they got there; delete that directory once you have looked); or with a job whose worktree or branch is still there (merge or delete the branch first), or whose branch relay cannot look for (git fails there, or its repository is not there, as on a volume not mounted: relay cannot tell that from a repository deleted for good, so such a run is kept until you say otherwise with `relay clean --forget`, below). `relay clean` lists the runs it kept, with why. The setting in your config when the forgetting happens is what applies, not the one a run began with. The registry's backups are not touched, since going back to the relay that wrote one depends on it: `relay doctor` and `relay clean` list them, for you to delete once you will not go back.
  - **`relay clean --forget <run_id>`** (1.0): forgets a run that is kept only because a repository one of its jobs has a branch or worktree in is not there, once you know it is gone for good, whatever `keep_records_days` says. Without `--write` it only reads, settling nothing and stopping no process: it prints, as JSON, what it would remove (`relay_files`), how many of the run's rows the registry holds (`registry_rows`), what it would leave alone and why (`left_alone`), and the branches it cannot reach (`branches_not_touched`). With `--write` it removes the run's rows from the registry (overwritten and the file rebuilt, as for `keep_records_days`, the rebuild recorded before the rows go), its directory under `runs/`, its harnesses' state, the transfers of it `relay adopt` authorized, and, in relay's worktrees directory, the run's directory with its jobs' worktrees (anything never committed in them goes too) and identity files' build directories. These are moved aside in the transaction that removes the rows, each only while it, the run's directory and the worktrees directory are the directories relay looked at, and removed after it; a relay stopped in between leaves them to the next `relay clean`, which removes them, or puts them back should the registry still list the run. Nothing else: not a directory relay did not make there, nor one that is a link (each is listed in `left_alone`, for you to delete once you have looked), nor a job's worktree recorded outside relay's worktrees directory, and no link is followed. Its branches are in repositories relay cannot reach, so it does not touch them: a repository that was moved, or is on a volume not mounted, still has them (there, `git worktree prune` drops git's record of the worktrees removed; if the repository can be put back, do that instead, and `relay clean` deals with the run as with any other). It is refused, saying why and forgetting nothing, for a run it does not know; a run still in use as `keep_records_days` counts it; a run with a job whose worker has died, or an approval request no job can take up any more, until `relay tree` or `relay clean` has settled it (recording the job lost, expiring the request, and stopping agents left without a supervisor), which `--write` does first, as `relay clean` does; a run with login-store entries relay quarantined; a run any of whose repositories is there (then `relay clean` applies) or that relay cannot look at, and a run that no repository keeps; a worktrees directory that is not a plain directory of yours (a link, say); and from a launched agent's environment, as `relay cancel` is. A refusal or an unknown run exits 1, and any other spelling of `--forget` (`--forget=<run_id>`), or a flag `relay clean` does not have, is a usage error that cleans nothing.
  - **Temporary files.** Whatever the config, `relay clean` and a worker's daily housekeeping remove the temporary directories relay made itself and a crash left behind, once nothing uses them: the broker directory of a turn in relay's own sandbox, or a boundary probe's decoy of one (`~/.relay-t/s/relay-turn-*`, `~/.relay-t/s/relay-probe-*`, only while the sockets root is a plain directory of yours, not a link), from more than an hour ago, whose socket nobody listens on; a boundary probe's scratch directory (`relay-probe-*` in relay's inherited temp directory or `~/.relay-t`) from more than an hour ago; a job identity file's build directory beside a worktree, from more than ten minutes ago; and a forgotten run's directories left aside, its worktrees among them (put back instead, should the registry still list the run). In relay's worktrees directory, only while that is a plain directory of yours, not a link. Only by relay's own names, and only directories your user owns. What cannot be swept (a temporary directory that is not there, say) is listed in `relay clean`'s `temp_dirs_left` and a worker's `worker.log`, and the rest of the clean or the housekeeping is still done. A turn's private temporary directory (a native turn's six-character directory under `~/.rn`, or `relay-tmp-*` under `~/.relay-t`, with legacy shared-temp leftovers still inventoried) is also removed once its registry turn is settled (done, failed, cancelled or lost) and no recorded worker, agent, process group or relay process may still be running, with process identities checked by start time. Relay records the directory's path, device and inode before launching the harness (the real path in `~/.rn`, also for a Claude turn given it through the short link; the link itself is never swept). Running or unknown turns, links and replacement directories are left alone. A directory that cannot be matched to a turn (including one left by an older build) is left alone and reported: by `relay clean`, each in `temp_dirs_left`, and by `relay doctor`, as one warning for each directory they are in and each reason (cannot be matched, or could not be checked against the registry), with how many there are and a few of their names. Builds before 1.0 made turns' directories in the shared temporary directory without recording them, so their leftovers there are never matched; 1.0 makes none there. On macOS 27 that directory (`/var/folders/…/T`) has been seen emptied when the Mac restarts (2026-10-21); macOS documents no such cleanup, and relay does not rely on it.
  - **A full disk, or a directory that is not writable.** While the registry can still be written, a turn of a session whose directory is already there still runs and answers. A record relay could not write is named in the turn's `warnings` (`ask`'s `warning`), which say what that cost and whether the disk is full or the file or its directory not writable: the prompt's copy is then not kept, the final message is kept whole in the registry instead of in its file (a job's result then has all of it in `final_message`, and no `final_message_path`), an agent's log may be incomplete, a worker's `worker.log` that cannot be opened is said once, and a transcript that could not be written is one warning on the discussion. A turn that cannot write what its agent is launched with fails, saying why and what to do: a new session whose directory cannot be made, or a turn whose launch files (`claude-mcp.json`, `claude-settings.json`, `context.json`) cannot be written. A review whose directory or plan cannot be written is not started, and a review that cannot be saved is refused with the reason and can be handed in again; a review's files that cannot be marked with the families at its end are named in its `warnings` and keep what they held (relay writes a file it rewrites beside it first and renames it into place), and its result says the families. A worker that cannot go on says why, if the registry can still take it. `relay adopt` that cannot write its authorization says so, with what to do, and authorizes nothing. Once the registry itself cannot be written (its disk full, or the file read-only), relay can record nothing new: a turn then fails, and what it would have said may not be recorded. `relay doctor` warns when less than 1 GB is left there.
- **What is tested.** Relay's automated suite tests its own logic against stub agents, and, where an installed Codex is found, Codex's sandbox as relay configures it, without a model. The confinement itself is checked on real CLIs by the maintainer, on the maintainer's Macs: the Codex qualification behind each shipped pin (33 items), live sandbox and decoy-keychain checks of Claude and Codex, and red-team campaigns; the records in [docs/qualification](qualification) say which checks ran for each version. Not tested: your Mac (a shipped pin is the maintainer's qualification, taken on trust here), Grok signed in, the keychain arm of the red team, Gemini's live checks on 0.67.0 and 0.68.0, and the signed-in Codex cases on 0.167.2 and 0.170.0.
