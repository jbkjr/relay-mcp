# Known limits

What relay does not do, does not protect, or has not checked, in full. The [README](../README.md#known-limits) lists the
ones most people meet first; [security-model.md](security-model.md) is the model these qualify. These are stated
limits, not vulnerabilities ([SECURITY.md](../SECURITY.md)).

- **Stage 2's network for ordinary grants goes through relay's proxy, and only tools that honour proxy settings work.** With stage 2 on, a Codex job's network grant (also `child_network`, a grant kept on resume, and a one-turn capability from `escalate`) gives its commands public hosts through an HTTP(S)/SOCKS5 proxy relay runs for the turn. Direct TCP, UDP and DNS stay denied, so a tool that ignores the proxy variables fails rather than going around it. Go and Swift programs that use Apple's TLS stack (Security.framework) fail too: their certificate checks need the certificate-trust daemons, which relay keeps closed because they fetch URLs past the proxy; success with Node or OpenSSL says nothing about them.
  - The proxy checks each destination's host name, the names it resolves through, and the addresses against your `never` rules, and refuses local, private, on-link and this Mac's own addresses. It cannot see inside TLS: it cannot tell apart services behind one allowed public endpoint, or stop an allowed server from forwarding the connection elsewhere, and it does not know your network's own public address. A host your `never` rules forbid must resolve afresh, or the connection fails; an endpoint refused once stays refused until the turn ends.
  - An approved loopback port to connect to (`127.0.0.1:P`, from `escalate`) also reaches port P on this Mac's LAN and tailnet addresses; requests and results say so. Never and control-port denies still win, and such requests are refused while you have `never.hosts`.
  - With stage 2 off, Codex's own proxy in strict mode applies instead. There, macOS's certificate-trust daemons can make blind OCSP/CRL requests to addresses a certificate names, local ones included, past the proxy (measured with 1.0.5 and 1.0.6; no route to reading the responses was found). Stage 2 keeps those daemons closed. Whether Claude's network route has the same gap has not been checked. Coverage: [qualification of the escalation work](qualification/escalation-wp6.md).

- **No approval dialogs in the ChatGPT desktop app.** In its Codex side and its Work mode alike, approval requests arrive with the conversation's next relay call, not as a dialog: only the app's idle case has been checked, and relay cannot tell idle from busy there.

- **Keychain IPC for Claude and network-on Codex turns is open.** The never floor denies the keychain
  files to a floored job's commands; a command can also ask the security daemons for an item
  (`security find-generic-password`). Relay's own Seatbelt denies those daemons; the native
  sandboxes do not: Claude Code 2.1.309's profile allows `com.apple.SecurityServer` and
  `com.apple.securityd.xpc` on every turn, and Codex 0.164.0's network profile allows
  `com.apple.SecurityServer` on a turn with shell network (stage 2 off; with stage 2 on such turns
  run in relay's executor). The file denies still keep items in file-based keychains unreadable,
  since reading one needs its keychain file as well as the daemons: `gh`'s keyring token and git's
  osxkeychain credentials in the login keychain stay out of reach (measured 2026-11-04; checked
  each release by a floored decoy keychain and its control without the file deny: qualification
  item 33 for Codex, release check `claude-floor` for Claude). Not covered: what the daemons serve
  without a keychain file, such as data-protection keychain items, and a copy of a keychain file
  kept outside the denied directories. Relay accepts the open IPC and does not enforce a deny
  there.

- **Extension MCP servers are refused until their per-server never-screen
  adapter is qualified.** The production adapter catalog is currently empty. Refusal
  happens before extension consent or model launch, including servers configured with
  `allow_tools`; person consent cannot screen opaque effects. The semantic adapter
  interface remains available for qualification. Skills retain their separate consent
  flow.

- Relay steers to native subagents for one's own family, allows deliberate same-family calls by default, and labels every item. Omitted targets never pick the caller's routing family. Set `same_family: "refuse"` for strict admission.
- The Claude desktop app's `relay-desktop` entry is shared: main-window desktop chats share one process; Cowork, the Code tab's in-app bridge, remote Cowork and widgets share a second. The app sends no per-conversation metadata (Claude.app 2.42304.0 code inspection, 2026-10-17), so conversations are kept apart by a session token the model carries: a bearer key that separates honest conversations, not ones whose model has seen another's token. That models carry it reliably through long chats, compaction and app restarts has not yet been checked in the app. The Code tab's dedicated registration is separate. See [Claude desktop app and Cowork](install.md#claude-desktop-app-and-cowork) for the token, the 50-second wait cap, explicit cwd and recovery.
- The direct in-session approval prompt is offered only on surfaces qualified for unsolicited elicitation while idle and busy: interactive Claude Code from 2.1.286 (rerun at 2.1.302), and Codex CLI from 0.163.0. Codex CLI 0.162.1 and the Codex app 0.162.0 have idle evidence only. The app has not been checked showing one while busy, so relay withholds dialogs there in every state. Unknown hosts and custom Codex originators get none, under `auto` or `always`. Later versions of the same qualified surface retain its gate; status reports the effective decision and doctor describes the table. Withheld requests arrive in the next call's events, and `confirm` remains available where separately qualified.
- Codex's own confirmation of the `approve` tool, which the install asks for, has not been checked in real use. With `approvals_reviewer = "guardian_subagent"` in your Codex configuration, Codex's automatic reviewer answers that confirmation instead of you, and can approve relay's `approve` call without asking you.
- Codex CLI 0.162.1 does not take back an approval form: after a request is decided elsewhere (by the agent or from a terminal), the form stays on screen and the Codex turn waits until you answer it or press Esc. Relay sends Codex no cancellation of the form (Codex would answer it with an automatic "cancel" and stop listening for yours), keeps listening, records an answer given then without changing the decision, and tells the agent (an event in its next result) so that it can tell you. This has been checked against relay's test client modelled on Codex, not yet against a real Codex run.
- Codex's form preselects its first choice, and Enter submits it at once, so relay lists `deny` first there: a stray Enter denies rather than allows. Claude Code's dialog keeps `allow` first.
- The note given with `approve` reaches a Claude agent only with a denial: Claude Code's answer to a permission prompt has a message for a denial and none for an allow, so a note given with an allow (with `approve` or `confirm`) does not reach a Claude agent. Codex's approval answer has no place for one (it tells its agent only that the user approved or rejected), so relay adds the note to the Codex agent's running turn as a message (`turn/steer`), which has not been checked against a real Codex run. An agent in relay's own sandbox does not get it.
- Relay judges whether an answer in a Claude Code session can be yours when that session's relay server starts, from the command line, settings, installed plugin hooks and skill frontmatter named under [Approval requests](usage.md#approval-requests). It does not see a switch of permission mode during the session, settings or hooks changed after it started, or settings delivered from the claude.ai console: under those, a `confirm` or an approval dialog answer is only as much yours as the mode, setting or hook that gave it.
- What you approve acts with the access it names: a file change you allow is made outside the job's sandbox, and a capability you allow for a stage-2 turn (a listener on ephemeral ports, say, which may bind every interface) is that turn's to use. No agent can have a command approved to run outside its sandbox: relay declines those requests itself (see [Approval requests](usage.md#approval-requests)).
- **A relay-enforced harness (Copilot, Gemini, Grok) given the network has IPv4 only.** Seatbelt cannot refuse the IPv4-mapped spellings of this Mac's own addresses without refusing all IPv6, and through 1.0.5 those spellings reached this Mac's services. A tool that needs IPv6, or that reaches IPv4 hosts through an IPv6 socket (Java by default), fails; most fall back to IPv4.
- A Codex job's shell network in strict mode is the internet over HTTP(S) through Codex's network proxy. Raw TCP, ssh remotes and direct DNS do not work, and Codex stops a command outright the moment it asks the proxy for a local or private address (seen on 0.163.0 and 0.164.0: `Network access to "127.0.0.1" was blocked`), so a script that tries one does not get to its later steps. A job that needs its own server on localhost needs local mode (`grant.local_network` and your consent), which opens every service on this Mac's loopback and the local network (sshd and anything else listening) to that job, with your account's reach, and lets it listen on every interface, so devices on your LAN or tailnet can reach servers it starts. Relay's own Seatbelt around Codex, with per-port rules, is the planned replacement.
- Strict mode rests on Codex's experimental network proxy. Relay verifies it before every turn and falls back to hosted search only, but the proxy judges destinations by address range alone: an address of this Mac's own that is public (a global IPv6 address) would let commands reach this Mac's services through it, which is why relay checks the interfaces before each turn; an address that appears during a turn is not seen. Likewise relay reads exec-policy rules folders it knows Codex loads; a `network_rule` loaded from elsewhere would not be seen.
- Codex's exec-policy rules can allow a command without asking, and Codex's app server has no switch to ignore them. Relay's Codex jobs load them from the `rules` folder of relay's own Codex home (`~/.local/share/relay-codex-home/rules`; your `~/.codex/rules` is not loaded), from `/etc/codex/rules`, and from a trusted repository's committed `.codex/rules`, which a job's worktree loads too. Relay's profile denies reads of the credential stores, and while it does Codex lets no command leave its sandbox, so a rule-allowed command still runs sandboxed; relay declines a request to approve one outside it (see [Approval requests](usage.md#approval-requests)). `relay doctor` lists the rules files in relay's Codex home and `/etc/codex` (`codex rules`).
- **A Codex job with raw network (stage 2) reaches your LAN and tailnet on every port, and this Mac's loopback but the denied ports.** Relay cannot close the LAN or tailnet. Its deny matches this Mac's own addresses only (over IPv6, the denied ports at every host, so IPv6 to them fails everywhere), so a router port forward reached through NAT hairpin, a tailnet subnet router or a VM bridge can lead back to a denied service. A service started after the turn begins is reachable. Codex's app server stays outside relay's sandbox; relay switches its own local actions off and reads them back, and relies on Codex's experimental environments API (0.164.0 and later). A process the job detaches can outlive the turn, still in relay's sandbox with its network; relay looks for such processes and reports survivors, but the look is best effort. The local-mode interlock sees relay's own registry only. See [Codex raw network](configuration.md#codex-raw-network-stage-2).
- Codex's hosted web search stays on with a network grant, in every mode, hosted-only included: its results can carry prompt injection into the agent's context, and what the agent searches for leaves this Mac with the query.
- A launched Claude agent's shell commands cannot be given network access by an approval inside its sandbox: under `claude -p` (checked with Claude Code 2.1.301) the sandbox's network question is answered "user denied" at once and never reaches relay's permission tool, and no setting routes it there. Relay makes the sandbox refuse ungranted hosts outright (`sandbox.network.strictAllowlist`) and tells the agent so. Its WebFetch and WebSearch requests do reach relay. For shell network access, grant `network` when starting or resuming the job. (Approving the command to run outside the sandbox is not a way round it: under the never floor relay refuses such a request for a Claude agent.)
- **A Claude job's shell, with the network (a grant or `child_network`), reaches only addresses relay's proxy judges public; Claude's own WebFetch does too unless settings relay cannot see exempt it** (relay 1.0.5; for what this misses, see the network's own public address below, and "Outside the guarantee"). Claude Code's sandbox sends every connection its commands make (HTTP, HTTPS through CONNECT, and SOCKS5 for the rest, git over ssh included) to a proxy relay runs for the turn (`sandbox.network.httpProxyPort` and `socksProxyPort`), and relay points the Claude process itself (its WebFetch, which runs outside the sandbox, and its model traffic) at the same proxy, through `HTTPS_PROXY` with the turn's token and an empty `NO_PROXY`. The proxy resolves each name once, checks the addresses and connects to the checked one. What the job keeps: any public host on any port, public IP literals, WebFetch and WebSearch to public sites. What it loses, from the shell always, and from WebFetch unless settings relay cannot see exempt it: loopback (`localhost`, `127.0.0.0/8`, `::1`, and every other spelling of them), private ranges (`10/8`, `172.16/12`, `192.168/16`), shared address space (`100.64/10`, which Tailscale uses), unique-local IPv6 (`fc00::/7`), link-local and cloud-metadata addresses, this Mac's own addresses, and any address on the same link as one of its interfaces (LAN devices, their global IPv6 addresses included), whether named by IP or by a name that resolves to one. Local binding stays closed, and so do Unix sockets, except a list of `allowUnixSockets` in your own settings under `child_settings: "inherit"` (below). Before 1.0.5, relay used Claude Code's own proxy with every host allowed, which reached this Mac's loopback services and its LAN for the job.
  - Relay checks this as the turn runs, and stops the job otherwise: Claude Code's sandbox reports the proxy ports it uses (relay sets `SRT_DEBUG`, whose output stays in the agent log), and a report naming another port stops the job at once. At the start of Claude's first response (`--include-partial-messages`), before a tool in it can run, both ports must have been relay's, and the Claude process must have sent at least one request carrying the turn's token to the model host through relay's proxy (`api.anthropic.com`, or Bedrock's or Vertex's runtime host where `CLAUDE_CODE_USE_BEDROCK` or `CLAUDE_CODE_USE_VERTEX` picks them; another provider refuses the network grant). That catches a sandbox moved off relay's proxy, a Claude process that ignores relay's proxy variables, a `NO_PROXY` covering the model host, and a Claude Code version that changes how it reports. It does not prove that the model requests themselves, or WebFetch, went through the proxy: Claude sends other requests to the same host as it starts, and relay cannot see inside TLS. `smoke/claude-network-probe.mjs` checks all of it against a Claude Code binary without spending model usage; `--control port`, `--control noproxy` and `--control modelbypass` show the job stopped, and `--control collision` shows the case the check misses.
  - **Outside the guarantee: settings relay cannot see.** Managed settings delivered from the claude.ai console are not on disk, and relay cannot read them. Such settings can send Claude's model requests or WebFetch around the proxy while its other traffic stays on it, and the check above still passes: for example a managed `ANTHROPIC_BASE_URL` with a `NO_PROXY` for its host (which also redirects the endpoint, see the item below on settings from the console), or a `NO_PROXY` listing local ranges (say `192.168.0.0/16`), which would let WebFetch reach them from the Claude process, outside the sandbox. The shell's connections are unaffected: the sandbox sends them to the proxy whatever `NO_PROXY` says. Managed settings on disk that would do this are refused (next item).
  - Relay refuses a Claude network grant when the environment it passes to Claude carries a proxy (`HTTPS_PROXY`, `HTTP_PROXY` or `ALL_PROXY`): behind another proxy, that proxy would resolve the names relay checks. It also refuses one when managed settings on disk (`claude_managed_settings: "accept"`) set the sandbox's proxy ports, `allowLocalBinding`, `allowAllUnixSockets` or `allowUnixSockets`, or proxy variables in their `env`: managed settings outrank relay's own.
  - Under `child_settings: "inherit"`, relay's settings set `allowLocalBinding` and `allowAllUnixSockets` to false and an empty `NO_PROXY`, which outrank yours, but a list of `allowUnixSockets` in your own settings is merged into the job's sandbox, and those sockets stay reachable from it.
  - No Claude command runs outside the sandbox: under the never floor, which every Claude job carries, relay refuses a request to approve one.
- **The network's own public address is not screened** (Claude's proxy and Codex's strict-mode proxy alike). Both judge a destination by its address: not loopback, private, shared, link-local or unique-local, not one of this Mac's own addresses and, for relay's proxy, not on the same link as one of them. The public address the router shows the internet (its WAN address) passes those checks. A connection a job makes to it can come back in through the router: to a port the router forwards, to a mapping a device opened with UPnP or NAT-PMP, or to the router's own services, where the router allows hairpin NAT. So a network-granted job can reach a service on this Mac or the LAN that you have exposed through the router that way, as anything on the internet could, and the router's own WAN-side services. Relay does not know the WAN address (it is not on any interface of this Mac) and does not look it up. Not probed.
- `user_confirmed` on the `approve` tool, and a decision recorded as coming from the terminal, are statements, not proof that a person acted. The root agent is trusted to decide for its run; these exist to make "the user said so" explicit.
- Relay's check on Claude's confinement is weaker than its check on Codex's, and it cannot see Claude settings an organisation delivers from the claude.ai console, which could also redirect a launched Claude agent to another endpoint (see Security model).
- Relay's denial of harness configuration at the top of each writable root (`.claude`, `.codex`, `.gemini`, `.mcp.json` and the rest; see Security model) binds every target's write jobs, at the top of the worktree and of each granted directory: the targets it confines itself (Copilot, Grok and Gemini); Claude write jobs, for which relay sets the same names in Claude Code's own sandbox (for the shell) and permission rules (for the file tools); and Codex jobs, whose permission profile carries the same list (see Codex launch checks). It does not hold under full access (`allow_dangerous`), nor, for Claude and Codex, for a command or file change approved to run outside their sandbox (an approval the root agent can give; for the targets relay confines, an approval never lifts relay's sandbox). Copies below the top of a writable root are not denied, though each harness also loads its configuration from deeper directories. Such a file is committed with the job's work, and once merged it takes effect in your own agent when you run it in that repository. Review a write job's diff before you merge it.
- Relay keeps grants and file requests off what it runs outside every sandbox as far as it can name it when it checks a grant (when given, and on every turn that keeps it): its own installation, the Node it runs on (and the one its launcher, `bin/relay`, would pick now from `RELAY_NODE` or PATH), the git it runs, each target's CLI as found on PATH or set by `targets.<id>.bin`, with the installation holding it where relay recognises one (a Homebrew keg, an npm package, a Node distribution), and every directory on its PATH, in either direction. Relay's Seatbelt profiles, and Claude's sandbox settings, deny writing all of these, and before each launch relay refuses a turn whose own PATH finds the target's CLI in, or passes through, one of its write paths. Not covered: files a CLI or git loads from outside the installation relay recognises (git's own config, a credential helper), a Node the launcher would find only through a version manager's fallback, and directories on a PATH other than the relay process's and the turn's own (your shell's, if it differs).
- Removing a worktree discards files git ignores in it (build output, for example). Tracked and untracked work, committed or not, is not discarded.
- Git hooks, yours included, do not run for relay's commits, merges and checkouts. A repository that depends on a hook to finish a checkout or a merge needs that step run by hand.
- No mid-task messaging between running agents. `resume` delivers at turn boundaries, and a discussion advances only when the calling agent sends its next message.
- **Rooms are a bounded exchange, not a channel** ([Rooms](usage.md#rooms)). Text reaches a conversation only on its own next `room` call; nothing wakes an idle conversation, and no unattended convergence is promised. A member is bound to its relay server, so a restarted Codex or Claude Code server needs a re-seat from your terminal. Relay cannot tell whether anyone is at a Claude desktop chat or Cowork session, and the desktop apps have not been qualified for rooms. The room terminal checks are best effort against an unrestricted local shell, and a model with one could read the clipboard while it holds an invite. After an owner receives room text its `user_confirmed` counts for nothing, but that rule follows the relay owner, not text copied elsewhere or a conversation whose server restarted.
- A review whose other side is stopped by its vendor's safety system (OpenAI's cybersecurity classifier, or a Claude refusal) ends `refused`, with no independent verdict. Relay reports the refusal as such, and does not retry, rephrase, switch models or fall back to another target; your own review, if you gave one, is kept and stands alone. A review of security-sensitive code (a sandbox, an exploit, a red-team harness) is the likeliest to be stopped.
- With stage 2 on, a Codex job reaches relay's tools through a per-turn HTTP broker, which checks the TCP peer of each new connection with `lsof` (2 s per attempt, one retry). If both attempts time out, the broker answers HTTP 503, refuses every later call, and relay fails the turn with the reason: it fails closed rather than serve a peer it could not check. This has been seen once, on a machine under heavy concurrent test load; run the job again.
- **With stage 2 on, an MCP server declared in a configuration file the executor reads might reach a Codex job; this is not ruled out.** For a turn run in relay's executor, Codex asks the executor for HTTP MCP servers declared in the executor's own configuration layers (its `CODEX_HOME`, the system configuration `/etc/codex/config.toml`, and a project's `.codex/config.toml` at the turn's directory) and registers any it finds, beside relay's broker. Relay gives the executor a scratch `CODEX_HOME`, but whether the system or a repository's file is read there has not been tested. Such a server's traffic would still go through the executor, inside relay's sandbox, so it is not a way out of the sandbox; but its tools could reach the agent without relay having admitted them, and it has not been shown that relay's check of a stage-2 turn's tools would catch them. Avoid `url` MCP servers in `/etc/codex/config.toml` and in the `.codex/config.toml` of repositories you run stage-2 jobs in.

- A person-only request (one-turn environment disclosure, consent to extensions, a call of an extension server's tool, any request of a session holding MCP servers) can be allowed only in relay's approval dialog, where the host is known to show it to you, or through `confirm`. A root session with neither cannot give extensions, and one whose dialog you closed without answering (relay asks each request once) leaves the request to `confirm` where there is one, or to a denial: deny it, and the agent can ask again in a later turn.
- Person-only consent is enforced on relay's tools and commands: the root agent's `approve`, a launched agent's tools and `relay approve` cannot allow such a request. Relay does not confine the root session, so a root agent whose own shell is unconfined could act outside that (write relay's registry, or use the credentials in `mcp.json` itself). It guards against a root agent being talked into approving, not against one acting on its own; as with `user_confirmed` above, the root session is trusted.
- Launched agents can read what you can, but not `mcp.json`: it is among relay's config files, which every agent's sandbox denies by each of the file's names. A Codex write job run without a sandbox (`allow_dangerous` with stage 2 off) can read it, and any job other than one holding MCP servers can be granted the network, so such a job could use what `mcp.json` holds past relay's gate. Prefer server commands that fetch their secrets (from the keychain, say) over literal values in `env`.
- Extension gateway mediation is checked against stub agents and a stand-in MCP server, not yet in signed-in Claude or Codex model turns. Native skill discovery/loading controls have been exercised under scratch homes without model calls (Claude Code 2.1.302 init reports, Codex 0.163.0 `skills/extraRoots/set` and `skills/list`), with selected reply fields replayed as fixtures; this does not establish long-wait gated-tool behaviour.
- Claude's and Codex's own built-in subagents work inside a launched agent without going through relay, so they are not counted against relay's depth or concurrency.
- `codex app-server` is labelled experimental by OpenAI. If a Codex update changes its protocol, set `codex_backend: "exec"`; if the effective-configuration query itself breaks, relay refuses to launch Codex rather than launch it unchecked.
- When a turn ends, relay kills the agent's own process group and every other process it can still trace to the agent. It cannot trace all of them. macOS gives no way to follow a process that has been cut loose from its parent, so something an agent put in the background (`nohup … &`, a daemon) can outlive the turn, as it can when you run the CLI yourself. Seen with a real Claude job; Codex stops each command's processes itself. Such a process keeps the sandbox it was started in, and agents are told to stop what they start. It can go on writing to a write job's worktree after the turn, but it can no longer change what `merge` takes without your say-so: merge takes only the commit the job's result showed, and merges nothing while the worktree or branch holds more, unless the root session passes `include_changes_since_result`. Where relay knows it missed something (a process that would not die, or an agent that crashed or was gone before relay's last look), the result's `warnings` say so. No warning is not proof that nothing was left: check with `ps` if it matters.
- macOS only. Process handling relies on `ps`, and confinement on each CLI's macOS sandbox, or on relay's own Seatbelt sandbox for Copilot, Gemini and Grok.
- Copilot ships in 1.0 as an experimental target, not qualified ([signed-in qualification record, 1.0.98](qualification/copilot-1.0.98.md); the maintainer's choice, 2026-10-17). A later qualification needs only one check: that it reports a pinned model exactly, on a plan with model choice. The other, an approval request that reaches the root session, was shown signed in on 2026-10-23 (it reached the root agent's `approve`: the run had no dialog to show it to a person). The two limits below, no relay tools and the repository's own files loading, are accepted and documented. On Copilot Free it offers only `auto`. Under the default `same_family: "allow"` that runs, labelled family unknown (read, write and merge, resume and cancel all passed signed in on `auto`), and nothing reports which model answered; a plan with model choice is still needed to check that it reports the model a call names. It drops relay's tools: it takes only HTTP or SSE MCP servers from an ACP client, and relay's bridge is stdio, so a Copilot agent cannot delegate or reach relay, and relay's prompts tell it so. Its only approval requests under relay's flags are its own check of a path outside the worktree, which says the path but not whether Copilot would read or write it. Relay reads that from the tool call the request belongs to and puts the request to you (kind `path`). Allowing it lets Copilot go on, with relay's sandbox unchanged: an allowed read succeeds anywhere but relay's own directories, config and key files, and a write outside the worktree still fails. A signed-in run (2026-10-23) showed them reaching the root, an allow answered once only, and the sandbox still refusing the write; it also showed that Copilot asks once per path, that a denial ends its turn with no reply (the job ends `blocked`, naming the request), and that its shell commands raise no path check at all, so for them the sandbox alone decides. Instructions files (AGENTS.md, CLAUDE.md, `.claude/rules`) and skills in the repository (`.claude/skills`, `.github/skills`) still load, and a repository's `.claude/settings.json` can turn hooks back on; all of these run inside relay's sandbox. Its telemetry is refused with the network off, and it works without it. It needs the certificate-trust downgrade (its TLS checks go through `trustd`) and the keychain one (its login is there).
- Grok is not qualified (what relay knows of it comes from the 1.0.62 package run without a login). Unverified until a signed-in run: that its `cached_token` check succeeds with a stored login (without one, under relay's settings, it fails at once and opens no browser), which models a subscription offers and whether `-m` takes them (relay knows `grok-4.6`, `grok-4.5` and `grok-4.7`; without a login Grok offers the first two, relay refuses a listed model a session does not offer, and it runs Grok on no other), which hosts it needs, whether it needs the certificate-trust daemons, that its server-side search stays off in a turn without network access (relay sets `features.backend_tools = false` and `GROK_BACKEND_SEARCH=0` there), that relay's bridge gives the model working tools (Grok starts it and lists its tools, seen with a made-up login, although it advertises only HTTP and SSE servers), and a real refresh of its login through relay's login store. Its turns may refresh the stored login in `~/.grok` as Grok does (Grok's lock, a temp file, a rename onto `auth.json`) and change nothing else there. A turn that ends or is cancelled while Grok is refreshing can cut the refresh short: relay closes the turn's proxy tunnels at once and stops Grok soon after, so a refresh that xAI has already answered (its refresh token is single-use) may never be saved, and you then sign in again with `grok login`. The window is one exchange with `auth.x.ai` and the save; relay has not reproduced it. Relay cannot tell which login is stored there (`cached_token` reports no account, and accepts an expired login), so a turn could replace it with another account's, and later turns, and your own `grok`, would run on that one without anyone being told; if a Grok job worked on content you do not trust, sign in again with `grok login`, which stores your own. Relay runs Grok only on that login, and refuses a `GROK_AUTH_PATH` or `GROK_HOME` that keeps it elsewhere.
