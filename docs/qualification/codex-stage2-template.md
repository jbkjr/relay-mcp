# Codex CLI stage 2 qualification: template

Stage 2 runs a Codex job's commands in `codex exec-server` inside relay's own Seatbelt profile, bound to the app server's thread as its only environment ([design](../codex-confinement-design.md) §2, §7.2). Relay's tools are served by the authenticated HTTP `relay_tools` broker outside the executor ([broker design](../codex-mcp-broker-design.md) §7.2, §14). Every Codex release is qualified for it before relay's stage-2 jobs run on it. The release watcher runs the qualification as the case `stage2` of the Codex live checks (the maintainer's release watcher), and its result is the "Stage 2 qualification" section of `codex-<version>.md`. A run by hand is recorded as `codex-stage2-<version>.md`, generated by `stage2Record` in the maintainer's release watcher (not published) from the run's `stage2-verdict.json`.

## Running it by hand

On a Mac with a login session (relay's own sandbox does not launch on the maintainer's release-watcher Mac, which has none), with relay built (`npm run build`) and a short TMPDIR:

```sh
export TMPDIR=/tmp/s2q
node scripts/codex-qualify/codex-stage2.mjs "$PWD" /tmp/s2q/run <version> <path to codex> \
  --old-bin <path to codex 0.163.0> [--source <codex-rs checkout at rust-v<version>>] [--items 1,10]
```

- `<path to codex>`: the release under test. The watcher uses npm's darwin-arm64 binary (`fetchCodex` in the maintainer's release watcher (not published)).
- `--old-bin`: Codex 0.163.0 (`STAGE2_OLD_CODEX`), the last release below `STAGE2_MIN_CODEX`. Without it item 13 is "not run".
- `--source`: where to read the bundled model catalog (`codex-rs/models-manager/models.json`). Without it, the catalog is fetched from GitHub at the tag.

It needs no vendor login and spends nothing. The model is a fake Responses API on loopback, and every Codex home, relay home and HOME is a scratch directory under the run's directory. Every listener is the run's own, on a random high port, except relay's leased executor and broker ports in its reserved range (47200-47263). Direct Codex fixtures use the production HTTP front/core and deterministic tool answers; relay parts use the real tool handler. The run stops everything it started, and fails if anything is still running afterwards. It writes `<run>/stage2-verdict.json`. A full verdict contains exactly the current schema's items (`stage2-v4`: items 1–33), `relayPath: "present"`, and passed evidence for every expected part (a pin qualified earlier under `stage2-v3`, items 1–32, stays valid); selecting items is diagnostic and cannot qualify a release.

Items **23–30** are the [Release A escalation gates](escalation-wp6.md), including an
explicit public control (`RELAY_TEST_PUBLIC_NET=1`) and a fixed 3601-second MCP probe
(`RELAY_TEST_ESCALATION_LONG=1`). The current integrated omissions are pending parts.
No partial or historical 22-item receipt qualifies the enlarged gate.
Items **31–32** check standing network policy and the disclosed IPv4 localhost scope. Item **33** tries a decoy keychain item from native Codex turns, network off and on (host only, `RELAY_TEST_KEYCHAIN_LIVE=1`): floored, with its directory in `never.paths`, it must be refused on every turn; the control without that entry must match doctor's documented keychain IPC (refused off-network, retrieved on-network). Claude's side is release check `claude-floor`, which the pin does not run.
For a full qualification set both opt-ins above; `RELAY_TEST_ESCALATION_LONG=readback`
checks only item 30's timeout setting and leaves the actual long call unqualified.

Feature policy follows the validated selected executable, never a second lookup of `current`.
On 0.166.0 and later, `plugin_discovery_prefetch` and `prediction_preserve_parent_tools`
must be pinned false in config and listed false by `experimentalFeature/list`. They are absent
from 0.164.0 and are not required there. `reasoning_effort_override` may be on: it changes
effort encoding, checked by item 10's fresh/resumed effort part. This policy update is not a
qualification receipt for 0.166.0.

`deferred_tool_world_state` must be pinned false and listed false on every version. 0.164.0 and
0.166.0 list it off by default; 0.167.0 turns it on by default. It changes only the model-visible
world state (deferred tool namespaces), and relay keeps it off for parity with 0.166.0.

On 0.167.2 and later, `incremental_tools_legacy_gcp` must be pinned false and listed false. 0.167.2
adds it on by default; older versions do not list it and are not required to. Codex reads it only
for the `gcp` model provider, and relay keeps it off rather than admitting it.

On 0.170.0 and later, these must be pinned false and listed false (`STAGE2_FEATURES_OFF_0170`),
each on by default there: `code_mode_host_grpc`, `code_mode_host_output_truncation`,
`guardian_include_additional_context`, `incremental_tools_legacy`, `retain_client_tool_outputs`,
`unified_image_budget` and `untrusted_as_tool_output` ([design](../codex-confinement-design.md) §2.5).
0.170.0 changed two things the harness had relied on:
- **A goal's objective.** It now reaches the model as untrusted additional context: a
  `function_call_output` with no `call_id`, in namespace `agent`. The fake model routes a request
  on that output as well as on its messages. Without this, item 11's goal cases cannot tell.
- **Discovery prefetch.** `plugin_discovery_prefetch` is removed. From 0.170.0, item 12's positive
  control must instead see the authenticated startup requests that remain with plugins on:
  `/backend-api/ps/plugins/installed` and `/backend-api/ps/plugins/suggested/codex`
  (`PLUGIN_STARTUP_DISCOVERY_PATHS`). Its negatives are unchanged: any `plugins` path still fails
  them. Since 0.170.0 they also count any request to the plugin service (`/backend-api/ps/`), which
  catches its MCP endpoint (`ps/mcp`, seen with plugins on).

Item 12's discovery control is feasible without a vendor account. At `rust-v0.166.0`, the
[upstream startup test](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/tests/suite/v2/plugin_list.rs#L1964-L2042)
uses a scratch ChatGPT login and `chatgpt_base_url` pointing to a local mock. Its
[auth fixture](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/app-server/tests/common/auth_fixtures.rs#L142-L217)
writes synthetic tokens to the file credential store; no real authentication or bundle download
is needed for an empty catalog. The [startup manager](https://github.com/openai/codex/blob/rust-v0.166.0/codex-rs/core-plugins/src/manager.rs#L2884-L3023)
gates discovery on `plugins` and `plugin_discovery_prefetch`; `remote_plugin=true` additionally
enables the remote catalog and recommendations. Item 12 uses that setup in `i12-prefetch-on`,
and the same local service and synthetic credential in `i12-plugins-off` and
`i12-plugins-only`. Each has a fresh scratch home and the same 9.5-second observation window.
The positive control must receive authenticated GETs for `/backend-api/ps/plugins/list`,
`/backend-api/plugins/featured` and `/backend-api/ps/plugins/suggested/codex`; installed-plugin
sync and GitHub traffic do not count. A missing endpoint fails the `prefetch` part with
"the prefetch check cannot tell". Older versions record that this part is unsupported.

To exercise these cases on the host (after building, in a Mac login session):

```sh
TMPDIR=/tmp/s2q node scripts/codex-qualify/codex-stage2.mjs "$PWD" /tmp/s2q/item12-0.166.0 \
  0.166.0 /absolute/path/to/codex --items 12
```

## How an item is judged

Each item has up to three kinds of part:
- **codex:** this release run directly. An executor the run starts under relay's stage-2 profile (built by relay's own `seatbeltLaunch`), and an app server with relay's own stage-2 flags (`codexFlags` with `stage2Plan`).
- **control:** the same calls where they must escape (no environment, no turn binding, plugins on). A control that does not escape fails the item, because the check could then not tell.
- **relay:** the same through relay's own path, `codexBackend.start` with stage 2 switched on (`targets.codex.stage2`) and `grant.raw_network`. It reports "pending integration" in a build without WP-C, and "not run" where relay's own sandbox cannot launch (no login session).

An item passes only when every one of its parts passed. The run passes only when every item passed; "pending integration" and "not run" are never a pass.

Item 22 uses scratch copies of the bundled catalog to select direct/v1 and code-mode/v2
explicitly (the B5 probe shape), even if the release's catalog defaults entirely to v2. Item 10
always uses the unmodified catalog. All broker cases use the canonical
`agents.max_concurrent_threads_per_session = 6` pin. A changed session count is a failed
qualification to investigate, not a reason to raise the cap automatically.

The exact live peaks in the design's B5 table came from a stand-in that observed eager DELETE of
the threadless readback session. That retirement timing is not a broker safety requirement:
the design explicitly reserves the eighth slot for readback overlap. Item 22 therefore requires
exact totals (eight sessions/seven successful tool calls, then three/two on resume), a successful
reply for each named parent/child, and a bounded live peak: 2–3 for v1 and resume, 2–8 for v2.
It waits for the **parent thread's** completion. A child's completion cannot trigger teardown.

## What to do with a result

- **Passed:** the record goes with the version's PR; the watcher may merge it if every other check passed too.
- **Failed:** the PR is the maintainer's. Read the item's parts in `stage2-verdict.json`.
  - A codex part that failed means this release changed something stage 2 relies on.
  - A control that failed means the check can no longer tell, so the item needs revisiting before anything is concluded.
  - A relay part that failed is a relay bug.
- **Item 10 failed on a tool or a global:** the release offers the model something relay has not qualified. Read what it does before adding it to `STAGE2_TOOLS` or `ISOLATE_GLOBALS` (a change to relay's source, reviewed like any other).

## What it does not cover

- Behaviour that needs a real model: hosted `web_search` was never seen with the fake provider, and a real model may call tools in ways the scripted calls do not.
- The isolate is checked from inside: an escape from V8 itself is outside any such check (design §8, residual 8).
- Item 10 follows the bundled catalog. A model the account's own catalog adds after release (a remote catalog entry) is not seen until the next run.
- The watched source (`STAGE2_SOURCE` in the maintainer's release watcher (not published)) catches changes in the files it lists. A new path that runs something locally from a file outside them is caught only if the live items exercise it.
- **Self-started turns.** Item 11 catches a new source only if it fires on a plain resume or with an active goal under relay's flags. The static `callers` entry catches a new caller of the start-if-idle submission (any `*_if_idle` name, `continue_daemon_turn`, `submit_turn_input_with_mode`) anywhere in codex-rs but tests and the TUI. It misses:
  - a source that starts turns through another API;
  - a new condition around an existing call in a file not otherwise watched;
  - one that fires only on events the qualification does not produce (a mailbox message, a timer, daemon recovery after a crash).

  `thread/sample` (0.164.0) starts a turn on an ephemeral fork, but only at a client's request, which relay never makes.
- **The model provider.** The Codex parts use OpenAI's own provider pointed at the fake model, as production does. A tool Codex offers only to a real account (signed in with ChatGPT, say) is not seen.
