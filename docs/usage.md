# Using relay

The tools, by what they do: [Delegate](#delegate), [Consult](#consult) (`ask`), [Discuss](#discuss),
[Review](#review) and [Rooms](#rooms) (`room`), with [Speed](#speed), [Approval requests](#approval-requests),
[Extensions](#extensions) and [Watching and stopping](#watching-and-stopping). Configuration is in
[configuration.md](configuration.md), and what each of these does and does not protect in
[security-model.md](security-model.md).

Relay fills the gaps between families of agent. For more agents of its own family, an agent should use its host's native subagents. Naming its own family through relay is allowed and labelled, for when the user asks, or when the session has no subagents of its own. Leaving `target` out never picks a target registered as the caller's own family. Every item carries `families`: caller, launched, relation (`cross-family`, `same-family` or `unknown`), a summary, and a note exactly when the relation is not cross-family. `same_family: "refuse"` restores strict admission.

Vendor safety stops settle as `refused`, preserving the vendor's message and unfinished work; relay never retries, rephrases or switches models or targets automatically.
Claude refusal detection is source-derived from Claude Code 2.1.302 and is not live-qualified. An unrecognised refusal shape may keep the ordinary harness outcome, including apparent success.

## The tools

Each host session gets these MCP tools from relay (in Claude Code, `mcp__relay__<tool>`):

| Tool | What it does |
|---|---|
| `delegate` | Starts a job and returns its id at once (`background: false` waits for the result instead): `mode: "read"` runs in place, read-only; `mode: "write"` runs in its own git worktree on branch `relay/<job_id>`. |
| `status` | An item's state, or a wait for it (`wait_s`); with `notice`, verifies a notice relay posted. |
| `result` | A finished job's parsed report (summary, files changed, branch, tests run, open issues), its branch and diff summary. |
| `resume` | A follow-up message to a job in its existing session, to steer or continue it. |
| `cancel` | Cancels a job, thread, discussion or review and everything it started, or a whole run (root session only). |
| `merge` | Merges a finished write job's work into your tree: exactly the commit its result showed. |
| `ask` | Puts a question to another agent and waits for the answer; `thread_id` follows up in the same thread. |
| `discuss` | A turn-by-turn discussion in which the calling agent is one side. |
| `review` | An independent review from another agent, set against the caller's own, then reconciled. |
| `brief` | The prompting brief for writing a task or question for another family's agent, written by that family. Starts no agent. |
| `approve` | Decides a launched agent's approval request. Not offered to launched agents. |
| `confirm` | Proposes allowing a request through the host's own permission prompt, so that you decide. Offered only to a root session on a host relay has identified as prompting for it (see [Approval requests](#approval-requests)). |
| `adopt` | Takes over an orphaned run into this connection, with your authorization ([Run access and recovery](install.md#run-access-and-recovery-in-10)). |
| `room` | Joins, reads and sends in a room that links this conversation with another existing one, or asks you to open one (see [Rooms](#rooms)). Root sessions only; starts no agent. |

A Codex agent relay launches with stage 2 on (see [Codex raw network](configuration.md#codex-raw-network-stage-2)) also has `escalate`, which asks for capabilities for its next turn and runs nothing itself.

You can start any of these with a slash command, or just ask the agent in plain language; the tools are the same either way. The examples are from a Claude session, where the other agent is Codex. From a Codex session it is Claude. `target` can be left out everywhere: relay never picks your own family when it is omitted. With the default `same_family: "allow"`, explicitly naming your own family is admitted and labelled; `same_family: "refuse"` refuses it.

## Delegate

```
/relay:delegate write Add input validation to src/api/upload.ts and cover it with tests
```

The agent calls:

```json
delegate({ "mode": "write", "task": "Add input validation to …" })
→ { "job_id": "j_7cfab338", "target": "codex", "branch": "relay/j_7cfab338", "status": "queued" }
```

Then `status({ id, wait_s })` to wait, `resume({ job_id, message })` to steer or continue, `result({ job_id })` for the parsed report (summary, files changed, branch, tests run, open issues) and diff summary, and `merge({ job_id })` to bring the work that summary shows into the current tree.

`delegate`, `ask`, and the calls that start a discussion or a review take an optional `request_id`. A call repeated with the same `request_id` (say after the host gave up waiting for the answer) returns what the first call started, and waits for it as the first would have, rather than starting it again; a `request_id` reused for a different call is refused. Request ids are matched per caller: a launched agent's are its own, and a root session's belong to its relay server, so a server that was restarted does not recognize the ids of its predecessor. On a shared relay (the Claude desktop app's `relay-desktop`) they belong to the conversation's session token instead: two conversations' ids never meet, and they survive a restart.

`status` and `result` also give the session's token usage as its harness reports it (`usage`: Claude's tokens and cost added up over the job's turns; Codex's running total for its thread), and, once an item has finished, `resume_natively`: the command that opens its session in your own CLI (`cd <dir> && claude --resume <id>`). That session then runs outside the confinement relay gave it: Claude's with your own settings and permissions, Copilot's on the Copilot home relay keeps for the item (relay's settings file there, and your own `config.json` through a link). A write job's session works in its worktree; the note says whether that still exists (it is removed after a merge or `relay clean`; relay's `resume` puts it back). For Codex, Grok and Gemini there is no command, only a note saying why. Relay runs Codex with its own Codex home and pinned Codex and archives the thread after each turn, so `codex resume` with your own Codex does not find the thread, and in relay's Codex home it would run unconfined on relay's login. For Grok and Gemini a native resume would restore session files their confined turns could write, outside relay's sandbox and with relay's settings rather than yours. Gemini would also believe it is sandboxed when it is not ([docs/gemini.md](gemini.md) §3.5). Continue these sessions with relay's `resume`, which keeps them confined.

`delegate` returns at once. To hear when a job finishes, the agent calls `status({ id, wait_s })` with a long wait. In an interactive Claude Code session in a terminal (2.1.212 or later) that wait may last up to six hours: Claude Code moves the call to the background after two minutes, the agent carries on, and the completion starts a turn on its own even when the session is idle. Everywhere else (the Claude desktop app, `claude -p`, Codex) relay ends a wait after `block_s` (under the desktop app's own entry, after 50 seconds at most: see "Claude desktop app and Cowork" in [install.md](install.md#claude-desktop-app-and-cowork)) and the agent calls again; a `status` result whose wait relay ended short of the `wait_s` asked for says so (`wait_ended`). Under `claude -p` with `CLAUDE_AUTO_BACKGROUND_TASKS=1`, relay caps the whole call’s waits at 110 seconds, below Claude Code’s default 120-second auto-background threshold, so the result returns before the turn can end and discard its background task. A custom `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` changes that cap with the same safety margin; `0` or `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` disables this cap. Detection uses the environment inherited by relay; restart the server after changing it. Interactive terminal sessions retain their long waits. These variables and the non-interactive exception are documented in [Claude Code’s environment reference](https://code.claude.com/docs/en/env-vars) and [MCP backgrounding guide](https://code.claude.com/docs/en/mcp#automatic-backgrounding-of-long-tool-calls). For the Claude agents it launches, relay removes `CLAUDE_AUTO_BACKGROUND_TASKS` from their environment, and its own settings for them turn MCP auto-backgrounding off (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` set to `0`, as Claude Code documents it; not yet checked in a run), so a settings file's `env` that sets the variable does not bring it back; only organisation-managed settings, which outrank relay's, could. `status` and `result` are marked read-only, so both hosts run several waits in parallel. While a call waits, its progress line says what the launched agent is doing (its current command, tool or file, and since when), which turn it is on, and any approval request it is waiting on. Cancelling a waiting call (Esc, or stopping a background task) only stops the waiting; the job goes on.

Relay also tells the session about events in its run that no call is waiting on: one of its jobs or threads finished, its review's reviewer finished, its discussion has a reply, or an approval request needs it (one not shown to you in an approval dialog, or one you closed). Each event has an id and is delivered at least once:

- In Claude Code 2.1.286 or later (terminal or desktop Code tab, through the session's own `relay`), relay posts a notice such as `relay (event 12, tag <32 hex digits>): Sent by the local relay server, not by a Claude session or by the Codex agent (OpenAI) of job j_7cfab338. Verify first with status notice={"event_id":12,"tag":"<32 hex digits>"}. Pointer: job j_7cfab338 finished (done). Call result j_7cfab338.` Claude Code shows it as a message from another Claude session, since that is how it presents everything on its inbox; the notice's first sentence says that relay's own server sent it, and which agent it is about. It starts a turn when idle and arrives after the current tool call when busy. The inbox is a documented [Claude Code interface](https://code.claude.com/docs/en/cross-session-messaging#the-sessions-inbox-socket); relay enables notices from 2.1.286, the first version seen taking them (also seen on 2.1.299 and 2.1.302). Each event gets at most one notice, and none when a call of the session was waiting on that item. A notice is only a pointer, never authority or approval. Before acting on one, call `status({ notice: { event_id: 12, tag: "<tag copied from the notice>" } })`. This verifies only: it ignores `id` and `wait_s`, and never dispatches work. A successful `notice_verification` has `verified: true` and the real stored `event` (`event_id`, `kind`, `item`, `about`, `notice`); follow that event, not the inbox text. Ignore a notice with no tag, an unknown event or `verified: false`, and report it to the user. The notice carries no launched agent's words or approval command; read the actual request in a subsequent tool result.
- Events count as given only after the tool reply is written to the transport. Cancellation, a closed connection or a failed write keeps them pending for a later call; concurrent results or a failed acknowledgement may repeat an `event_id`. A successful write confirms transport delivery, not that the agent read it. On every host, the next relay tool result carries the events the session has not been given yet, in an `events` field, apart from those the result itself reports on. Each entry has the same `event_id` and unsigned pointer text; verification tags appear only on the inbox wire. The id identifies the same event across both channels. Codex has no way for relay to start a turn, so there this is how a background job's completion arrives: on the next relay call, or when the agent next waits.
- When a person decides a request (in an approval dialog, in the host's permission prompt through `confirm`, or with `relay approve` or `relay deny` in a terminal), the next tool result says so in an `events` entry of kind `decided`, naming the request, the asking item, what it wanted and how it was decided, so that the agent does not report that nobody approved anything. These go only into tool results, never into a notice: the person already knows. The `confirm` result itself says `decided_by`. An answer given in an approval form after the request was already decided (Codex keeps a withdrawn form open, however long after; or the answer crossed a decision made elsewhere) comes as an event of kind `late`, saying it changed nothing. A decline from a host whose declines relay does not take for the user's (Codex) is reported as the host's answer, which may or may not be the user's.
- What happens while no session of the run is open (it was closed, or its relay server restarted) is not lost: the session that next takes the run over, through explicit `adopt`, is given every event of the run it has not been given yet, those that settled meanwhile included. A job whose relay worker died counts as finished (`lost`) and is reported like any other.

Relay authenticates inbox pointers with a 128-bit truncated HMAC-SHA256 over the session, run, event id, item and stored event contents. Each server generates a separate random key held only in memory, outside the registry ownership token. Relay writes neither that key nor notice tags to its registry, agent files or diagnostic logs; durable events and verification replies have no tag. The receiving host can retain the delivered notice and verification call in its own transcript. A tag authenticates an event, not fresh delivery: repeating it can verify the same event, so deduplicate by `event_id`. After a server restart or ownership transfer an old tag fails; use ordinary `status` to recover the current state.

Notices that relay posted, or failed to post, are logged in `notices.log` in relay's state directory (event id and outcome only, without the inbox token, notice text or verification tag). Relay reads the session's inbox token only to post to that same session, never stores or forwards it, and keeps it and the socket's path out of launched agents' environments. That only stops them finding the inbox by inheritance; it is not a gate. On macOS and Linux the token is optional, and when no `crossSessionInbound` setting applies, Claude Code delivers to a session that prompts for permissions a message from any process running as you, verified or not ([own-child messages](https://code.claude.com/docs/en/cross-session-messaging#the-sessions-inbox-socket)). So a process of yours outside any sandbox, a launched agent's command allowed to run outside its sandbox included, can find the socket and post text in relay's notice format. To restrict which messages reach Claude at all, set `"crossSessionInbound": "refuse"` in Claude Code settings to drop every incoming message, including relay notices, or `"hold"` to withhold them until a later `accept` applies. `"accept"` delivers them. These controls govern delivery, not who can connect or write to the socket, and do not provide a relay-only sender allowlist. Project and local settings can impose a stricter value over other sources. You can also select the setting in `/config` under “Messages from your other sessions”; see [inbound controls](https://code.claude.com/docs/en/cross-session-messaging#control-inbound-messages) and the linked precedence rules. Relay's events still arrive with the next tool result when notices are held or refused. `relay doctor` reports the `crossSessionInbound` values and source files it can read for the current directory, including unreadable sources; it cannot establish another running session's effective setting, command-line overrides or console-managed values.

The desktop Code tab keeps inbox delivery on, including when it sets Agent SDK markers. Hosts built on the Agent SDK alone (T3 Code, for example) default inbox delivery off; set `RELAY_HOST_INBOX=off` to disable it for a host deployment, or `RELAY_HOST_INBOX=on` to enable a qualified SDK deployment. The client-name and registered-family checks still apply. Only a relay server registered for Claude Code (`--host claude`) whose client introduces itself as Claude Code posts notices: another program started from a Claude Code session inherits the inbox variables, and its notices would land in that session.

- **write** jobs run in their own git worktree on branch `relay/<job_id>`, so siblings never collide. Writes are confined to that worktree by the agent's sandbox. Relay commits the job's work when its turn ends.
- **read** jobs run in place, read-only: they can read and run commands such as the test suite, but cannot change files or git state.
- `merge` takes exactly what the job's result showed: the commit its diff summary is of (the result's `commit`), and only while the job's worktree is still at that commit with nothing else in it (or, once the worktree is gone, while its branch is still at it). Otherwise nothing is merged, and merge says why and lists the files that changed since: a process the job started may still be running there (see [Known limits](known-limits.md)), or someone edited the worktree. You can look at the changes; resume the job, whose next turn commits them and ends with a result that shows them; or, if you want them merged as they are, have your own session merge with `include_changes_since_result: true`, which commits what is in the worktree and merges the branch as it then is (if that commit cannot be made, nothing is merged and the worktree is left as it is). The same holds when relay could not commit the work when the turn ended (the result has a `checkpoint_error`) or the job has no result at all.
- A job's worktree is removed once its branch is merged, and put back automatically if the job is resumed later. A write job whose turn finishes without changing anything says so: its status and result carry `outcome: "no_changes"`, and `merge` has no changes to merge (files git ignores are not counted). It also removes its own worktree and branch, unless agents it started are still working there or something it started may still be running. A kept worktree is looked at again each time the job is reported: if it has changed since the turn ended, the outcome is dropped and a warning says so. A worktree is never removed while it holds uncommitted work, an unfinished merge, or agents still working in it.
- `relay clean` removes what is left from finished runs. It commits leftover work to the job's branch first, keeps any worktree whose work it could not commit, and deletes a `relay/*` branch only when its commits are already in your current branch. It lists everything it kept. It also removes the temporary directories relay made and a crash left behind, and, only if you set `keep_records_days`, the records of runs with no activity for that many days (see "What is kept" in [security-model.md](security-model.md)). A run kept because its repository is gone is forgotten only when you say so, with `relay clean --forget <run_id>` (same place).
- Relay's own commits, merges and checkouts run no git hooks and are not signed. For write jobs it refuses a repository that configures content filters other than Git LFS, or merge drivers, unless you set `trust_git_filters`; diff drivers and an external diff (difftastic, say) stand, since relay's own diffs do not use them. Launched agents' pnpm copies packages instead of hard-linking them (relay sets `pnpm_config_package_import_method=copy`, which pnpm reads from version 11), because relay refuses a write turn whose worktree holds files hard-linked to ones outside it. With pnpm 10 or earlier, set `package-import-method=copy` in your own pnpm config (`pnpm config set package-import-method copy`), or a job that ran `pnpm install` may have its next write turn refused by that check. If an agent creates a git repository inside its worktree, relay leaves the job's work uncommitted in the worktree and says so. If an agent changes its worktree's `.git` file, relay runs no more git for that job and says so (to put it back, delete it with `rm -r`, which does not follow a link, then run `git worktree repair <worktree>` in your repository). The reasons are under "Relay's own git" in [security-model.md](security-model.md).
- Git LFS objects are not fetched into job worktrees: relay's checkouts and merges leave LFS files as pointer files (`GIT_LFS_SKIP_SMUDGE=1`). Objects already in your repository are unaffected; after merging a job that changed LFS files, `git lfs checkout` (or `git lfs pull`) fills them in.
- Jobs run with shell network access off; a write job is also confined to its worktree. To allow more, the root session passes `grant` on `delegate` (or on `resume`, to widen a job mid-way): `{ "network": true }` works for read and write jobs, `"write_paths": ["/abs/dir"]` for write jobs. For web research, start the job with the network granted. With stage 2 off, a Codex job's granted network goes through Codex's own network proxy: the internet over HTTP(S), never this Mac's loopback, the local network or Unix sockets outside the job's own places, as far as an address shows them (see [Codex launch checks](configuration.md#codex-launch-checks), and Known limits for the network's own public address). A Codex write job that needs a server of its own on localhost can also be given `"local_network": true` (with `"network": true`), which opens this Mac's loopback and the local network to it; only you can allow that, once per job before it starts. Where stage 2 is switched on, a Codex write job can instead be given `"raw_network": true` (with `"network": true`): raw TCP, UDP, ssh and DNS inside relay's own sandbox, with the LAN and tailnet reachable; only you can allow that too (see [Codex raw network](configuration.md#codex-raw-network-stage-2)). Launched agents cannot grant, and relay's own directories can never be granted, nor relay's config files (`config.json` and `mcp.json`, a linked `config.json` by its own name or where the link leads, and any directory holding one), with extensions or without, nor the directories that decide which API key relay hands Gemini: relay's config directory (`~/.config/relay`) and the key directories, nor anything relay runs outside every sandbox: relay's own installation (the checkout whose `dist/` is running), the Node it runs on, the git it runs, and each target's CLI (`codex`, `claude` and the others: the name relay starts, the file it leads to, and the Homebrew keg, npm package or Node distribution holding it), or a directory holding any of them, nor a directory on relay's PATH (or one holding it, or one inside it), where a program a job put would be found first; relay's sandboxes deny writing all of them too. Relay itself runs every program by an absolute path: macOS's own tools from the system volume, git and the target CLIs as found on PATH. A Codex job is not given a directory whose name holds a double quote, a tab or a line break: Codex 0.164.0 cannot build its sandbox with such a directory writable (with a double quote, none of its commands would run; with the others, a granted or git directory stays unwritable without a word), so relay refuses the grant, and a turn whose own directory or git directories are so named, saying why. Other control characters in a name are fine.
- If a job hits its sandbox mid-task, it can ask for approval for that one action instead of failing (see "Approval requests" below).
- `resume` on a job that is mid-turn queues the message for delivery when the turn ends. To redirect a job at once, `cancel` it and then `resume` it: the job continues in the same session with your new message.
- If the first launch failed before a CLI session was recorded, the next turn includes the original prompt and preamble followed by the follow-up messages. This also applies to consult threads.

What a launched agent may do with these tools is narrower than what your own session may do:

- It can start work of its own within the depth limit. Leaving `target` out never picks its own family; explicitly naming its own family is admitted and labelled under the default `same_family: "allow"`, and refused under `same_family: "refuse"`. From a read-only turn it can start only read-only work.
- It can resume, cancel, merge, continue or bring into a discussion only work that it started, directly or through agents it started, and nothing that has been given more access than its own turn has.
- It cannot cancel a run, set `cwd`, give grants or extensions, merge with `include_changes_since_result`, raise speed (the work it starts runs at its own speed or slower; see "Speed"), or decide approval requests.
- Its relay connection stops working when its turn ends.

## Consult

```
/relay:ask Is the retry loop in src/net/client.ts safe if the server returns 429 with no Retry-After?
```

```json
ask({ "message": "…", "context": ["src/net/client.ts"] })
→ { "reply": "…", "thread_id": "t_c0bbe50e" }

ask({ "thread_id": "t_c0bbe50e", "message": "What would you change?" })
```

The consulted agent is read-only and cannot delegate unless the caller passes `allow_delegation: true`. If answering needs the web, pass `grant: { "network": true }`. Without it, a consulted Claude agent can still ask to use its web tools (WebFetch, WebSearch), but its shell commands get no network, and relay declines a request to run a command outside the sandbox to get it (with stage 2 on, a Codex agent can instead ask for a new turn with the network; see "Approval requests"). `model` and `effort` choose the other agent's model and reasoning effort, here and on `delegate`, `discuss` and `review`; `speed` asks for a faster one (see "Speed").

## Discuss

```
/relay:discuss Should the TTL cache evict lazily on access or with a sweep timer?
```

The calling agent is one side. It opens with its own position, and relay brings back the other agent's reply:

```json
discuss({ "topic": "…", "message": "Lazy eviction, because …\nCONTINUE", "context": ["src/cache.js"] })
→ { "discussion_id": "d_138a70e8", "with": "codex", "reply": "…\nCONTINUE", "marker": "CONTINUE", "turns": 2 }

discuss({ "discussion_id": "d_138a70e8", "message": "…\nAGREE: lazy eviction on get and has" })
→ { "outcome": "agree", "conclusion": "…", "closed_by": "codex", "transcript_path": "…" }
```

Every message ends with `CONTINUE`, `AGREE: <the conclusion>` or `CRUX: <what cannot be agreed>`, on its own line as the message's last line. Failing that, relay reads a marker at the end of the last line only where that is unambiguous; a caller's message with no marker it can read is taken as `CONTINUE`. When relay does either with the caller's message, the result's `marker_note` says so. Two AGREEs in a row end it agreed. When the caller writes CRUX the other answers once and it ends with `{ "outcome": "no_agreement", "cruxes": { "claude": "…", "codex": "…" }, "final_positions": { … } }` (each side's last marker as written, so an `AGREE: …` given in answer to a CRUX keeps its conclusion); so does reaching `max_turns` (messages across both sides), but only if the caller set one: by default a discussion, and a review's reconciliation, has no length limit.

- `with: "<job or thread id>"` holds the discussion with an existing session of the other agent, so that it keeps what it knows. Discussion turns are read-only even on a write job's session.
- `role` sets the other agent's role: `critic` (the default), `proposer`, `peer` (the default with an existing session), or free text.
- Relay passes each message verbatim and keeps the transcript. `relay chat <discussion_id>` shows it in your terminal; type a line to add a message of your own. The other agent sees it on its next turn and the calling agent on its next call, marked as coming from you.
- A discussion does not run by itself. It advances when the calling agent sends its next message.

## Review

```
/relay:review src/cache.js --focus "expiry handling"
/relay:review --plan docs/cache-plan.md
```

Two reviews of the same target, intended to be written separately: the calling agent's own, and one from the other family. Withholding is a safeguard for normal use, not a guarantee of independence. The target is code (a path, a diff range, a branch) or a plan for work not yet done.

1. `review({ target | plan, focus })` starts the other reviewer and returns at once. The reviewer's instructions are built only from the target or the plan (its path, or its full text) and the focus. The focus and a plan's text reach the reviewer word for word, so neither should carry the caller's opinion of the work.
2. The calling agent writes its own review, itself or with its own subagents, and hands it in with `review({ review_id, own_review })`. Relay accepts and saves it only after the reviewer's job has settled. If the reviewer is still working, the call waits up to `block_s` under the host's tool timeout cap, with the same progress and cancellation as a status wait. If that wait ends first, relay accepts and stores nothing: keep the review in context, call `status` on the reviewer with `wait_s` until it settles, then resend `review_id` and `own_review`. Until the caller's review is saved (or explicitly skipped), relay keeps the other review and its log and transcript paths out of its replies, across server restarts and connections too. Until the review has ended, its reviewer is reached only through the review: resuming it, or bringing it into another discussion, is refused, so that nothing reaches its session ahead of the review or the reconciliation.
3. Relay returns the other review and opens a reconciliation with the reviewer's own session, which the calling agent carries on with `discuss`.
4. `result({ job_id: "<review_id>" })` gives the verdict and the consensus list: each item with severity, confidence, location, who raised it, and status (`agreed`, `dropped`, `unresolved`), plus each side's own verdict and coverage (`sides`) and its closing verdict and coverage (`closing`), any remaining cruxes, and the paths to both reviews and the transcript.

Relay writes neither the caller's review files nor the reconciliation's opening until the reviewer has settled. It replaces only the `own_review` argument of an identified relay `review` tool call with `[own_review: N chars, withheld]` in launched agents' logs, structured reply echoes and diagnostic errors. This covers the Claude, Codex and ACP call envelopes, including JSON-encoded arguments and debug-quoted JSON. Ordinary prose, code examples and unrelated fields stay intact; free-form echoes and unrecognised fragments can still hold the review. Prefixed diagnostic scans stop after 4,194,304 character inspections per line, leaving any unrecognised remainder unchanged. The caller's host still records the `own_review` tool call in its own transcript (Claude Code: `$CLAUDE_CONFIG_DIR/projects/<slug>/<session>.jsonl`, default `~/.claude`; Codex: `$CODEX_HOME/sessions/.../rollout-*.jsonl`, default `~/.codex`), and drafts may hold the same text. A read-only reviewer could read unprotected copies. Likewise, a caller can open the reviewer's files directly. Neither direction is a guarantee of independent judgment.

For sandboxed Claude review turns, with either isolated or inherited settings, relay adds `permissions.deny` Read rules and `sandbox.filesystem.denyRead` entries for the caller's host-state directory: `$CODEX_HOME` (default `~/.codex`) for a Codex caller, or `$CLAUDE_CONFIG_DIR` (default `~/.claude`) for a Claude caller. For an unknown caller, relay uses a contradicted registration's host home when present, or both Codex and Claude homes otherwise. When a candidate home differs from the reviewer's own Claude config directory, relay denies the whole directory. When they share it, relay instead denies `projects/**/*.jsonl*` (including subagent and superseded transcripts), `projects/**/sessions-index.json`, `history.jsonl`, `debug/`, `paste-cache/`, `feedback-bundles/`, `feedback/drafts/` and `usage-data/`. This leaves the reviewer's tool-results files, shell snapshots, skills, plugins and memory readable. The [Claude application-data reference](https://code.claude.com/docs/en/claude-directory#application-data) describes these stores; same-home copies in tool results, memory, tasks, drafts or other unlisted paths remain readable. Codex's installed relay registration and launched-child configuration pass `CODEX_HOME` through its filtered MCP environment; reinstall relay's Codex registration after upgrading to get that passthrough. The [Claude Code sandbox docs](https://code.claude.com/docs/en/sandboxing#configure-sandboxing) and [Read permission rules](https://code.claude.com/docs/en/permissions#read-and-edit) describe these separate layers: file tools follow permission rules, while Bash subprocesses follow sandbox filesystem rules. The Claude host itself reads its configuration outside these tool restrictions. These denies apply only to the independent review turn; copies outside the denied paths and drafts remain outside them. A Codex reviewer, same-family or otherwise, gets no read denies because Codex's read-only sandbox has no read carve-out; it can still read the caller's transcripts and drafts.

The whole-home deny covers Codex's `logs_2.sqlite`, `state_5.sqlite` and `history.jsonl` when stored under that home. Codex `rust-v0.162.1` separates [diagnostic logging](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/state/src/log_db.rs), [state and thread history](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/state/src/runtime.rs), and [message history](https://github.com/openai/codex/blob/rust-v0.162.1/codex-rs/message-history/src/lib.rs). Which files retain `own_review` tool arguments at default settings remains unverified; denying the directory covers them without relying on that distinction.

**Both closing blocks settle the list.** The consensus list is a join of the two sides' closing blocks on item id, whether or not the reconciliation ended in agreement, so the side that closes it cannot settle the list alone. An item is `agreed` or `dropped` only where both blocks give it that status and the same severity (an entry without a severity holds the one its items have in the reviews). Anything else, a missing or malformed status included, is `unresolved`, with each block's position under `positions`: its status (`not stated` if it gave none), its severity where it gave one, and its ids where it merged the item differently. A merge both blocks make stands. An entry's summary, location, fix and other fields replace the original item's only where both blocks give the same value; where they rate confidence differently, both ratings are kept.

`skip_own: true` in step 2 returns the other review unreconciled, with its verdict as the review's. If the other reviewer fails, nothing is reconciled and the review's verdict is `unknown`: the caller's own review is kept under `sides` but never stands as the verdict, and the review ends as failed unless the caller's own review raised items.

**Plan review.** Pass `plan` instead of `target`: the path of the plan's file, or the plan's full text. One line naming an existing file (relative to the working directory) is a file; a single word that names no file is refused, so that a mistyped path is not reviewed as a one-word plan; anything else is the plan's text. For a launched agent only a file inside its own working directory counts, and relay does not look outside it, so the reply never says whether a file elsewhere exists. The reviewer is told the plan is work not yet done, so it does not report the code the plan proposes as missing, and judges whether the plan would work against the code it builds on. A plan file is passed to the reviewer by path and relay does not read it; a plan given as text goes into the reviewer's instructions and is kept as `plan.md` with the review. Withholding and reconciliation are as for code.

**What each review says.** Both reviews end with the same JSON block: numbered items, each with `severity` (blocker, major, minor, nit), `confidence` (high, medium, low), `file` and `lines` (an inclusive `[start, end]`) where the item has them, `location` for anything else (a symbol, a step of a plan), `summary`, `evidence` and `fix`; a `verdict` (`pass`, `fail` or `unknown`); and `coverage`, what the reviewer examined and did not (`complete`, `examined`, `not_examined`). The reconciliation's closing block carries a verdict and coverage for the two reviews together. An item's id is its side's prefix and its `n` (`C1`, `X2`). An item whose `n` is missing, not a positive whole number, or used before gets the next number above every `n` given, so that no two items share an id; the side's `note` names each such item, and so do the review's file, the reconciliation's opening for the reviewer and `ids_note` for the caller. An entry of `items` that is not an object is left out, and the note says so.

**A pass over partial coverage is unknown.** Relay applies one rule, mechanically, to each review's verdict and to the reconciled one: a `pass` stands only if its coverage is declared `complete: true` with nothing listed as not examined; otherwise it is recorded as `unknown` (with a note, and the declared verdict kept beside it). A missing coverage statement is not complete. Relay goes by what the reviewer declared and never judges coverage itself. `fail` and `unknown` stand as given; anything else is no verdict, and a review or closing block with no verdict is recorded as `not stated`. The review's verdict is the one both sides' closing blocks reach, whether or not they agreed on the list (so `not stated` when neither declares one); otherwise it is `unresolved`, with each side's position under `verdict_positions` (`not stated` for a side that declared no verdict). One side's block never settles it alone, so the side that closes the reconciliation (often the caller, whose work is under review) cannot set it. Each side's closing verdict and coverage, as declared and as they stand, are kept in the result under `closing`. One more rule, also over declarations only, applies to a closing block: anything both independent reviews declared not examined was examined by neither, so the block's pass stands only if its coverage lists that under `examined` (in the same words, ignoring case); otherwise it is `unknown`. Two partial reviews that covered different things can still pass together.

## Rooms

A room lets two of your existing root conversations compare recommendations, exchange facts, and
reach agreement or state a crux. Both must use relay on the same machine and relay home. Same-family
pairs are allowed. Relay launches nobody: each conversation keeps its own files, tools, runs and
permissions, and joining grants no access to the other's work.

1. In **your own terminal**, run `relay room new`. It creates a room and prints two labelled
   invitation prompts. There is no creation confirmation to type. Each invite is one-use and
   expires in ten minutes, and a room still waiting for a seat ends (`expired`) when that seat's
   invite lapses unused, so both conversations must join within those ten minutes. A room never
   lasts past 24 hours from its creation (the `expires_at` that `relay room list` shows). On macOS it then offers the prompts on
   the clipboard one at a time: press Enter to copy member-1's, paste it, press Enter to replace it
   with member-2's, paste that, and press Enter once more to clear the clipboard (type `n` to skip).
   The clipboard is cleared of the invites however the flow ends, Ctrl-C included, unless you
   copied something else meanwhile; if relay cannot confirm the clear, it says so and asks you to
   replace the clipboard yourself.
2. Paste one prompt into each intended conversation. Each calls `room` with `action:"join"` and its
   invite, carrying its existing `session_token` if the entry uses one. A ChatGPT chat without local
   relay tools cannot join.
3. The conversations read with a room cursor and take alternating sends, starting with member-1.
   Each message has stance `continue`, `agree` or `crux`. Two consecutive acknowledged agrees end in
   agreement; a crux gets one answering turn. They report the ending and stop. There are at most 24
   member sends in all.

**Or let a conversation ask.** In interactive Claude Code in a terminal or the Codex CLI, a
conversation can call `room` with `action:"open"`. Relay then asks you in that host's own dialog,
with its own text: a room passes information only, never approvals, permissions or control of work;
at most 24 messages; with one other conversation you choose. Only your explicit "open the room"
opens it; declining or closing the dialog opens nothing, and relay puts no time limit on your
answer. The conversation may add a one-line purpose, which the dialog shows as its own unverified
words. On your yes the asking conversation takes member-1, and relay puts member-2's prompt on your
clipboard (replacing what is there); the asking model never sees its invite. Paste it into the
conversation you choose within ten minutes: the room ends if that invite lapses unused. If relay cannot write the clipboard, nothing opens. A conversation can ask
again after you decline, but not while one of its questions is open or while it holds a seat in a
live room.

Where the joining conversation is also interactive Claude Code or the Codex CLI, its join asks you
"Join this room?" first, showing who holds the other seat and how the room was created; saying no
seats nothing and leaves the invite usable until it lapses. That question is asked for terminal invites too.
`relay room list` and `--print` show each room's origin (terminal, or opened by a conversation).
Nowhere else can a conversation open a room. The Codex app (ChatGPT desktop, its Work mode
included), the desktop Code tab, Claude desktop chats and Cowork, and hosts with
`ask_user: "never"` can join from a pasted invite but cannot open a room, because relay cannot tell
that a dialog there reaches you; those hosts also do not ask before a join. `claude -p`,
`codex exec`, T3 Code, OpenCode and unknown wrappers cannot use rooms at all (see **Who may join**
below). An invite is passed on only by your paste: relay refuses
one in room text and in every other relay tool's arguments. A model with an unrestricted shell could
still read the clipboard, or start another conversation itself and paste the invite there;
`relay room <id> --print` shows which host and client took each seat.

**A bounded exchange.** A message waits for the other conversation's next room call; nothing wakes
an idle conversation, and you may need to nudge either side. A wait defaults to 45 seconds (at most
50, or a shorter host or config limit; up to six hours in interactive Claude Code, where the call
moves to the background) and can return empty. A conversation may stay quiet for as long as it
works: waits are refused only once the other conversation is gone (its relay server has exited),
or, where relay cannot tell (a desktop chat), after two hours without it calling `room`; unread
text and endings are still returned. A bare call from the other side refreshes its presence but
does not wake a wait. Presence reports last calls, not whether a model is making progress.

From your terminal:

```sh
relay room list                             # inventory, without text or credentials
relay room <id> --print                      # full transcript and ending
relay room <id>                              # follow; type a line to add terminal text
relay room <id> --say "consider this fact"    # add one terminal line
relay room <id> --reseat member-1             # review both seats; type the printed confirmation
relay room <id> --close                       # review both seats; type the printed confirmation
```

**Seats and restarts.** Re-seating revokes that seat's owner and outstanding invites immediately,
pauses the room, and prints a replacement prompt; paste it into the intended conversation within
ten minutes, since the paused room ends (`expired`) if the replacement invite lapses unused. History
and the turn budget remain. A member is bound to its relay server: a restarted Codex or Claude Code
server needs a re-seat. A shared desktop chat keeps its seat while it keeps its session token and
the same relay home, key file and registry; losing the token needs a re-seat
([Claude desktop app and Cowork](install.md#claude-desktop-app-and-cowork)). The Code tab's
dedicated and shared relay entries are separate owners.

**Who may join.** Admission is checked on every room call. Codex CLI and local ChatGPT Codex roots
need valid turn metadata with `thread_source:"user"`; `turn_trigger:"exec"`, subagents, full access
(`danger-full-access`), approval policy `never` and custom or multi-model originators are refused.
CLI and desktop originators are admitted; auto-review alone is admitted. Interactive Claude Code,
the positively identified desktop Code tab, and token-scoped Claude desktop chats and Cowork are
admitted unless relay detects disqualifying evidence: launched-agent or child-session markers,
unattended or SDK operation, or bypass permission mode. Known T3 Code, OpenCode and unknown wrappers
are refused. Native Claude subagents sharing their root's server can be indistinguishable from it.
Relay **cannot tell whether anyone is at a Claude desktop chat or Cowork session**, or what it may
do unprompted; the terminal opt-in does not prove attendance.

**Room text is not your consent.** Room text comes from another conversation's model, never from
you. A terminal line is labelled as coming from a terminal, which also does not prove your
instruction. After an owner receives external room text, `user_confirmed:true` on `approve` counts
for nothing: it cannot override a pending request's `asking` or `dismissed` person-question state or
claim a confirmation audit label. Existing qualified person paths remain available, and ordinary
root judgments otherwise permitted, denials and grants keep their rules. This is not a general
approval or grant ban, and it cannot prevent lobbying or track text copied to another owner. The
rule follows the relay owner, not the conversation: after a Codex or Claude Code relay server
restarts, the same conversation is a new owner with no record of the room text it still holds. A
session's own shell can also read a transcript with `relay room <id> --print`, which records
nothing. The room terminal commands require TTY input and output and refuse known host-shell and
launched-agent evidence before writes. They are best effort: an unrestricted local shell can unset
markers, allocate a terminal or write the registry directly.

**What is kept.** Transcripts are local records, readable by launched agents under the limits in
[What confines a launched agent](security-model.md#what-confines-a-launched-agent). Membership does
not make stored text secret. Credentials relay recognizes are cut from member messages, terminal
lines and purpose lines before they are stored, as in its other records
([Secrets cut from what relay writes](security-model.md#what-relay-relies-on-what-it-checks-and-what-it-does-not-do));
text carrying an invite or a session token is refused instead. Room calls expire rooms but never delete their rows. `relay clean` and
daily housekeeping delete transcripts `keep_records_days` after a room ends; unset or null keeps
them indefinitely. Polls do not extend that period. Exposure hashes remain indefinitely; backups and
host histories are outside deletion guarantees. A registry rebuild or WAL cleanup may wait for
active room calls and waits to finish.

Rooms were checked live in a terminal on 2026-11-16, with interactive Claude Code 2.1.325 and
2.1.326 and Codex CLI 0.169.0: opening, joining, declining, closing the question and a long single
wait. The desktop apps were checked on 2026-11-20, with the Claude desktop app and ChatGPT
26.1117:
- a Claude desktop chat and a conversation on ChatGPT's Codex side joined from pasted invites and
  agreed;
- asking either to open a room was refused;
- after ChatGPT was quit mid-room, the other side was told it had gone, and a new conversation
  re-seated with `--reseat` caught up and agreed;
- a ChatGPT Work-mode chat joined and exchanged messages with a Claude desktop chat, still counted
  as present after three idle minutes, and counted as gone once ChatGPT was quit. A Work-mode room
  was not run to agreement.

ChatGPT asks before each of relay's tool calls in a Work-mode chat unless you allow it always.
No unattended convergence is promised.

## Speed

`delegate`, `ask`, `discuss`, `review` and `resume` take `speed`: `standard` (the default), `fast`, or `ultrafast`. A faster speed costs you money or allowance, so the tool texts tell agents to pass one only when you ask for it.

- **Claude** has `fast`: Claude Code's [fast mode](https://code.claude.com/docs/en/fast-mode), for Opus 5.5, Opus 5 and Opus 4.8 only (relay refuses a model it can tell has none, such as `sonnet` or `claude-opus-4-7`). Fast mode is billed to usage credits on every plan ($8 and $40 per million input and output tokens on Opus 5.5, as of 2026-10-16), has its own rate limits, and re-bills a session's context uncached the first time it is used. Relay turns it on with `fastMode` in the settings file it passes Claude, and off on every other turn. Whether the account can use it (usage credits on, no cooldown after a rate limit) only Claude can tell, once it runs: a fast turn that ran at standard speed is reported in the result's warnings (a consult's `warning`) with Claude's reason, such as `extra_usage_disabled`, or the notice Claude gives instead when usage credits run out or a spend cap is reached mid-session (its result then still says fast mode is on) (a write job that changed nothing is still cleaned up: the warning is about cost, not about anything left running).
- **Codex** has `fast` and `ultrafast`: the service tiers `priority` and `ultrafast` in your account's model catalog. Fast uses the plan's included allowance 2.5 times as fast (credits 2 times), ultrafast 8 times (credits 6 times), as of 2026-10-16 ([pricing](https://learn.chatgpt.com/docs/pricing), [speed](https://learn.chatgpt.com/docs/agent-configuration/speed)). Before each turn relay reads the account's catalog from Codex and refuses a speed it does not offer for the model that would run, before anything starts, saying why (ultrafast, for one, is offered on Pro $500 and eligible Enterprise and Edu plans, for GPT-6 Astra and GPT-6.1 Sol). Relay goes by the catalog, never by a list of plans. A turn that carries on a thread and names no model is checked against the thread's own model, which Codex resumes it on. The thread Codex starts must then report the tier relay asked for, `default` included. Codex drops every service tier while its `fast_mode` feature is off (`[features] fast_mode = false`), so relay turns that feature on for standard turns (the tier stays `default`). Relay's Codex runs with a Codex home of its own whose `config.toml` relay writes, so your `~/.codex/config.toml` does not set it; a configuration layer relay does not write (an administrator's `/etc/codex` or managed configuration, say) can. While one turns it off, relay refuses `fast` or `ultrafast`, saying so, rather than overriding that switch.
- **Copilot**, **Gemini** and **Grok** run at standard only.

The speed behaviour was checked with Codex 0.163.0 and Claude Code 2.1.302 (field names, the `default` pin, the `fast_mode` feature, Claude's fast-mode report). Those are now relay's tested minimums. A signed-in account's catalog remains unverified.

Standard is pinned on every turn too: Codex is given the service tier `default` (a model's catalog entry can carry a faster default tier of its own) and Claude `fastMode: false`. `targets.<id>.speed` sets a root session's default for a target; relay will not load a config whose `targets.<id>.speed` the target cannot run (`fast` for Copilot, say, or for Claude with a `default_model` that has no fast mode). Only the root session raises speed: the work a launched agent starts or carries on (a job it resumes, a thread it follows up, a session it discusses with) runs at that agent's own speed or slower, so an agent you have slowed down carries on its faster work only at a speed it passes; nor can a Codex subagent thread ask for more than you set up. A call that continues a session (`resume`, `ask` with `thread_id`, `discuss` with `discussion_id` or `with`) sets the speed of the turn it queues, and the session goes on at it from that turn: turns queued before it, and the one running now (with what its agent starts meanwhile), keep theirs. One that names no speed keeps the session's; one whose message is not sent (to a discussion that has ended, say), or whose turn never starts (cancelled while queued, or dropped behind a turn that failed), changes nothing. `review` with `review_id` gives the reviewer's speed for the reconciliation's first turn, which that call or a later one opens; once the reconciliation is open, pass it to `discuss` instead. A faster speed whose turn starts but never reaches the model (one the Codex catalog does not offer) is undone, so the next call is not refused the same way; a slower one stays. A refusal names a speed to pass, and says where the speed it refused came from: the call, the session it continues, the agent's own, or `targets.<id>.speed`. `status` shows a session's speed when it is not standard (as do `discuss` and `review` replies and their status, for the other side's session, with a speed `review_id` kept for the reconciliation as `speed.next`): `speed.requested`, the speed of its turn now running or last started, since Codex does not report the tier that served a turn; `speed.next`, where a call has asked another for its queued turns; and for Claude `speed.reported`, with its result's `fast_mode_state`, `fast_mode_disabled_reason` and `speed`, and its fast-mode `notice` where it gave one.

## Approval requests

A job, consult or discussion turn that needs something its sandbox does not allow can ask. What can be allowed is narrow, and depends on the agent:

- **Claude**: a change to files its sandbox does not let it write (outside its worktree and granted directories, or, at their top, configuration your agents or tools load and git metadata), and a use of its web tools (WebFetch, WebSearch). Every request to run a command is refused without anyone being asked, under the never floor, which every Claude job carries.
- **Codex, with stage 2 off** (the default): a file change, as for Claude, and a command's request to have an explicit access added inside its sandbox for that one command. Relay switches off the Codex feature that sends the latter (`exec_permission_approvals`), so they are rare. A plain request to run a command outside its sandbox, a request for a host Codex's network proxy refused, and any request relay cannot read in full are declined by relay itself, without anyone being asked; the agent is told why.
- **Codex, with stage 2 on**: its commands and file changes run in relay's own sandbox whatever is decided, so allowing one goes ahead there and lifts none of its limits. A job that needs more calls relay's `escalate` tool to ask for a new turn with named capabilities: the network through relay's proxy, a loopback port to connect to or listen on, ephemeral ports, a directory to write, or raw network. Allowed, relay ends the turn and starts the next one with them, for that turn only.
- **Gemini, Copilot and Grok**: allowing a request lets the agent go ahead inside its sandbox, which stays as it was (see below).

A read-only turn can never ask to change files. The agent stays blocked until someone decides; time spent waiting does not count against its timeout.

- The request shows the exact command or the files, the directory it would run in, what allowing it means, the agent's stated reason, and which job it came from.
- **What allowing does.** A file change you allow is made outside the job's sandbox, with your authority: read it as you would a change someone asked you to apply. An access added to one Codex command applies to that command alone, can be allowed once only, and is declined by relay itself when it adds the network on a job without Codex's network proxy. A stage-2 capability lasts one turn, and the request says what it opens: a port-0 listener may bind every interface, so it is reachable from your LAN, and a loopback port to connect to also reaches that port on this Mac's LAN and tailnet addresses. The request's effect says which kind it is.
- A request to change a file inside relay's own directories, one of relay's config files (`config.json` and `mcp.json`, by either name of a linked one, or a directory holding one), or a file in another job's worktree, is refused without anyone being asked.
- It goes to the root session, however deep the asking agent is. Agents in between can see it but cannot decide it.
- Where the host is known to show it, relay puts the request to you in an approval dialog in the session that started the run, as soon as the request is filed, whether or not anything is waiting on the job: interactive Claude Code in a terminal (2.1.286 or later), and Codex CLI 0.163.0 or later. Both surfaces were seen showing unsolicited dialogs while idle and busy. The Codex app is withheld: it was seen showing a dialog while idle, but not yet checked while busy, and relay cannot reliably tell idle from busy. Codex CLI 0.162.1 has idle evidence only and is withheld too. Relay distinguishes the app by its observed bundled version, MCP UI capability, forwarded desktop originator or `client_type: desktop_app` call metadata; custom originators and unknown hosts are unqualified. Desktop evidence on a call withholds dialogs for the rest of that connection, even when later calls omit it. In Claude Code, Decline denies the request. A dialog closed without an answer (Esc) decides nothing: the request stays pending, the agent is told you closed it (`user_dismissed_prompt`), and it may not allow it on its own judgment; it has to ask you, and say that you confirmed, or deny it. In Codex, decline and Esc decide nothing either, because Codex declines on its own when its approval policy is `never`; the agent is told what Codex answered (`host_answered_prompt`) rather than that you closed it, and is not barred from deciding, since relay cannot tell that you saw it. Codex's form has the decision only, no note field: it could not be submitted with an optional field left empty; it lists `deny` first, because it preselects the first choice. In Claude Code, a dialog for a request decided elsewhere first (by the agent or the terminal) is withdrawn. Codex keeps it on screen, and its turn waits, until you answer it or press Esc (see Known limits); an answer given then changes nothing, and relay tells the agent so, so that it can tell you. Each request is shown once, also across a restart of the relay server.
- Hosts known to answer approval dialogs on their own are never shown one: Claude Code under `-p`, and Claude Code in the Claude desktop app or another Agent SDK host, which declines every dialog within milliseconds without showing it.
- Otherwise the request stays pending and arrives in the next relay call's `events`; `status` supplies its full `needs_approval` details. The root agent is handed the request (`needs_approval` also interrupts a wait on its run) and decides with the `approve` tool: it allows what you have clearly authorized for the task, denies what you would not want, and asks you in conversation when unsure. A request marked `person_only` (see [Extensions](#extensions)) is the exception: only you can allow it, in the approval dialog or through `confirm`, and `approve` can only deny it. Under Codex, the install sets `approve` to ask for your confirmation first; that has not been checked in real use. With `approvals_reviewer = "guardian_subagent"` in your Codex configuration, Codex's automatic reviewer answers that confirmation instead of you, and can approve relay's `approve` call without asking you.
- In interactive Claude Code in a terminal (2.1.286 or later) and in Claude Code in the Claude desktop app's Code tab (through the session's own relay, as above), the root agent also has `confirm`; relay offers it only to hosts it has positively identified as prompting for it, never on the strength of the family it was registered for. Claude Code asks you Yes/No in its own permission prompt before every `confirm` call, even in auto mode and with relay's tools allowed, so `confirm` is how the agent proposes allowing a request and leaves the decision to you: one you have not clearly authorized, one you closed without answering, or any request when relay could not show you an approval dialog (in the desktop app, which cannot show one). The agent passes the request's id, the asking agent, its kind, its effect (what allowing it does), the directory it would act in and what it wants exactly as relay showed them, which is what the prompt shows you; relay allows only a pending request of that session whose details match character for character, line breaks included, so a prompt showing one command cannot allow a request that runs two. The approval dialog shows a request, and the directory it names, with line breaks or other control characters escaped, with its line count, so that nothing is folded out of sight; invisible Unicode format characters that could make it display as something else (bidi controls such as U+202E, zero-width characters, anything of category Cf, and the line and paragraph separators) are shown as visible `\u{XXXX}` escapes. `confirm` still compares the raw text. `approve` stays the tool for denying, and for allowing what you clearly authorized.
- Neither `confirm` nor the approval dialog was checked with Claude Code able to skip its permission prompts, or with hooks that answer for you. So relay withholds both, whatever `ask_user` says, where the process that started relay was launched with `--dangerously-skip-permissions`, `--allow-dangerously-skip-permissions` or `--permission-mode bypassPermissions`, or a Claude Code settings source sets `permissions.defaultMode` to `bypassPermissions` (or a mode relay does not know). Hooks withhold only what they can answer: Elicitation or ElicitationResult hooks whose matcher can match the server name `relay` (no matcher, `*`, `relay`, or a pattern that matches it) withhold the approval dialog; PreToolUse or PermissionRequest hooks whose matcher can match `mcp__relay__confirm` withhold `confirm`. Hooks on other tools or servers (a PreToolUse hook on an email server's send tool, say) withhold nothing. Relay reads matchers as Claude Code does (exact names separated by `|` or `,`, otherwise an unanchored regular expression), and a matcher it cannot read or compile counts as matching. The settings sources are `~/.claude/settings.json` (and `settings.json` in `CLAUDE_CONFIG_DIR` when set), the project's `.claude/settings.json`, `.claude/settings.local.json` wherever Claude Code may keep it (in the starting directory, at the git repository's root, and, in a linked worktree, at the main checkout's root; any one of them withholds, and where git cannot say, the starting directory only), managed settings on disk, and a `--settings` file or inline JSON on the command line of the process that started relay. If relay cannot read the command lines of the processes that started it (`/bin/ps`), it withholds both as well. From them relay reads the default mode and the hooks' matchers only, never `env`, the hooks' commands or anything else, and a source it cannot read counts as one that skips prompts. `relay doctor` says what the settings files that apply in the current directory allow, and why. The root agent is handed the requests instead. A dialog answer that is not one of the dialog's own choices decides nothing, and how fast an answer came is never taken as a sign that a person gave it.
- You can also decide from a terminal, except that a request marked `person_only` can only be denied there (see [Extensions](#extensions)):

```sh
relay approvals                 # what is waiting
relay approve <request_id>
relay approve <request_id> --job   # for the rest of that job
relay deny <request_id> not on this machine
```

- With `desktop_notifications: true` in config (off by default; `notify`, its earlier name, is still read), a macOS desktop notification also appears when a request is filed. macOS shows it as coming from Script Editor, and clicking it only opens Script Editor; decide in the session or with the commands above. It is off by default because the request already reaches the session as an approval dialog or a notice. Under the Claude desktop app's own entry (`relay-desktop`) it reaches neither: there it comes with the result of the next relay call of the conversation that started the work, so turn this on or look with `relay approvals`. No answer within `approval_timeout_s` counts as a denial.
- "For the rest of the job" (`scope: "job"` on the `approve` tool, `--job` in the terminal) saves repeat questions. On a Claude web request (WebSearch, WebFetch) it lets that job's later web searches and fetches go ahead without asking; it gives the job's shell commands no network access. On a Codex command it covers similar commands for the remainder of that turn. For an agent inside relay's own sandbox (Copilot), relay itself allows each later request of the job that is the same (same kind, same command, same directory, same files), once each, and never widens what the job was granted, web access included.
- An agent inside relay's own sandbox asks for something within that sandbox: allowing it lets the agent go ahead, and the sandbox stays on whatever you decide. Requests whose command, files or URL relay cannot read from the agent's tool call, and kinds of tool call relay has no reviewed reading of, are refused without anyone being asked.
- Copilot's own check of a path outside its trusted directories reaches you as a request of kind `path`. `wants` gives the access and the path (`write /x/escape.txt`), and `in_directory` the path. The access is `read`, `write`, or `read or write` when relay cannot tell from the tool call it belongs to, which relay takes as writing; Copilot's request itself says `read` even for a write. Allowing one lets Copilot go on, and nothing about the job's grant or its sandbox changes. For a read, that means the read happens: relay's sandbox allows reads everywhere except relay's own directories, its config and install files, and its API key files. A write outside the job's worktree, its granted directories and its temporary directory still fails. Relay refuses without asking a path in its own directories, in another job's worktree or in its config, or a directory holding one of these, and, in a read-only turn, any path Copilot could write.
- Set `escalation: false` to turn requests off, in which case a blocked job reports what it needed and you can `resume` it with a `grant`.
- A turn whose agent finished but was refused something it tried ends `blocked`, not `done`, and `status` lists what was refused under `blocked` (a consult's reply carries the same list). Relay goes by what the agent's own CLI reports: Claude's permission denials, and the commands and file changes Codex reports as declined. A command that simply fails inside Codex's sandbox is not reported as a refusal, so it is not counted, and neither is a file change refused under the `codex exec` backend, which reports it the same way as a change that failed to apply.

Two kinds of network access are separate. **Shell network access** (what `curl` or `npm install` needs) is off in every job's sandbox unless granted. No approval inside a running turn gives it: relay declines a Codex request to run a command outside the sandbox, and one to add the network to a single command on a job without a network grant (without Codex's network proxy, Codex would open loopback and every Unix socket to that command too). A Claude agent's sandbox never sends its network question to relay under `claude -p` (it answers it "user denied" on the spot), so relay sets the sandbox to refuse every host not granted and tells the agent that such a refusal is no one's decision; and relay refuses a Claude request to run the command outside the sandbox. So the root session gives the job a network grant when it starts or resumes it, or, with stage 2 on, allows a Codex job's `escalate` request for a turn with the network. **The host's own web tools** are handled per host. Claude's WebSearch and WebFetch need a network grant or an approval, because a launched Claude agent does not load your own permission rules (see `child_settings`). Codex's web search is left to Codex's configuration under `child_web: "inherit"`, the default (relay's own Codex home, not your `~/.codex`; see `child_web` in [configuration.md](configuration.md)), and is off unless granted under `"ask"`; with a network grant it is on (it runs at OpenAI, not on this Mac), whatever network the job's shell gets. Grok's `web_search` runs through Grok's own API host, which relay's proxy admits with the network off, and never asks, so relay drops it, `web_fetch` with it, and Grok's server-side tools (`features.backend_tools`: backend web search, X search, the code interpreter, which run inside the model request on that same host), from every Grok turn without a network grant, whatever `child_web` says (relay's Grok reads none of your own Grok settings); with a grant, `web_search` and the server-side tools are on and `web_fetch` stays off.

Whether relay shows you an approval dialog is the `ask_user` setting. `"auto"`, the default, and `"always"` offer dialogs only on a surface qualified both idle and busy; `"always"` remains valid for config compatibility and cannot override qualification. `"never"` leaves every request to the root agent and the terminal. A capability advertisement alone never qualifies a host. Withheld requests remain pending for next-call events, with `confirm` where its permission prompt is qualified. `status.approval_dialogs` reports whether this session offers dialogs and its reason, even with no pending requests; `relay doctor` lists the qualification floors and reasons for each surface. Relay’s Codex registration writes `env_vars = ["CODEX_HOME","CODEX_INTERNAL_ORIGINATOR_OVERRIDE"]` into `config.toml` (supported by the tested Codex 0.162+ floor), so the originator marker that T3 Code sets in that variable reaches the MCP server (and `CODEX_HOME`, for the review read denies above). Doctor warns when an older entry lacks the marker; reinstall and restart Codex to update it. Both `auto` and `always` leave decisions in T3 Code to the root agent or `relay approve` in a terminal; its waiting profile stays the same. Relay removes the originator marker from every launched agent’s environment so its Codex threads identify relay. Children other than Claude's (Codex, Copilot, Gemini and Grok) also lose Claude’s session variables (`CLAUDECODE` and `CLAUDE_CODE_*`). Claude children keep the auth/provider variables their backend needs; `CLAUDE_CONFIG_DIR` stays available so nested Claude turns find the user’s deny rules. A cancel is never read as an answer. What each host answered, how fast, and how relay read it, and every request it did not put to you and why (for example "host lacks elicitation"), is logged in `elicitation.log` in relay's state directory.

## Extensions

A launched agent gets relay's isolation: no MCP server but relay, no plugins or hooks, and, for Claude, none of your settings. An *extension* is a skill or an MCP server you allow a target's agents to be given anyway, one job or thread at a time, when the root session asks and you consent. Only Claude and Codex agents take extensions; an agent inside relay's own sandbox (Gemini, Copilot, Grok) does not.

**In this release only skills work.** A job or thread given an MCP server as an extension is refused before you are asked to consent and before its agent starts, `allow_tools` or not: relay passes an extension server's tool calls only through an adapter that screens each call's effects (paths, network destinations, redirects) against the never floor, and no server has a qualified adapter yet. `relay doctor` shows the count under "extension tools". The description of MCP servers below is how they will work once one has; until then, leave `mcp_servers` out of your config.

1. **Allow them in config**, per target. For example, two skills for Codex:

   ```json
   "targets": {
     "codex": {
       "skills": ["tdd", "~/.claude/skills/diagnose"]
     }
   }
   ```

   `skills` is `"none"` (the default), `"user"` (your own user skills for that target's CLI: `~/.claude/skills`, or `$CLAUDE_CONFIG_DIR/skills`, for Claude; `$CODEX_HOME/skills`, default `~/.codex/skills`, and `~/.agents/skills` for Codex: each skill there the CLI itself would find, for Codex one inside a group directory too, the first directory's for a name in both, and none that only a person can use; refused whole if one of them cannot be given), or a list of skill names in those directories and paths of skill directories (absolute or `~/…`; this is how a skill kept for one CLI, a plugin's say, is given to the other). `mcp_servers` names servers defined in relay's own file `mcp.json`, which relay reads from the directory of the config file it uses (`~/.config/relay/mcp.json` by default; beside `RELAY_CONFIG`'s file when that is set, and beside a linked `config.json`, not beside its target), in the shape of Claude Code's `.mcp.json`, stdio servers only:

   ```json
   { "mcpServers": { "email": { "command": "email-mcp", "args": ["--stdio"], "env": { "TOKEN": "…" } } } }
   ```

   It may hold credentials: keep it private (`chmod 600`; `relay doctor` warns otherwise) and out of any synced directory, so a `RELAY_CONFIG` file in a synced directory is no place for it. Better still, give a server a command that fetches its secret itself (from the keychain, say, with `security find-generic-password -w`) rather than a literal value in `env`: launched agents can read files you can (see "No way round the gate"). Relay does not read your Claude Code or Codex MCP configuration. `allow_tools` names a server's tools that run without asking you; every other tool asks.
2. **Ask for them on the call.** `delegate` and `ask` take `extensions: true` (root session only; for `ask`, when the thread starts). Relay resolves the target's extensions there and then, returns them (`extensions`, with a note on consent), and keeps them with the session for every later turn. It refuses the call if the target has none, a server is not defined in `mcp.json`, or a skill is not found; if the session is one where relay cannot put the consent to you (it has neither the approval dialog nor `confirm`: Claude Code under `-p`, a host relay does not recognise) or the call comes from a Codex subagent thread; and, for a session given MCP servers, if it asks for network, for write paths or for `allow_delegation: true` (such a session may not start or steer other relay agents, which would not have its limits).
3. **Consent.** Before the agent starts, relay files an approval request of kind `extensions` naming every skill, every server and every tool that runs without asking, with an effect that says what allowing does for what the session was given (the limits of a session given MCP servers only when it was given some). Only you can allow it: in relay's approval dialog, where your host is known to show it to you (interactive Claude Code, Codex), or in your host's permission prompt through `confirm`. The root agent's `approve` may deny it but cannot allow it, whatever it says you said, and `relay approve` cannot allow it either: any agent with a shell tool can run a command, under a terminal of its own if need be. An unqualified host gets no approval dialog even under `ask_user: "always"`; without a qualified dialog or `confirm`, it cannot allow a person-only request. Denied or unanswered, the turn fails without the agent having run; a later turn asks again. `status`, `result` and `relay tree` show each item's extensions and who consented, or that nobody has yet.

What the agent then gets:

- **Skills**: copies made for each turn in relay's own directory, removed when the turn ends: the skill's regular files only (no symlinks, dot-files, `agents/` directory or `SKILL.json`, by any case of the name), and no `SKILL.md` below the skill's top (Codex would load one as a skill of its own), with `SKILL.md`'s front matter cut to `name`, `description`, `license`, `metadata` and `argument-hint`, so a skill's `allowed-tools`, `hooks`, `model` and the like never apply. `user-invocable` goes too: nobody types a launched agent's slash commands, and Claude Code leaves a skill with `user-invocable: false` out of the report relay checks. A skill that sets `disable-model-invocation` (a slash command only a person can use) is left out under `"user"` and refused when named, since the agent could never load it, as is a skill whose `SKILL.md` is a symbolic link (the copy takes regular files only) or one larger than the copy takes (200 files or 5 MB), before you are asked to consent. The front matter is read fail-closed: a skill is refused if any line at its left margin is not a plain `key: value`, a list item or a comment (a quoted, `?` or `<<` key, an anchor or tag, a tab), if a key is given twice, or if it has a line break other than `\n`, since a YAML reader could see a key there that relay did not. Every launched Claude or Codex agent loads exactly the supplied skills, none by default, including when no extensions were requested. Personal, repository and bundled skills are switched off for every turn. Claude receives copies as `relay-skills:<name>` through a session plugin; its init report must list exactly that package and its skills (or empty lists). Codex uses an extra skill root and session-only `skills.config` overrides, disables skill MCP dependency installation, and checks `skills/list` before the thread starts; no system-skill exemption applies. Unexpected or missing skills, unreadable reports and discovery errors refuse the turn. The Codex `exec` fallback checks its empty skill set through its existing app-server preflight; extensions still need the app-server backend. `targets.<id>.skills: "user"` allows your user skills to be selected and copied through the consent flow. Nothing is written into your own CLI configuration. [Native probe and fixtures](extensions.md) record the scratch-home checks on Codex 0.163.0 and Claude Code 2.1.302.
- **MCP servers** (refused in this release; see above): never configured in the agent's CLI. The agent's own relay server, which its CLI starts outside its sandbox as your process, starts each server and offers its tools as `<server>__<tool>`. A call's arguments are checked against the tool's input schema; a call the config does not allow outright is an approval request of kind `mcp` showing the server, the tool and the arguments in full, which only you can allow, and nothing reaches the server before you do. Allowed, it goes to the server with exactly those arguments; "for the rest of the job" lets later calls of that tool through, whatever their arguments; refused, the agent is told not to try another way. A server is started with the environment the agent's CLI gives relay's server (Codex passes only a few variables) plus its own `env`, in its own `cwd` or your home folder, never the agent's directory. A server that cannot start, or a tool relay cannot offer as given, is left out for that turn: the turn goes on without it, the agent is told so before it starts (in relay's server instructions, which Claude Code shows the agent; not yet checked for Codex), and the turn's result has a warning. Skills are stricter (a given skill that does not load stops the turn), since a skill missing changes what the agent does without its noticing, and a server missing only takes tools away.
- **No way round the gate from the session given them.** The agent can read what you can, credential files included. So a session given MCP servers has no network and no write paths outside its worktree: a network grant or write paths are refused for it, at the start and on every resume, `child_network` and `allow_dangerous` cannot be set with `mcp_servers`, and every approval request from it, a web fetch or a file outside its worktree included, is yours alone to allow. It may not start or steer other relay agents either (`allow_delegation` is off for it, and its calls that would are refused), since an agent it started would have none of these limits; its CLI's own subagents (Claude's Task tool) work inside it, under the same sandbox and gate. The CLI's own web tools ask in such a session (Claude's WebSearch and WebFetch) or are off (Codex's web search, which cannot ask, and which relay reads back in Codex's effective configuration), as under `child_web: "ask"`, whatever your settings say: a search or fetch could carry a credential to the service. No grant may cover relay's own config files (`config.json` and `mcp.json`, a linked `config.json` by either its name or where it leads, and any directory holding one, by a name in any case on macOS's disks, which ignore case, or by the data volume's name for it, `/System/Volumes/Data/…`), no file request may change one, and Claude's sandbox and relay's own deny writing either, `mcp.json` also before it exists (they are among relay's protected config files, with its install record). This is about the session given the servers. Another launched agent can read what you can as well, but not `mcp.json`: it is among relay's config files, which every agent's sandbox denies (by each of its names), except a Codex write job run without a sandbox under `allow_dangerous`.

A config is refused that combines any extension with `child_mcp: "inherit"` or `child_hooks: true`, or a Claude target's extension with `child_settings: "inherit"` (each loads your own servers, hooks or settings ungated; `child_settings` concerns Claude agents alone), that combines any extension with `escalation: false` (consent is an approval request), or that gives Codex any extension under `codex_backend: "exec"`.

## Watching and stopping

```sh
relay tree            # latest run: every job, thread, discussion and review, with status and elapsed time,
                      # and for running ones what the agent is doing and how long it has been quiet
relay tree --watch
relay cancel <id>     # a job, thread, discussion or review, and everything under it
relay cancel <run_id> # the whole run
relay clean [run_id]  # remove finished runs' worktrees and merged relay/* branches (all finished runs if no id),
                      # relay's leftover temporary directories, room expiry, and old run/room records under keep_records_days
relay clean --forget <run_id> [--write]
                      # forget a finished run kept because its repository is gone: its records and relay's own
                      # files for it; prints what it would do, and changes nothing without --write
```

For a running item, `status` also gives its `liveness`: when its agent last did anything (`last_activity_at`, and `quiet_s` since then), what it last started (`activity`: a command, tool or file, the same as in a waiting call's progress line, with `activity_at`; left out until it has started anything), and for a write job the files changed so far (`files_touched`). It is information only: relay stops nothing for being quiet. `quiet_s` counts from the agent's last logged event, so a model thinking for a long time looks quiet too.

Cancel asks each agent to stop cleanly, waits a few seconds, then kills whatever is left, including the processes the agent started that relay can still trace to it (see Known limits). If relay could not stop a process, or knows it missed its last look at them, the result of the job, consult, discussion or review carries `warnings` saying so, whatever the outcome was. Cancelling a discussion closes it and stops the reply it is waiting for.

Runs keep going after you close the session that started them, until their work ends or is cancelled (or a time limit you set below runs out). A run belongs to the session that started it. If that session has gone (closed, or its relay server restarted), recovery requires explicit adoption: get the destination connection's `status.session.fingerprint`, then use `adopt` with the run's reported adoption details and the required person's permission or terminal authorization. Follow [Run access and recovery](install.md#run-access-and-recovery-in-10) for the exact procedure. Merely naming an item does not transfer access.

Relay keeps three directories. `~/.local/state/relay/` is its control directory: the registry, and under `runs/<run_id>/` the logs, the prompts sent and the transcripts. Job worktrees live separately, under `~/.local/share/relay/worktrees/`, and the state relay keeps between turns for harnesses in its own sandbox under `~/.local/share/relay/harness/`. How long the records are kept is under "What is kept" in [Security model](../README.md#security-model); `relay doctor` says how much they take and how much room is left on their disk.
