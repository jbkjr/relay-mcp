# Extensions for launched agents: design note

Status: written 2026-10-17, before the code, and kept in step with it since. Extensions shipped in relay 1.0, after an extra security review round (the maintainer's decision of 2026-10-17).

An *extension* is a skill or MCP server given to a launched Claude or Codex agent when config allows it, the root requests it, and the person consents. Every launched agent loads exactly the skills Relay gives it, none by default. Personal, repository and bundled skills are switched off even without extensions. Use `targets.<id>.skills: "user"`, request extensions and consent to give an agent your user skills.

Codex skill sources come from the root Relay process's original environment: `$CODEX_HOME/skills` (or `~/.codex/skills`) and `~/.agents/skills`. Relay's separate `targets.codex.home` provides runtime config and login; it is not the source catalog. After consent, filtered copies reach the runtime through an extra skill root for that turn.

## What the review items require, and what relay does

The items are from the plan review `r_e9616e60` (discussion `d_29ef7fac`, final list in its last turn).

**C2/X1 (blocker): qualified mediation, person-only consent, no direct bypass.** Required: mediation per harness bound to server, tool and arguments, unknown forms denied, nothing run before approval; the person's consent for external actions (subject to tools the config allows outright); Codex's own MCP approval path probed before relying on it; no way round the gate through readable credentials and a reachable endpoint, or the configuration refused; docs saying effects are outside the worktree promise.

- *Gateway, not the harness's own MCP handling.* No allowlisted server is ever configured in Claude or Codex. Relay's own MCP server for the turn (the launched agent's `relay` server, which both CLIs start outside the agent's sandbox, as the person's process) starts each allowed server as its client and offers that server's tools as its own, named `<server>__<tool>`. Both harnesses already allow relay's tools without asking (Claude: `--allowedTools mcp__relay`; Codex: `default_tools_approval_mode = "approve"` on relay's entry), so every call reaches relay's code, and relay alone decides. Codex's own MCP approval path (W-1 X-a: unqualified) is never used, so there is nothing of it to probe or trust. What the gateway does rely on in each harness (that relay's tools are called without asking, Claude's `--allowedTools mcp__relay` and Codex's `approve` mode on relay's entry, and that a call waiting for the person is not cut off first: Codex's `tool_timeout_sec` on relay's entry is set past the longest an approval can make a call wait, a wait behind an earlier request of the agent's and then the answer's, each up to `approval_timeout_s`) is checked against stub agents only. Qualifying it in signed-in Claude Code and Codex turns, a gated call allowed and one denied across a long wait, is open (plan A6 status).
- *Bound to server, tool and arguments; unknown forms denied.* A call names one of the tools relay listed, or it is an error and nothing is asked. Its arguments are checked against the tool's input schema first; malformed ones are an error and nothing is asked. The approval request shows the server, the tool and the arguments in full (as relay will send them, defaults filled in), and an allowed call is forwarded with exactly those arguments. Nothing reaches the server before the allow.
- *Person-only.* A tool call that the config does not allow outright is an approval request of kind `mcp`. Like the request for consent to the extensions (below) it can be allowed only by the person (a *person-only request*, in GLOSSARY.md's terms), and only in two places, which this lane chose (the review's final text requires person-only consent and names no route; plan A6 reading (5)): relay's approval dialog (MCP elicitation, where the host is positively known to show it to a person: interactive Claude Code, Codex) and `confirm` (Claude Code's permission prompt, offered only where relay has checked nothing answers it for the person). The root agent's `approve` may deny it, never allow it, `user_confirmed` or not. A launched agent has no tool that decides anything. A command cannot allow one either: `relay approve` refuses every person-only request, since any agent with a shell tool can run a command, under a pseudo-terminal of its own if relay looked for one (an earlier draft of this lane checked for an interactive terminal; `script -q /dev/null relay approve …` got past it). `relay deny` still works from anywhere. This is enforced on relay's tools and commands: relay does not confine the root session, so it guards against a root agent talked into approving, not one acting on its own through an unconfined shell (README, Known limits). Under `ask_user: "always"` relay also asks hosts it does not know to show the question to a person; there, an allow of a person-only request decides nothing (it is recorded as unattributed and the request stays pending), and a deny counts. A root session with neither the dialog nor `confirm` gives no extensions at all (the call is refused, saying why), since nobody could consent there.
- *Explicit preauthorization.* `mcp_servers` entries may name tools that run without asking (`allow_tools`), as the plan allows. The consent text names them.
- *No direct bypass.* A launched agent can read what the person can (reads are not confined for Claude and Codex), including credential files and relay's own definition of each server. What it must not have is a way to use them past the gate. So a session given MCP servers has no network and no write paths outside its worktree: a network grant or write paths are refused for it, at the start and on every resume, and `child_network` and `allow_dangerous` cannot be set together with any `mcp_servers` (config error). And every approval request from such a session is person-only, whatever its kind: a command outside the sandbox, a web fetch or a file outside the worktree would each be a way round the gate if the root agent could allow it. Nor may such a session start or steer other relay agents: an agent it started would have none of these limits (the root agent could allow its commands, and its web tools would follow the person's settings), so `allow_delegation` is off for it (asked for outright, the call is refused), its turns' relay server is told it may not delegate, and relay refuses its delegate, ask, discuss and review calls, and its calls that steer an item, whatever its turn's policy says. The harness's own subagents (Claude's Task tool) are not relay agents: they work inside the same agent, under its sandbox and relay's gate. Inside its sandbox the agent can do what it could do without extensions; outside, the servers' processes are reachable only through relay. The servers' definitions live in relay's own file (below). It is one of relay's protected config files (`src/core/protected-config.ts`, with `config.json` and the install record), so Claude's sandbox and relay's own deny writing it, also before it exists, and a directory that holds only these files is protected whole (Codex's sandbox writes only in the worktree, temporary directories and granted paths). No grant may cover it or `config.json`, and no file request may change either: each by the name relay looks for it under and, for a link (a `config.json` linked into a synced repository, as docs/UPGRADING.md describes), by where the link leads, and any directory holding one. On macOS, whose default disks ignore case, a name in another case is the same file, and is refused as one (relay compares the existing part of a path by its name on disk, and the rest without regard to case), and so is the data volume's own name for it (`/System/Volumes/Data/Users/…` is `/Users/…`, a firmlink that realpath leaves as given), as are relay's control directory and the worktrees' directory. This holds for every job, given extensions or not, since a job that rewrote either file would change what the next one is given. The CLI's own web tools are held back in such a session as under `child_web: "ask"`, whatever the person's settings say: Claude's WebSearch and WebFetch ask (and so are person-only), Codex's web search, which cannot ask, is off, and relay reads that back in Codex's effective configuration before the turn starts. A search or fetch could carry a credential to the service as a URL. Once the turn has ended or its work is cancelled, the gateway forwards no call, one the config allows outright included. All this concerns the session given the servers. Every other launched agent can read what the person can too: relay denies each launched Claude agent (not under `allow_dangerous`) reading `mcp.json`, by each of its names, through the sandbox's `denyRead` and a Read deny rule, as it does for the independent review's transcripts; Codex's sandbox cannot deny a read, and a command approved outside the sandbox is not confined, so such an agent with the network could use what `mcp.json` holds. The README says so (Known limits) and recommends server commands that fetch their secrets (from the keychain) over literal values in `env`.
- *Docs.* README and this note say that an allowed tool call acts outside the worktree, as the person's process, with whatever the server can reach.
- *Open.* The gateway is qualified against stub harnesses and a stand-in server only (above); a signed-in Claude Code and Codex turn calling a gated tool, allowed and denied, across a long wait, is still to run (plan A6 status).

**X2 (major): authority counts extension capabilities.** Required: effective MCP/tool capabilities in per-turn authority; delegation, resume and borrowed sessions constrained; tests that a descendant cannot confer more external authority.

- Only a root session gives extensions (as with grants): a launched agent's call that asks for them is refused, so nothing a launched agent starts holds an extension. A call from a Codex subagent thread, a root session with no person in its conversation, is refused too, as its grants are (review C6). A session that holds MCP servers starts and steers nothing at all (above), so its limits cannot be left behind in a child.
- `authority()` compares extensions as it compares grants: a launched agent may not resume, cancel, merge or borrow into a discussion an item whose session holds an extension (a skill by its source, a server, a tool allowed outright) that its own session does not.
- Extensions are fixed when the session starts. A resume or follow-up neither adds nor drops them; a network grant on resume is refused for a session holding servers.

**C8 (major): skills need extraction, loading and verification.** Required: a filtered per-turn instruction package without hooks, MCP configuration or agent definitions; discovery and tool behaviour stated; the effective surface verified where the harness exposes it; modes that cannot be checked refused.

- *Sources.* `targets.<id>.skills` is `"none"` (default), `"user"`, or a list. `"user"` is the person's own user skills for that target's CLI: `$CLAUDE_CONFIG_DIR/skills` (default `~/.claude/skills`) for Claude; `$CODEX_HOME/skills` (default `~/.codex/skills`, without its `.system`) and `~/.agents/skills` for Codex. It takes each skill there that the CLI itself would find: for Claude the skill directories directly in the root; for Codex also one inside a directory that is not a skill (a group), as deep as Codex looks (six levels, observed with codex-cli 0.163.0), never in a dot-directory; for a name found twice, the first root's. A skill nested inside another is part of that one's copy, not a skill of its own (below). A list names skills in those directories (each found as `"user"` finds it), or gives a skill directory's path (absolute or `~/…`; the skill goes under the directory's name), which is how a Codex job gets a skill kept for Claude (a plugin's, say).
- *What a launched agent could not load whole is refused when the call is made*, naming the skill, rather than failing after consent: a `SKILL.md` relay cannot read fail-closed (below), one that is a symbolic link (the package takes regular files only, so the skill would arrive without it; this lane first read through the link and then copied nothing), one named only in another case (`skill.md`), a skill larger than its package takes (200 files or 5 MB of what the package copies, below), and a skill whose front matter sets `disable-model-invocation` to anything but a plain false, a slash command only a person can use, which the model can never load. Under `"user"` such a slash command is left out and the rest are given; any other of these refuses `"user"` whole. The package checks each skill again when it is built, so one changed after the call fails the turn before the agent starts.
- *Package.* Before each turn relay copies every selected skill into a directory of its own under the turn's node directory, which no agent can write: the skill's regular files, without symlinks or dot-files, without an `agents/` directory or `SKILL.json` at its top, by any case of either name (harness metadata: Codex reads MCP dependencies from there, and a disk that ignores case opens `Agents/` as `agents/`), and without any `SKILL.md` below its top, in any case (Codex loads such a file as a skill of its own, with its own unfiltered front matter, observed with codex-cli 0.163.0), within a size cap (200 files, 5 MB; a larger skill is refused, not cut). Its `SKILL.md` keeps only the front-matter keys `name`, `description`, `license`, `metadata` and `argument-hint`: `allowed-tools`, `hooks`, `model`, `context`, `agent` and anything else are dropped, since they would pre-approve tools, run hooks or start other agents. `user-invocable` is dropped too: Claude Code 2.1.302 leaves a skill with `user-invocable: false` out of its init report's `skills` (it lists only skills a user can invoke), where relay checks that every given skill loaded, and nobody types a launched agent's slash commands. `disable-model-invocation` is read first (above) and dropped. Relay reads the front matter line by line, fail-closed, rather than with a YAML parser whose reading might differ from the harness's: a line at the left margin must be a plain `key: value` (a bare key, a colon, then a space or the end of the line), an item of the sequence above it (`- …`) or a comment; indented lines belong to the key above. Anything else at the margin (a quoted key, a `?` or `<<` key, a flow collection, an anchor, a tag, a tab, a document marker), a key given twice, or a line break other than `\n` (YAML also breaks lines at a lone `\r`, and some readers at U+0085, U+2028 and U+2029) refuses the skill, since a YAML reader could see a key there that relay did not. The kept keys are written out as they were, under relay's own `name`. A skill's scripts, and commands a skill has Claude run as it loads (its `` !`…` `` lines), go through the agent's own tools, sandbox and permission checks like any command of its. Nothing is ever written into the person's own `~/.claude` or `~/.codex`. The package is removed when the turn ends.
- *Claude.* The package is a session plugin, `relay-skills`, passed through `--plugin-dir`; each skill is `relay-skills:<name>`, and a read turn gets the `Skill` tool. Without a package, `--disable-slash-commands` disables skills entirely under isolated and inherited settings alike. Every turn also sets `disableBundledSkills`, disables the two built-in skill plugins of Claude Code 2.1.302, and turns off discovered personal/repository skills and the remaining bundled plugin commands with `skillOverrides`. The init report must list exactly Relay's plugin at its package path and exactly its skills, or empty lists when none were given. Missing reports, unknown names (including unprefixed ones), duplicates and unexpected plugins refuse the turn before work, including full-access turns. Extensions remain incompatible with inherited Claude settings.
- *Codex.* Every turn switches off all discovered user, repository, machine and bundled system skills with session-only `skills.config=[{path, enabled=false}, …]` overrides, and disables `skill_mcp_dependency_install`. The known 0.163.0 bundled paths are disabled even before a fresh home installs them; a new upstream skill fails closed at readback. A package has no plugin manifest (otherwise 0.163.0 prefixes its names) and is added through `skills/extraRoots/set`. Before the thread starts, `skills/list` with the turn's cwd and `forceReload: true` must report exactly the given copies enabled at `<package>/skills/<name>/SKILL.md`, with their given names and no discovery errors. There is no system-skill exemption. Without a package, none may be enabled. The `exec` fallback checks its empty skill set through its existing short-lived app-server preflight, using the same configuration passed to `exec`; given extensions still require the app-server backend. No personal CLI config is written.
- *Native evidence.* `scripts/probe-skill-isolation.mjs` uses scratch homes, Codex 0.163.0 app-server RPC and Claude Code 2.1.302's local `/skills` command, without a model turn. It checks user/repository discovery, isolated and inherited Claude settings, an empty skill set, and exactly one supplied skill. Selected native reply fields, with scratch prefixes normalized, are replayed in `test/native-skill-fixtures.test.ts` from `test/fixtures/native-skill-isolation.json`. This does not qualify signed-in model turns or gateway mediation.

**C17 (minor): legacy inheritance settings must not bypass the guarantees.** Required: precedence defined; incompatible combinations refused, or configurations that waive the guarantees identified.

- Any extension in the config together with `child_mcp: "inherit"` or `child_hooks: true`, and a Claude target's extension together with `child_settings: "inherit"`, is a config error naming both: each of those loads the person's own servers, hooks or settings (plugins and their skills among them) ungated, which would make the allowlist meaningless. `child_settings` is about Claude Code's settings files alone and loads nothing into a Codex agent, so it does not conflict with a Codex target's extensions. There is no precedence to learn: the two cannot be combined.
- `relay doctor` says, for each of the three, that it waives relay's isolation of launched agents and cannot be used with extensions (for `child_settings`, Claude's).


## Consent scans include extension hooks

Claude Code documents plugin hooks in default [`hooks/hooks.json` and the manifest's `hooks` field](https://code.claude.com/docs/en/plugins-reference#hooks). The latter accepts inline event maps, paths to wrapped hooks files, or mixed arrays; these merge with the default file. Its [loading reference](https://code.claude.com/docs/en/plugins/loading#check-which-stage-a-plugin-reached) identifies `plugins/installed_plugins.json` (including in-place `installPath` records) and `plugins/cache/` under the Claude config directory. [Skill frontmatter can declare hooks](https://code.claude.com/docs/en/hooks#hooks-in-skills-and-agents), which stay registered for the rest of the session once invoked.

Alongside settings and DM8 subagent definitions, Relay scans `~/.claude/plugins` and `$CLAUDE_CONFIG_DIR/plugins`, including cached versions, recorded install paths and locally registered marketplaces outside the cache, each plugin's default and declared hook files, and personal/repository/plugin skill frontmatter (legacy command and plugin agent definitions too), including nested repository skill roots that Claude can discover later. A `PreToolUse` or `PermissionRequest` matcher that could match `mcp__relay__confirm` or `mcp__relay__adopt` withholds permission-prompt authorization; an `Elicitation` or `ElicitationResult` matcher for `relay` withholds the approval dialog. `confirm` is also the extension-consent tool, so these checks cover giving extensions and allowing their gated calls. Unrelated plugin matchers leave those routes available.

Marketplace entries that declare hooks, agents or commands also withhold both routes, since relay cannot establish their effective sources. An entry that declares only `skills` is checked instead. Relay looks under every copy of the plugin on disk: the marketplace directory for a relative `source` (also under `metadata.pluginRoot`), every cached version under `plugins/cache/*/<plugin>/`, and each recorded install path. It reads every `SKILL.md` under each declared path with the skill frontmatter check below. A declared path or source outside the plugin or marketplace, a link leading out of the plugin directory, a zipped cached copy, or an unplaceable plugin name withholds both routes. A remote plugin with no copy on disk adds nothing. Every cached version directory counts as a plugin root, with or without a `plugin.json`, so its default skills, agents, commands and hooks file are read too. `CLAUDE_CODE_PLUGIN_CACHE_DIR` and `CLAUDE_CODE_PLUGIN_SEED_DIR` withhold both routes, because they move plugins outside the scanned directories. Unreadable directories, plugin registries/manifests, hook files, ambiguous shapes and JavaScript hook modules fail closed. As in DM8, any skill/command/plugin-agent `hooks` key or unreadable/ambiguous frontmatter conservatively withholds both routes, even if its hooks look empty or unrelated; only the bounded leading frontmatter is read. The frontmatter check follows how Claude Code (2.1.326) reads the block: up to the first `---` anywhere, Bun's YAML parser, then one retry with each column-0 `key: value` line's value quoted; hooks are the result's top-level `hooks` key. Relay withholds when `hooks` followed by `:` appears anywhere in the block, or when a line at column 0 is anything but a comment, a `- ` entry under the key before it, or a plain `key:` entry, or continues a quoted scalar or flow sequence opened earlier. It also withholds, as margin, for YAML it does not model: flow mappings, anchors, aliases, tags, directives, quoted and explicit keys, duplicate top-level keys, nested flow collections, and comments or pairs inside a flow sequence. A `:` that is not followed by a space, as in `allowed-tools: Bash(git add:*)`, is part of a plain value, and flow (`[Read, Grep]`) and block lists of plain or quoted values are read as values. A hooks file that loads a hooks module (`modules`) withholds both routes, with a reason that names the module. Cached/disabled copies count too: Relay cannot prove the running session unloaded their hooks. CLI-only plugins (`--plugin-dir`, archives/URLs, or `CLAUDE_CODE_PLUGIN_DIRS`) withhold both routes when their source cannot be established from the flattened process command line. Nested directory walks are bounded and fail closed on unreadable roots; a session started in the home directory withholds these routes rather than scanning the whole home. The scan runs when Relay's server starts; later changes and console-delivered managed settings remain outside what it can establish. Terminal adoption tickets remain available.

## The rest of the design

**Config** (keys new in 1.0; keep them out of a config file an older relay also reads, as [UPGRADING](UPGRADING.md#your-config-across-versions) says):

- `targets.<id>.skills`: as above.
- `targets.<id>.mcp_servers`: a list of server names, or `{ "name": …, "allow_tools": [ … ] }`.
- Only targets that can take extensions accept the keys: Claude and Codex. For an ACP target (Copilot, Gemini, Grok) they are a config error, and a call asking for extensions there is refused: such a harness runs inside relay's own sandbox, where a server outside it would be a way out that 1.0 does not qualify.
- Also config errors: `mcp_servers` with `child_network` or `allow_dangerous`; any extension with `escalation: false` (consent is an approval request); any extension for Codex with `codex_backend: "exec"`.

**Server definitions.** The names in `mcp_servers` are entries of relay's own file `mcp.json`, in the directory of the config file relay uses (`~/.config/relay/mcp.json` by default; beside `RELAY_CONFIG`'s file when that is set, and beside a linked `config.json`, not its target), in Claude Code's `.mcp.json` shape, stdio servers only: `{ "mcpServers": { "email": { "command": "…", "args": [ … ], "env": { … }, "cwd": "…" } } }`. It is machine-local, never synced (so a `RELAY_CONFIG` in a synced directory is no place for it), and may hold credentials, so doctor warns unless only its owner can read it. Relay does not read Claude's or Codex's own MCP configuration: their formats, scopes and login stores differ, and a server relay runs must be one the person defined for relay. The file is read when the call asks for extensions (to refuse unknown names early) and by the gateway when it starts, never copied into the registry or a run directory.

**On the call.** `delegate` and `ask` take `extensions: true` (root session only; not on a follow-up). Relay resolves the target's configured extensions there and then (skill names and sources, server names and their tools allowed outright), records them with the session, and returns them (`extensions` and `extensions_note`, in delegate's answer and in ask's reply or pending handle alike). A call is refused when the target has none configured or cannot take them, when the calling session has neither relay's dialog for a person nor `confirm`, when it comes from a Codex subagent thread (as a grant is: a root session no person is working in, which would choose unchecked which session holds skills and servers; the parent makes the call from its own thread), or when the session would have servers and a network grant, write paths or `allow_delegation: true`.

**Consent.** Before the first turn of a session with extensions runs, relay files an approval request of kind `extensions` whose text names every skill, every server and every tool that runs without asking, and whose effect says what allowing does for what the session was given, job or thread: for skills, that the agent gets copies of them without hooks, MCP servers, agent definitions or pre-approved tools, read and run through its own sandboxed tools; for servers, that they run outside the sandbox as the person's process, each other tool call asks, and the session gets no network (a job, no write paths outside its worktree either), may not start or steer other relay agents (its CLI's own subagents work under the same sandbox and gate) and has only the person decide its requests. A session given skills alone keeps every limit and permission it would have without them (a network grant included), and its other requests are not person-only, so its effect claims none of that. The agent is not started meanwhile; its slot is lent. Person-only, as above. Allowed: recorded with the session (who decided, when), and later turns do not ask again. Denied or expired: the turn fails without the agent having started, its error saying who refused (relay's record of the decider: the user, the root session, a terminal, named as `relay deny`, since `relay approve` decides no person-only request) or that nobody answered; a later turn asks again. A cancel while it waits ends the turn as cancelled.

**Status.** Every view of the item (`status`, `result`, `relay tree`) names its extensions (servers with the config's `allow_tools`) and the state of consent. A server that could not start, or a tool relay could not offer (a name or schema it cannot pass on), is left out for that turn, and the turn goes on: the agent is told before its first step, in the instructions of its relay server (its preamble was written when the work was given; Claude Code shows a server's instructions to the agent, and whether Codex does is not yet checked), and the turn's result has a warning. This is a deliberate difference from skills, where a given skill that does not load stops the turn: a missing skill changes what the agent does without its knowing, a missing server only takes tools away, and the agent is told which. Plan A6's "exactly these loaded and no others" is met on the "no others" side by the gateway starting only the allowlisted servers and by the per-launch checks that the harness has no MCP server but relay; on the "exactly these" side, a server that fails to start is reported rather than fatal.

**Where it lives.** `src/core/extensions.ts`: config shapes, resolution, the skill package, the consent text, authority keys. `src/mcp/gateway.ts`: the per-turn gateway in the launched agent's relay server. The Claude and Codex backends add the package and its checks; the worker files the request for consent; `approve` refuses what is person-only.
