# relay: how it is built

This describes relay as it is. For what it promises and what it does not, see [security-model.md](security-model.md).

## The pieces

- **The MCP server** (`relay mcp`, `src/mcp/server.ts`). Each host session starts one over stdio, and so does every launched agent that may use relay. The exception is the Claude desktop app, which starts one from its own entry, `relay-desktop`, for its chats and one for Cowork and the Code tab together (a Code tab session also has its own server, from Claude Code's registration); relay cannot tell those sessions apart, so sessions of a kind share one root ([install.md](install.md#claude-desktop-app-and-cowork), "Claude desktop app and Cowork"). The server holds no accepted state of its own: it checks the call, writes rows in the registry, starts workers, and waits. A review submission is accepted only after the reviewer settles; an unfinished wait accepts nothing and asks the caller to send the text again. The installer registers it with `--host <target>` (`claude` for Claude Code and the desktop app, `codex` for Codex), which is how a root session's server knows which family it is serving. A `--host` naming no known host makes the server refuse every call; without `--host` (older registrations) the host's client name decides, but only when it matches exactly one target. A `--host` contradicted by a non-empty client name leaves the caller's family unknown and is retained only for explanation and review transcript protection. With `same_family: "allow"` (the default), unknown callers may name a target; an omitted target requires `default_target.unknown`. With `same_family: "refuse"`, unknown callers cannot start or continue an agent. The desktop app's entry also carries `--desktop` (`hostFromArgs`): that server starts its instructions and every tool description with one sentence saying it is the app's shared relay, to be passed over where the session has its own, and its host profile caps every wait at `DESKTOP_WAIT_S` (50 s, below the app's 60 s tool timeout, a timeout restarting the shared server; `src/mcp/host.ts`, applied in `waitLimitS` in `src/core/wait.ts`). A client whose name starts `local-agent-mode-` (the app's connection) gets the same cap without the flag.
- **Workers** (`relay worker <id>`, `src/worker.ts`). One detached process per session that has work queued. A worker runs that session's turns one after another, each as a fresh process of the target CLI, and exits when the queue is empty, after its housekeeping: at most once a day across the control directory (a stamp file there), the sweep of the temporary directories relay left behind and, where `keep_records_days` is set, the forgetting of old runs (`housekeepDaily` in `src/core/retention.ts`). It outlives the server that started it, because a launched agent's server exits when that agent's turn ends. Told to stop (`cancel` sends it SIGTERM), it aborts a start still under way (the `codex exec` fallback's configuration check, which it runs itself), cancels the turns in flight and what any such start launched, and exits once they have ended (`cancelActiveTurns` in `src/core/session.ts`); a relay-enforced (ACP) start is not waited for yet.
- **The registry** (`src/core/db.ts`). One SQLite file in the control directory: runs, nodes (jobs, consult threads, discussions, reviews), turns, approval requests, concurrency slots, and relay's own processes. Every process reads and writes it; accepted state is durable across calls, until `keep_records_days`, where it is set, forgets a run nothing uses any more: its rows are deleted and the file rebuilt (`src/core/retention.ts`). The caller's review is saved before `own` is set and reconciliation starts, after the reviewer has settled, so every connection withholds the reviewer's artifacts until that save (or an explicit skip). It carries a schema version (`PRAGMA user_version`): a relay opening an older file backs it up next to itself before migrating it (`relay install --write` does this first), and refuses a file from a newer relay; see [UPGRADING.md](UPGRADING.md).
- **Targets** (`src/targets/`). The registry of agents relay can launch: for each, its id (what callers name and nodes record), the family behind it (the `vendor` field, what the cross-family rule compares; null for a harness that runs several families' models, whose family is then the model's, from a reviewed list of model ids), whether it is on by default, its harness's name, its tested version, its credential, login-override and endpoint variables, how it asks for approval, its capabilities (who confines it, whether read-only, network-off and extra write roots are enforced, how it asks for approval, whether an approval can escalate, whether sessions resume, how its login is known), whether it is qualified, and the names and text that go with it. It is data and imports no backend. `resolveTarget` decides which target a call reaches, and `incapable` whether it can honour the call. Adding a target is a module there and a backend.
- **Backends** (`src/backends/`). `index.ts` maps each target to its backend. `claude.ts` builds a `claude -p` invocation and reads its event stream. `codex-app.ts` drives `codex app-server` over JSON-RPC; `codex.ts` holds the flags and the `codex exec` fallback. `acp.ts` is the generic driver for harnesses that speak the Agent Client Protocol (version 1), and `copilot.ts`, `gemini.ts` and `grok.ts` are Copilot's, Gemini CLI's and Grok Build's profiles for it (see "ACP harnesses" below). A backend is one method, `start(spec)`, which resolves to the turn's handle (its process, `done`, `cancel`) once the agent is launched, so a backend may await something first (Codex's configuration check, ACP's launch). `run.ts` has `launchTurn`: the version gate, then the target's backend. `stream.ts` has the default runner, `streamTurn` (one process per turn, one JSON event per line on its stdout), which Claude and the `codex exec` fallback use, and `afterTurn`, which runs a step after the turn (archiving a Codex thread) before its result is reported. `env.ts` builds and checks the agent's environment once per turn (`agentEnv`: credentials removed, endpoint refused), `types.ts` has the shared types and the turn's policy (`turnPolicy`), and the process helpers (watching what an agent starts, and stopping it) are in `src/core/procs.ts`.
- **Hosts** (`src/hosts/`). The registry of programs relay installs into (Claude Code, Codex, the Claude desktop app): for each, the target family it registers as, how install and uninstall plan their changes there, its plugin's format and generated adapter, and its doctor lines. `adapters/build.mjs` generates the adapters from one set of skill texts, adding to each host's the prompting briefs (`adapters/briefs/`, read by `src/targets/briefs.ts`) for the families it reaches; the `brief` tool serves the same text to hosts without a plugin. `src/install/common.ts` holds what install, uninstall and doctor share.
- **Confinement** (`src/confine/`). Relay's own sandbox for harnesses that cannot be confined through their own settings (relay-enforced confinement): the mechanism interface, the Seatbelt profile, the per-turn proxy, state isolation, the hard-link check, the boundary probes, and the broker and bridge through which a confined agent reaches relay. No launch uses it yet (see "Relay-owned confinement" below).
- **Records and their storage** (`src/core/storage.ts`, `src/core/secrets.ts`, `src/core/retention.ts`). How relay writes what it keeps in the control directory: logs rotated at `log_max_mb`, the secrets it knows the shape of cut from what it writes and returns (`secrets.ts`), a write that fails said in words a person can act on rather than thrown at a worker, and what `doctor` says of the directory (`storage.ts`); and what relay removes of its own accord, the leftover temporary directories and, under `keep_records_days`, old runs' records (`retention.ts`). See "What is kept" in [security-model.md](security-model.md).
- **The CLI** (`src/cli.ts`): `bridge` (internal, see below), `tree`, `chat`, `cancel`, `clean`, `approvals`, `approve`, `deny`, `install`, `uninstall`, `doctor`.

## A call, end to end

`delegate` from a root session: the server resolves the target (a named one, else the caller's `default_target`, else the only switched-on target of another family; an omitted target never picks the caller's own family, and an unknown caller needs `default_target.unknown`; for a harness of several families, by the model the call would run, which is then kept with the item). Under the default `same_family: "allow"`, an explicitly named target may be of the caller's own family and an unknown caller may name one; `"refuse"` rejects those starts. Every start records family labels, including unknown. The server then admits the call (depth limit, the caller's own access, what the target can honour), creates a worktree for a write job, inserts a node and its first turn, and starts a worker. The worker takes a concurrency slot, writes a context file carrying that one turn's policy (which turn, read or write, may it delegate, may it ask), builds the CLI invocation with the sandbox settings for that policy, and runs it. If the launched agent has relay, its own server reads the context file: its authority is that turn's and ends with it. The turn's own record says it is over as soon as its agent has ended, which is where that authority ends. The worker then commits the job's work and, in one transaction, records the result and either settles the item or shows it as queued for the next queued turn (`finishTurn` in `src/core/outcome.ts`), so that no reader finds the result without the item settled, nor a failed turn's queued turns still waiting; a turn that never started holds no authority and is recorded as over in that same transaction. With nothing queued the worker exits. A turn whose harness reported that the agent was refused something (Claude's permission denials, Codex's declined items) leaves the item `blocked` rather than `done`; a write job whose branch is still at its base after a finished turn has the outcome `no_changes`. While a turn runs, `status` reports its liveness (`src/core/liveness.ts`) from the running turn's recorded activity (what the agent last started, which every backend records) and the agent log's modification time, and, for a write job, from git in its worktree without taking the index lock; it never acts on it.

`ask` is the same with a read-only turn on a thread, and the reply returned. `resume` queues another turn on the same session. At dispatch, a session with no recorded CLI session id receives its earlier prompts (including the original preamble) before the new message, so a failed first launch does not lose the task.

Codex threads are durable so they can resume across processes. After the agent and its descendants stop, the backend archives the thread through a short-lived app server before reporting the result, including after a failure or cancellation. A follow-up unarchives it before resuming. Both the app-server and exec backends do this; cleanup failures become result warnings. Active turns can appear in Codex history, and abrupt worker termination can prevent archival. No separate Codex home or credential handling is involved.

A call that waits (status with `wait_s`, `delegate` with `background: false`, `ask`, `discuss`, `review`) polls the registry: every 200 ms it looks at everything (the item, approval requests, its limit, its progress; `waitUntil` in `src/core/wait.ts`), and between those looks it naps on the registry (`registryPoll` in `src/core/wake.ts`). A file watch on the write-ahead log wakes the nap as soon as another process commits, `PRAGMA data_version` confirms the commit, and a quick look checks only what can end the wait: the item settling, or an approval request not yet put to the user, which the full look then puts to the user first. A call that waits for one turn's reply (`ask`, `discuss`, a review's reconciliation) takes it only once the session has also recorded the turn's end, settled or gone on to its next turn, or has no worker left to, which it learns only from a pid that is gone or now another process's (`turnSettled` in `src/core/db.ts`): what the call then returns, and a `resume` or follow-up sent at once, find the session as the reply left it. The wake is only a hint to look now: what the call waits for is still read from the registry, and the 200 ms look bounds every nap, so the call's own commits, a process that died, or a log that cannot be watched are seen no later than with the poll alone. A launched agent waiting for a decision on its approval request (`src/core/approvals.ts`, a full look every 250 ms) and a worker waiting for a concurrency slot (`src/core/slots.ts`, every 150 ms) nap the same way. It sends a progress line every 15 seconds built from the registry: the awaited item's status, its turn, and the activity its worker records from the agent's event stream (the command, tool or file it last started). It ends after `block_s`, or for a status wait in a positively identified interactive Claude Code session (`src/mcp/host.ts`) after up to six hours, or when the caller cancels the call; it never cancels the work it waits on.

**Events.** While it lives, a root session's server looks at its runs three times a second (`watch` in `src/core/watch.ts`; a tick that finds the registry's change mark, `PRAGMA data_version` with the connection's own `total_changes()`, and the session's own state as they were at its last look, with no question open on a pending request, does only what goes by the clock): it puts new approval requests to the user, and records events (`src/core/events.ts`) for its runs, looking back to each run's creation, also for a run it took over, so that what settled while no session was alive is not lost: its own jobs and threads settling, its review's reviewer finishing, its discussion's participant replying, approval requests handed to it rather than put to the user, and requests a person decided (in an approval dialog, through `confirm`, or from a terminal), which go only into tool results so that the agent knows. Each is one row in `events`, keyed on what it is about, so it is recorded once. Every few seconds the watch also marks jobs whose worker has died as lost, so that they settle, and become events, without anyone asking about them. An event is delivered at least once: every tool result of the session carries those it has not been given (`events`), apart from those about items the result reports itself, and where the host has an inbox (Claude Code's `CLAUDE_CODE_MESSAGING_SOCKET`, used only by a root registered for Claude whose client introduces itself as `claude-code`, so that a process that merely inherited the variable does not post into the session it came from) the server posts one pointer notice per event that no call of the session is waiting on. Launched agents' environments never carry the inbox.

## Discussions and reviews

Neither has a process of its own. Each is a record that its caller advances.

A **discussion** is the calling agent on one side and one launched session on the other, normally of another family. Both sides are recorded by label (each side's target id, with `caller` for a same-target or unknown caller), and so are a review's. Each `discuss` call appends the caller's message to the transcript, queues it as a read-only turn on the other session, waits for the reply, reads its closing marker (CONTINUE, AGREE, CRUX), and decides whether the discussion is over. A reply that arrives after the call has returned is folded in the next time anything asks about the discussion.

A **review** starts a read-only reviewer job, normally of another family, on code or on a plan, and keeps its result and its log and transcript paths out of relay's replies until the caller's review is saved (accepted only once the reviewer has settled) or skipped. It then writes both reviews to files (the text, and the parsed items, verdict and declared coverage) and opens a discussion with the reviewer's own session to reconcile them. Same-family and unknown callers are admitted under `same_family: "allow"` and labelled accordingly; `"refuse"` rejects those starts and unknown callers' continuations. A Claude reviewer gets transcript read denies for the caller's candidate homes: the known family's home, a contradicted registration's home, or both Codex and Claude homes when neither is known. Its own Claude config home is narrowed to conversation stores so its tools and memory stay readable. A Codex reviewer gets no read denies because its read-only sandbox has no read carve-out. When that discussion ends, the consensus list and the verdict are built from the closing messages; a pass over coverage not declared complete is recorded as unknown (`src/modes/review.ts`).

## Speed

A session's speed (`standard`, `fast`, `ultrafast`; the maintainer, 2026-10-16) is decided when the call that starts it is admitted (`admitSpeed` in `src/core/caller.ts`) and kept in its params. A speed belongs to a turn: a later call on the same session (a resume, a follow-up, a discussion carried on) keeps the speed it was admitted at for the turn it queues (`speed_queued`, written in the transaction that queues that turn by `changeSpeed`, so a call whose message is not taken changes nothing), and the session takes it only as that turn is claimed to start (`startSpeed` in `src/core/session.ts`, in the claim's transaction). So the turns queued before it, and the one running now, keep theirs, and so does a launched agent's own speed (`speed`, its running turn's), which caps what it starts; a turn that ends without starting (cancelled while queued, dropped behind a turn that failed, reaped) changes nothing, whatever closed it. A raise a turn started with is undone if that turn never reaches the model (`settleSpeedChange`; a slower speed stays, since it costs no more). A review carried on with `review_id` keeps its reviewer's speed with the review (`reviewer_speed`) until the reconciliation's first turn is queued, through `discuss`. Every call that continues a session is admitted with the speed that session goes on at (`speedAfter` in `src/core/db.ts`: its last queued turn's, else its running or last turn's), named or not. A root session's call takes its `speed`, else `targets.<id>.speed`, else standard. A faster speed costs the person money or allowance, so only the root session raises it: the work a launched agent starts or carries on runs at the agent's own speed unless it asks for a lower one (a session faster than the agent, one the root has since slowed, is refused until the call passes a speed), and a Codex subagent thread's root session goes no higher than what the person set up. Admission also refuses a speed the target has not got at all (the registry's `speeds`: Claude has `fast`, Codex `fast` and `ultrafast`, Copilot, Gemini and Grok none), and a Claude model that has no fast mode by its name; loading the config refuses a `targets.<id>.speed` of either kind. A refusal names a speed to pass and where the refused one came from (`SpeedSource`): leaving speed out gets another only when the speed was the call's own.

Every turn pins its speed, standard included. **Claude:** relay's settings file sets `fastMode` (`true` for fast, `false` otherwise); that file is Claude Code's flag settings, which outrank any of the person's that load and count as the opt-in a headless session needs (Claude Code 2.1.302). Claude alone knows whether its account can serve fast mode (usage credits, a rate limit's cooldown), so its result's `fast_mode_state`, `fast_mode_disabled_reason` and `usage.speed` are kept with the turn's usage, with the notice it puts on its stream when it refused fast requests and retried them at standard (`fast-mode-overage-rejected`: usage credits run out, a spend cap reached; its result then still says fast mode is on), and a fast turn that ran at standard speed is reported with the turn's warnings, with Claude's reason or notice. It is kept apart from the process warnings (`TurnResult.speedWarnings`), which keep a write job's unchanged worktree (`endJobTurn`); a speed warning says nothing about what the agent left running. A report is shown in status only with the speed its turn asked for (`speed_requested`). **Codex:** the speed is a service tier by its catalog id (`default` for standard, since a model's catalog entry can carry a faster default tier; `priority` for fast; `ultrafast`), set as `service_tier` in the flags (what `codex exec` goes by), on `thread/start` or `thread/resume` and on `turn/start`. Before the thread runs, relay reads the account's catalog (`model/list`, hidden models included) and refuses a faster tier the catalog does not offer for the model that would run (the one asked for, else, for a turn that carries on a thread, the thread's own as `thread/read` gives it, which Codex resumes it on, else Codex's configured one, else the catalog's default), naming the plan (`account/read`) only to explain; the decision is the catalog's, never a table of plans. The `codex exec` fallback names a thread's own model it checked with `-m`, so the model checked is the one that runs. Codex drops every service tier, `default` included, while its `fast_mode` feature is off (0.163.0: the thread then reports none), so standard turns set `features.fast_mode=true` (with `-c`: `--enable` of a feature a Codex version does not know stops its server), keeping the tier `default`, and a faster turn leaves the person's switch alone and is refused while it is off (`fastModeProblem`), before the thread runs. The thread's reported `serviceTier` must then be the one asked for, standard's `default` included: Codex 0.163.0 reports null both for a tier it dropped (one the account lacks) and for none, and with none a model's catalog default (priority, for some) would apply. A server that leaves the key out is judged by `config/read` alone. The `codex exec` fallback makes the catalog check in its preflight. No harness reports the tier that served a turn (Claude's `usage.speed` aside), so status shows the speed requested for the turn running or last started (`speed.requested`), the one asked for the queued turns where it differs (`speed.next`), and what Claude reported under `speed.reported`; a discussion's and a review's views give their other side's the same way (a review also gives its `reviewer_speed` as `next` until the reconciliation opens).

## Confinement

For Claude and Codex, relay does not sandbox anything itself. It configures each CLI's sandbox for the turn and then checks, as far as each CLI allows, that the configuration took.

- **Codex.** The sandbox is a permission profile of relay's own (`[permissions.relay]`, `backends/codex.ts` `codexPermissions`), defined and selected with `-c` and named on the thread: the same sandbox the legacy `sandbox_mode` and `sandbox_workspace_write` settings gave, plus relay's list of harness configuration read-only at the top of every workspace root. Before the thread is started or resumed, relay asks the same app server for the effective configuration in the job's directory, for an administrator's requirements and for the login method, and refuses to go on unless the profile is selected and exactly as relay defined it, the requirements allow it, and MCP servers, plugins and login are what it expects; the started or resumed thread, told its workspace roots (the job's directory alone), must then report the profile as active, with the sandbox kind and network relay set, those roots, and nothing writable beyond them and the profile's own.
- **Claude.** Relay passes one settings file and loads none of the user's, the project's or the local ones. The deny rules from the user's own settings (`permissions.deny`, read from that file and nothing else taken) are copied into it, with paths relative to the user's settings directory anchored there. The file turns the sandbox on, makes it fail rather than fall back if it cannot start, denies writes to relay's control directory, and without a network grant has the sandbox refuse every host by itself (`strictAllowlist`: under `-p` the sandbox's own network question is answered "user denied" and never reaches relay's permission tool); a read-only turn also denies the working directory and the repository's git directories and gets no editing tools; a write turn gets a fixed tool list. Claude does not report its effective sandbox settings, so relay checks what it does report at start (tools, MCP servers, permission mode, login) and stops the agent if any of them is not reported, or if it lists a tool or MCP server relay did not give it or a mode or login other than relay's. Fewer tools than relay gave is fine: a carried-over deny rule naming a whole tool removes it. It refuses to launch where organisation-managed settings are present on disk (settings delivered from the claude.ai console are invisible to it, and could redirect the agent's endpoint), and, because a settings file's `env` can redirect Claude to another endpoint after relay's environment check, wherever settings it does not vet would load (user, project and local settings under `child_settings: "inherit"`, or accepted managed settings) unless `claude_settings_env` is `"accept"`.
- **Both.** Launched only on macOS and only at or above the CLI versions the confinement was checked with, unless configured otherwise. API keys are removed from the environment (per target: every vendor's, unless that target alone is allowed its own; the legacy global `child_auth: "any"` removes none, which doctor warns about). Which family answers is checked too: Claude must report a Claude model, Codex's effective configuration must use OpenAI's provider and, when relay asked for a model, its thread must report OpenAI's provider and exactly that model (a missing field is refused), and neither is launched with an endpoint override in its environment. Under a Claude desktop or Agent SDK host (`CLAUDE_CODE_DESKTOP_APP_VERSION` or `CLAUDE_AGENT_SDK_VERSION` in relay's environment), the host session's own `ANTHROPIC_BASE_URL` is removed from launched agents' environments instead of refused, but only where Claude signs in with its login, so that the credentials that go with it are removed too (`hostSessionVariable` in `src/backends/env.ts`). Where Claude may sign in with a key, removing the endpoint would send that key to Anthropic, so the launch is refused there as well.

**Approval requests.** A launched agent that hits its sandbox can ask. Claude's permission prompt is pointed at a tool on relay's server; Codex's app server sends an approval request. Either becomes a row in the registry. While the root session's relay server lives, it watches the registry and puts each new request in its runs to the user through the host (MCP elicitation) as soon as it is filed, on hosts known to show the question (`src/mcp/host.ts`); one row per request in `elicitations` records which server asked and how it ended, so that a question is asked once, also across a server restart, and a cancel leaves the request pending. Only an answer that is exactly one of the dialog's choices decides; anything else leaves the request undecided, and is recorded as the person closing it (`dismissed`, which bars the root agent from allowing it on its own) only where that is known to be a person (Esc in interactive Claude Code); any other host answer is recorded as `unattributed` with the host's raw outcome. A question decided elsewhere first is withdrawn, on hosts that take a question back. Codex keeps the form on screen, and answers a cancellation with an automatic "cancel" and stops listening for the person's answer, so relay sends it none: the form stays open, the form's text says so, and relay keeps listening and records an answer given afterwards as a `late` event that changes nothing, reported to the agent in its next result (`src/mcp/elicit.ts`, `elicitThrough`). Should a cancellation go out all the same, relay notes it by the request id it puts in the question's `_meta`, so that the "cancel" acknowledging it is not taken for an answer. Claude Code started able to skip its permission prompts (its command line, read from the processes that started the server), or whose settings set a bypass default mode, is asked nothing whatever `ask_user` says, and gets no `confirm`. Hooks withhold only what they can answer: Elicitation or ElicitationResult hooks whose matcher can match the server name `relay` withhold the dialog, and PreToolUse or PermissionRequest hooks whose matcher can match `mcp__relay__confirm` withhold `confirm` (the user, project, local and managed settings files and any `--settings` argument, read with plutil for `permissions.defaultMode` and those events' matchers only, so nothing else in them reaches relay; `src/core/claude-settings.ts`; unreadable counts as matching). `relay doctor` reports the result for the current directory. A request not put to the user, or closed without an answer, reaches the root agent in the result of whatever it is waiting on, and the user can always decide from the terminal, except that a person-only request (below) can only be denied there. A request to change files in relay's own directories or relay's config files is refused on the spot.

**Extensions** (1.0; `docs/extensions.md`). A job or thread started with `extensions: true` by a root session holds the skills and MCP servers its target's config allows, resolved at the call (`src/core/extensions.ts`) and kept in its params. Before its first turn runs, the worker files an approval request of kind `extensions` naming them all; it, a call of an extension's tool (kind `mcp`), and any request from a session holding MCP servers are person-only: only relay's approval dialog (where the host is known to show it to a person) or `confirm` can allow them; the root agent's `approve` and `relay approve` refuse to (a command could be any agent's), and `approve` and `relay deny` can deny them. Only a root session gives extensions, and not from a Codex subagent thread. Each turn then gets a package of filtered skill copies in its node directory (Claude: `--plugin-dir`, checked against the init report's plugins and skills; Codex: the package without its plugin manifest, through `skills/extraRoots/set` on the turn's app server, the person's and the repository's skills switched off with `skills.config`, and `skills/list` checked before the thread starts) and, for servers, a gateway manifest that the turn's context names. The launched agent's own relay server (`src/mcp/gateway.ts`) reads it, starts the servers from relay's `mcp.json`, and offers their tools as its own, asking the person before forwarding each call the config does not allow outright. A session holding servers gets no network, may not delegate (its turns' context says so, whatever the session was started with, and relay refuses its delegate, ask, discuss and review calls), and its CLI's own web tools ask (Claude) or are off (Codex). No grant may cover relay's `config.json` or `mcp.json` (by either name of a linked one, or a directory holding one), and no file request may change one, for any job. The package and manifest are removed when the turn ends.

## Relay-owned confinement

For harnesses beyond Claude and Codex, relay puts the whole harness process under its own sandbox. The ACP driver does this for every target whose capabilities say `relay-enforced` (Copilot, Gemini and Grok, so far).

- **The mechanism** (`src/confine/index.ts`): a policy (worktree, read or write, granted and state directories, a private temp directory, denied directories, the bridge socket, network mode, keychain, the harness's state, extra executables) and a mechanism that wraps a command line in it, says whether it can enforce on this machine, and asks the kernel whether a process is confined. `confinement()` returns the one for this platform or the reason there is none, in which case relay refuses the harness. `prepareLaunch()` is everything that happens before a confined launch, in order: the hard-link check (write turns), `wrap`, the boundary probes; it throws `ConfinementRefused` naming the failed check. `confinementSummary()` is what `relay doctor` prints.
- **Seatbelt** (`src/confine/seatbelt.ts`): a `(deny default)` profile run with `sandbox-exec`. The profile text holds no path. Every path is resolved (Seatbelt matches resolved paths, so `/tmp` is `/private/tmp`), refused if it is relative or contains a NUL or a line break, and passed as a `-D` parameter. Writes are allowed only to the worktree (write turns), granted and state directories, the turn's temp directory (`TMPDIR`), by exact name the harness's token files, and, where the target declares a login store (`TargetDef.tokenStore`), its token, lock and temp names in that one directory of the person's home. Last-match-wins puts the hard denies at the end: the worktree's `.git`, and reads and writes of the denied directories, among them always relay's control directory. With the network off, only the turn's proxy port on loopback; with it on, any IP address except loopback, and DNS. Either way the only Unix socket is the bridge's. Executables are listed (see below). `sandbox_check`, asked through `osascript`, tells whether a pid is sandboxed.
- **The proxy** (`src/confine/proxy.ts`): one per turn with the network off, on `127.0.0.1` at an ephemeral port with a fresh token in `Proxy-Authorization`, so another turn (or any other local process) cannot use it. It tunnels CONNECT to port 443 for exact host names only (the hosts the target declares, `TargetDef.apiHosts`), resolves them itself, refuses IP literals and any name that resolves to a private, loopback, link-local or reserved address, answers anything but CONNECT with 405 and a bad token with 407 and a challenge, and appends each decision as a JSON line to `proxy.jsonl` in the item's directory (the ACP driver also writes each to the agent's log as a `[proxy]` line). `wrap` points the harness at it: `HTTPS_PROXY`, `HTTP_PROXY` and `ALL_PROXY` in both cases, an empty `NO_PROXY`, and `NODE_USE_ENV_PROXY=1` (Node's own `fetch` ignores the proxy variables without it). A harness that ignores them fails closed: it has no DNS and no other way out.
- **State** (`HarnessState` in the policy, supplied by the harness profile): by default a temporary home inside the turn's temp directory, mode 0700, with `HOME`, the XDG directories and the harness's own home variables pointing into it, so the harness loads none of the person's configuration and nothing it writes there outlives the turn. Login files it must read are linked into that home; relay never opens or copies them. With `home: "real"` the person's home is readable and not writable. Either way only the token files named are writable, by exact name; a directory or an executable is refused as a token file, so configuration directories, hooks and binaries never are. A harness that refreshes its login by writing a new file and renaming it into place cannot refresh through a token file; its target declares a login store instead (`TargetDef.tokenStore`: token, lock and temp-name pattern in one directory of the person's home, Grok's `~/.grok`), where exactly those names may be created as regular files, written and renamed onto, and which relay checks before and after every turn. The profile's environment (auto-updaters off) is passed through but cannot replace what relay sets (`HOME`, `TMPDIR`, `PATH`, the XDG and proxy variables, `NODE_OPTIONS`, `DYLD_*`). State directories must lie inside the turn's temp directory.
- **Executables.** Forking is free; executing is allowed only by resolved path: the system's directories (`/bin`, `/usr/bin`, `/usr/libexec`, `/System/Library`, the cryptexes and so on), the developer tools (Command Line Tools, Xcode), `/opt/homebrew`, `/usr/local`, the harness and the interpreter on its `#!` line, relay's own Node (the bridge and the probes run on it), the policy's `execPaths` (an interpreter found through `env`, toolchains in the home such as rustup or nvm), and the turn's writable directories, so that the agent can run what it builds. *What the exec list does not do:* since the writable directories are on it and reads are broad, an agent can copy any program it can read into its worktree and run the copy. The list stops running programs installed elsewhere in place (another agent's CLI in `~/.local/bin`, an app's binary); everything that matters for the boundary (files, network, services, signals) is enforced for every process whatever it runs. Keeping the writable directories off the list would break `cargo test`, `go test` and any build that runs its own output, for no gain while interpreters are on it.
- **Hard links** (`src/confine/hardlinks.ts`). Seatbelt decides by path, so a file in the worktree that is also linked from outside writes through to that outside inode. Before a turn relay walks every writable root (symlinks not followed, a stat only for regular files) and refuses if a file has a name outside them all; links whose every name is in a writable root pass. The paths the sandbox hard-denies inside the roots are not walked and a name there counts as outside: for a relay-enforced turn (`prepareLaunch`) the profile's own list, the `.git` pointer among them; for a native Claude or Codex write turn (`hardLinkProblem` in `src/core/worktree.ts`, roots: the worktree and granted directories) each root's `.git` and the worktree's `.relay`. About 25 ms for 4,500 files. The walk is synchronous, so a stop of the worker waits for it: a tree large enough to outlast the supervisor's deadline gets the worker killed before it cleans up the turn's temp and socket directories (review `r_f0fce42b` C3). (Creating such a link from inside is denied by the sandbox: a new link may not have more rights than the file it names.)
- **Boundary probes** (`src/confine/probe.ts`, `src/confine/canary.ts`). Before every launch relay runs a canary (Node built-ins only) through the same `sandbox-exec` profile and parameters (`ConfinedLaunch.rewrap`) and environment the harness is about to get. Each probe is a real attempt against a target relay sets up outside the sandbox (a directory with a file, a Unix socket, a TCP listener, a small app bundle). Positive controls: the worktree (write turns) and temp directory are writable, the worktree readable, `/usr/bin/true` runs, the bridge socket and the proxy port are reachable, the token files open for appending. Denials, each of which must be the sandbox's own `EPERM`: writes outside, beside the worktree, into a sibling worktree, the `.git` pointer, the control and denied directories, the real home, the login store beside the token files, the harness's directory; reads of the control and denied directories; a hard link to an outside file; a write through a symlink out; a loopback TCP connect; a Unix socket other than the bridge; an executable off the list; with the network off, a direct connect and DNS (both the system resolver and UDP). `launchctl submit` and `open` of the probe app must fail. Anything else refuses the launch with the probe's name. Nothing is cached across turns. About 260 ms per turn on an M-series Mac (an M5 Max, 2026-11-12, `prepareLaunch` for a read or a write turn with the network off). The probes never open an executable for writing: on macOS that alone makes every later exec of the binary be killed until the file is replaced.
- **The broker** (`src/confine/broker.ts`). A process under that profile cannot write the registry, so a relay server it started could not work, and must not be able to. Instead the worker, outside the sandbox, opens a broker for the turn: a Unix socket in a new private directory (mode 0700) serving the same tools as `relay mcp` (`relayServer()`), with the authority of that one turn taken from the worker's registry rows, never from anything the agent can write. Before the harness receives its bridge entry, the ACP driver pins its launched pid and start time with `bindHarness`. Each connection is paused until its kernel peer pid and uid are known: the uid must be relay's user's, and the peer must be the pinned live harness or a live descendant. `inProcessTree` uses fresh `procStart`/`sameProcess` checks (bypassing the ordinary two-second cache), a process-table ancestry snapshot and a second identity check of every process in the chain; missing, dead, zombie or changed identities fail closed. The broker also requires the random per-turn `RELAY_BRIDGE_SECRET` as the first line, compared in constant time, and rechecks ancestry after that bounded handshake. An outsider holding the exact secret is closed unanswered (core review C21). Broker refusals, including an unreadable peer identity, go to the turn's log with the reason and no secret. Every request is still checked against the live turn: once the turn is no longer running, or it, an ancestor or the run is cancelled, requests get a JSON-RPC error (-32001). Closing the broker drops its connections, reaps pending credential helpers and removes the socket and directory.
- **Kernel peer credentials** (`src/confine/peer.ts`, macOS). Node has no `getsockopt` API. Relay starts the fixed system `/usr/bin/perl -T -e <fixed program>` outside the sandbox, with the accepted `net.Socket` in stdio slot 3, a minimal environment and a two-second deadline. Perl's built-in `getsockopt` reads `SOL_LOCAL/LOCAL_PEERPID` and `LOCAL_PEERCRED` from that exact accepted socket; it does not read protocol bytes. Darwin defines the level/options in Apple's [sys/un.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/un.h), the `xucred` version/uid layout in [sys/ucred.h](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/ucred.h), and the socket-option implementation in [uipc_usrreq.c](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/uipc_usrreq.c). Verified on macOS 27 (Darwin 27.0.0, arm64), with the shipped Perl 5.34.1: an inherited accepted fd returned the connecting Node process's pid and uid. No compiler or npm dependency is needed. Unavailable Perl, unsupported platforms, failed socket options, malformed output and unknown start times refuse access. Relay requires ancestry while the original harness lives; a reparented or detached peer is refused, even if it retains the old process group. It does not authorize by a numeric process-group id alone.
- **Peer-authentication alternatives rejected.** `lsof -U` is an asynchronously sampled listing that would need to map the accepted endpoint back to a live process and handle missing/ambiguous entries and process churn; the socket's kernel credentials give that identity directly. Seatbelt's socket-path rules remain necessary but govern only the clients running under those profiles: they cannot forbid a different native-sandboxed or unconfined user process from connecting to the worker's socket. A bearer secret or a connection cap alone also supplies no process-tree binding. `test/broker.test.ts` proves refusal of an ordinary outsider and a deny-default `sandbox-exec` peer outside the harness tree, both with the exact secret; the latter verifies sandbox status and successful socket connect separately so a sandbox denial cannot pass as broker authentication. The real confined bridge e2e, unknown-peer/uid checks and start-time/pid-reuse regressions cover the positive and fail-closed paths. These scratch tests are separate from signed-in harness qualification.
- **The bridge** (`relay bridge <socket>`, `src/confine/bridge.ts`): the MCP server the confined harness is given. It forwards newline-delimited JSON-RPC between stdio and the socket, after presenting the turn's secret, and has no registry, context or other environment. When the socket cannot be reached or closes, it answers every request, those in flight included, with an error (-32002) so that the agent is told at once rather than left waiting.

A driver that confines a turn does this, in the worker, after the turn is marked running: `openBroker({ nodeId, turnId, mayDelegate, mayAsk })`; with the network off, `openProxy({ allow: <the target's apiHosts>, logFile: <the item's proxy.jsonl> })`; a per-turn temp directory (mode 0700); `prepareLaunch(mechanism, policy, harness, args)` with `bridgeSocket: broker.socketPath`, `network: proxy.network` and the harness profile's `state` and `execPaths`; launch the returned command with its environment added (it overrides the harness's own `HOME`, `TMPDIR` and proxy variables); give the harness `broker.bridgeCommand` as its relay MCP server; check `mechanism.confined(pid)`; and at the end of the turn `broker.close()`, `proxy.close()` and remove the temp directory. A tool call still waiting when the turn ends runs out its own bounded wait in the worker, and its reply goes nowhere. An approval request from the harness cannot widen the sandbox in 1.0 (no escalation): relay reports what the agent needed.

The ACP driver (`confinedLaunch` in `src/backends/acp.ts`) follows these steps for relay-enforced targets, with the per-turn checks (`prepareLaunch`: hard links, `wrap`, boundary probes) before every launch; the probe report is written to the turn's log. They are enabled (`PROBES_ENABLED` in `src/confine/turn-probe.ts`, since 2026-10-17, after the whole battery passed under the exact profiles of a signed-in Copilot read turn and write turn on macOS 27.0); a build with it false would refuse every relay-enforced target, by `capable` in `src/core/caller.ts` and again by the driver. Only test code can stand another probe in, through `setBoundaryProbeForTests`. With the network off the driver opens the turn's proxy before the probes (which check its port is reachable) and closes it, with the broker, as soon as the turn is over; a target that declares no `apiHosts` is refused a network-off turn.

## ACP harnesses

`src/backends/acp.ts` runs one turn of a harness over the Agent Client Protocol, version 1 only (v2 changes how a turn ends, so it is refused rather than guessed at): one process per turn, JSON-RPC over its stdio. ACP is the transport, not the security layer: nothing in it sets or reports a sandbox, a login or the effective configuration, so each harness has a profile (`AcpProfile`) reviewed as code, and confinement is relay's own.

- **Before the prompt.** The kernel confirms the process is sandboxed; `initialize` advertises no file system or terminal (the agent uses its own tools, inside relay's sandbox); the profile checks the login (an exact authenticate method known to succeed only with an existing login, never a login flow, or a verifier of initialize; a profile with neither is not launched under `child_auth: "login"`), and checks it again once the session exists; a profile that prepared an `authenticate` request (Gemini's API key, in `_meta`) has it made once, before the session, never logged; `session/new` (or `session/resume`, else `session/load`, for a resumed session) carries the directory, granted directories and the turn's relay server (the bridge); the profile's mode and the item's model are set where they differ and then read back from what the agent reports (session responses, `current_mode_update`, `config_option_update`), and so is the turn's reasoning effort where the profile names the config option that reports it (`effortOption`, Grok's `thought_level`). Anything missing or different stops the agent before it has done anything.
- **During the turn.** Updates are folded into tool-call state by id. The reply is what the agent says after its last tool call; a load's replay is not part of it. ACP v1 has an agent replay a loaded session before it answers `session/load`; one that answers first and replays afterwards (Gemini CLI 0.64.0) says so in its profile (`replaysAfterLoad`), and relay sends the prompt only once the session has been quiet for the profile's interval, failing the turn if the replay is still going after its limit, and warning if a replayed user message arrives after the prompt. Each tool call it starts is reported as the turn's activity (the command, the files, the URL, else the agent's title for it), and its usage (tokens from the prompt's response, cost from `usage_update`) is recorded, as the native backends do; events and notices come from the registry as for any turn. The resume command points `COPILOT_HOME` (Copilot), or `GEMINI_CLI_HOME` (Gemini), at the item's own home for the harness, where its session lives. For Grok relay shows none (`TargetDef.nativeResumeWithheld`, a note in its place): its session store is writable to everything in its turns, and `grok --resume` would restore it outside relay's sandbox, on relay's Grok settings, with Grok's own sandbox off for the life of the session. Client methods relay never offered are answered with a JSON-RPC error at once.
- **Approval requests** (`session/request_permission`) go through the profile's `normalizeApproval` to relay's `ApprovalAsk`, joined to the tool call they name. One whose action, files or scope cannot be established is refused without reaching anyone. Relay answers only with an option the agent offered, and never with `allow_always`: an approval for the rest of the job is held by relay, in the registry, and each later identical request is answered allow-once. For a relay-enforced harness nothing approved lifts relay's sandbox, and the approval request says so.
- **Cancel** sends `session/cancel`, answers pending approval requests "cancelled", and signals after the grace period.
- **Family.** Under `same_family: "refuse"`, a harness judged per model (Copilot, which runs several families' models; Grok, whose models are all xAI's while relay owns its configuration, but whose format allows others) must pin a listed model and report exactly that model before the prompt; a change to another family's model, or to one relay cannot name, takes away its relay tools, cancels the turn and fails it. A change within the pinned model's family goes on with a note, under either setting. Under the default `"allow"`, auto and unlisted models are allowed with unknown family labels, except on a target whose settings relay holds to its listed models (`TargetDef.listedModelsOnly`, Grok's `allowed_models`), where the driver refuses an unlisted model before the harness starts, under either setting, and only no model is labelled unknown; a pinned model must still match before the prompt, and mid-turn changes away from it are reported with the result. Under `auto` or no model, a model reported mid-turn is what was chosen, recorded with no note. Contributions spanning families make the item's family label unknown. Continuing an existing item may reach one's own family under either setting, subject to authority over the item; unknown callers can continue under `"allow"` and are refused under `"refuse"`. A harness that names the model that answered only in the prompt's response, its session reporting an alias such as `auto` (Gemini CLI: `_meta.quota.model_usage[].model`, read by `promptModels`), has a profile `servedModels` hook, handed the model the session reported, which such a harness may also list for rounds another model answered (Gemini does, for every round after a tool call). Each model it returns is a model report like the others: recorded with the item and in its label, and, where relay pinned a model, held to it as a mid-turn report is. Gemini's profile uses it.

Copilot (`copilot --acp`) is switched off by default and experimental (`targets.copilot.experimental`) until a signed-in qualification run: its flags, settings keys and login behaviour come from GitHub's documentation and the 1.0.98 package, not from a signed-in run. Its profile turns off Copilot's own sandbox (it would nest inside relay's), its hooks, the skills it would import from Claude Code's directories, its subagents (which run other models) and auto-update; removes `COPILOT_GITHUB_TOKEN`, `GH_TOKEN` and `GITHUB_TOKEN` from its environment (only `COPILOT_GITHUB_TOKEN` from other agents', since other tools use the GitHub ones), and every other Copilot variable; and refuses a repository whose `.github/allowed_models.txt` could make it fall back to another model.

Grok Build (`grok --no-auto-update [--disable-web-search] agent --no-leader --always-approve [-m <model>] [--reasoning-effort <effort>] stdio`, `src/backends/grok.ts`) is switched off by default and experimental (`targets.grok.experimental`) on the same terms: what its profile relies on comes from the 1.0.62 package run without a login and without a model call, its shipped user guide and its public source at 1.0.45. Each session gets a Grok home of relay's (`GROK_HOME`, under the harness directory), read-only to the agent but for `sessions/` (kept for resuming) and `turn/` (logs, removed with the turn), given to the sandbox as relay-owned persistent state; relay rewrites its `config.toml` before every turn: the stored login only (`[auth] preferred_method = "oidc"`, under which `cached_token` fails at once without a login rather than opening a browser or taking an API key from the environment, and, under `child_auth: "login"`, `disable_api_key_auth = true`, so that an API key Grok keeps in `auth.json` is refused too), Grok's own sandbox, telemetry, trace and codebase uploads, auto-update, the leader, subagents, memory, remote campaigns and managed MCP servers off, nothing imported from Claude Code, Cursor or Codex, only the reviewed models allowed (the driver refuses a turn that names another before Grok starts, `listedModelsOnly`; a listed model its session does not offer, which Grok would replace with its default without a word, is refused before the prompt, and so is an effort its model's menu lacks, which it would run as `high`: `effortOption`), `web_fetch` off, and, in a turn without network access, `web_search` dropped too (`disable_web_search`, and the flag), and Grok's server-side tools (`features.backend_tools = false`, and `GROK_BACKEND_SEARCH=0`): they run on Grok's own API host, which relay's proxy admits, and never ask. The same settings that have a variable are set in the environment too, which outranks Grok's files and the remote settings xAI can push, after every `GROK_*`, `XAI_*` and `OTEL_*` variable and `SENTRY_DSN` of the worker's is removed. No `requirements.toml` is written: Grok 1.0.62 applies nothing from an unsigned one. HOME is a temporary home, which hides the other agents' configuration Grok would import. The stored login is the one `grok login` keeps in `~/.grok` (`GROK_AUTH_PATH` points at it; a worker whose own `GROK_AUTH_PATH` or `GROK_HOME` puts it elsewhere is refused), and the target declares that directory as its login store (`tokenStore`): Grok refreshes by locking `auth.json.lock`, spending a single-use refresh token, writing `.{pid}.{counter}.tmp`, chmodding it and renaming it onto `auth.json`, and a confined turn may do exactly that there and nothing else. The sandbox layer checks the directory and every such name before each turn, and probes the same rules on a decoy store. The profile refuses a machine with `/etc/grok/managed_config.toml`, `/etc/grok/requirements.toml` or device-managed `ai.x.grok` preferences, which outrank everything relay sets.

Gemini CLI (`gemini --acp`) is switched off by default, qualified (the maintainer, 2026-10-22), and the one key-only target: it signs in only with an API key, which relay reads from a file the person keeps (`src/core/api-keys.ts`; by default `~/.config/relay-keys/gemini-api-key`, movable only in the machine-local `~/.config/relay/local.json`) and hands to its process alone, in ACP `authenticate`, never in an environment (the turn's own processes can read each other's start-up environment). It runs with `targets.gemini.child_auth: "any"` only. Its profile gives it a home of relay's own per session (read-only but for its runtime state), relay's settings and a policy file of its own, an untrusted folder (so the repository's `.gemini/.env` cannot redirect the key; there it connects no MCP server, so its agents get relay's tools through Gemini's own command-based tool discovery instead, from relay's settings: a shim in relay's home that reaches the turn's broker as the bridge does, `src/confine/gemini-tools.ts`), and removes every Google credential variable. Every relay-enforced turn is denied the default key directory and a key file the local config moves elsewhere, and Claude's turns may not read them either. The design and its qualification: `docs/gemini.md`.

## Git

Relay runs git on the agents' behalf, unsandboxed, in trees agents have written to. Every git call goes through one function (`git()` in `src/core/git.ts`) that turns off hooks, the fsmonitor program, submodule recursion and signing, sets the C locale and a timeout, and kills git's whole process group if it overruns. Before staging, relay checks for nested repositories whose git directory is outside the repository's own, and does not stage if it finds one. Before any command that could run a configured command on files (staging, checkout, merge, `git status`), it checks for content filters other than Git LFS and merge drivers, and refuses if it finds one (`filterRefusal`); the check covers each git context a command actually uses, so branching a new worktree admits the main worktree's own config (`config.worktree`) as well as the caller's, since `git worktree add` runs there. Diff drivers (`textconv`, `command`) and an external diff are left alone: relay's own diffs pass `--no-ext-diff --no-textconv` and nothing else it runs uses them, so refusing them would only block people with difftastic or the like configured. Its checkouts and merges skip Git LFS downloads. A job worktree's `.git` file is the agent's to rewrite, so relay never goes by it: `jobTree` finds the worktree's git directory in the repository's own records (`<common>/worktrees/*/gitdir`, the common directory asked of the main checkout), every git command for that worktree gets `GIT_DIR` and `GIT_WORK_TREE` explicitly, and relay refuses to run git for a job whose `.git` file no longer points there. A caller inside a job's worktree is located through the registry (`worktreeHolder`), never through git. A worktree is removed only when git reports it clean, with untracked files asked for explicitly.

## Programs relay runs

Relay runs every program outside a sandbox by an absolute path (`src/core/executables.ts`; review r_0c11d860 X1). macOS's own tools are named by their fixed paths in the sealed system volume (`/usr/bin/osascript`, `/usr/bin/pgrep`, `/bin/sleep` and so on). git and the target CLIs are found on PATH and run by the absolute name found: git once per process (`gitExecutable`), a target CLI on the PATH of the turn that launches it. That name is on purpose the PATH entry, not the file a link leads to: Claude Code updates itself by repointing `~/.local/bin/claude`, and the next start must follow the link. The name, the file it leads to and the installation holding it (a Homebrew keg, an npm package, a Node distribution) are all protected alike (`protected-config.ts`): no grant or file request may cover any of them, nor a directory on relay's PATH in either direction (`relayPathDirs`); relay's Seatbelt profiles and Claude's sandbox settings deny writing all of them (`relayWriteProtected`); and before each launch relay refuses a turn whose own PATH finds the CLI in, or passes through, one of its write paths (`targetLaunchProblem`), so admission's judgement, made on relay's PATH and config, and the launch's cannot disagree. The launcher `bin/relay` names its own tools by absolute path too and looks only Node up on PATH. `test/executables.test.ts` fails on a spawn of a bare name in `src/`, the launcher or the build scripts. The one exception is a test seam: the tests of install, uninstall and doctor run relay as a separate process and stand in pgrep, sw_vers and xcode-select through `RELAY_TEST_SYSTEM_TOOLS`, which relay honours only inside its own test suite (Node's test runner sets `NODE_TEST_CONTEXT` there, which nothing that starts relay for real sets, and a job cannot set relay's environment), and only for a directory of this user's under the temp directory.

## Processes

Each agent is started as the leader of its own process group. While it runs, relay notes its descendants at intervals, and once more when the agent says it is done or is told to stop. When the turn ends relay kills the group and everything it noted, checking each pid's start time first so that a reused pid is never signalled. This is best effort: a process cut loose from its parent is not found, and relay says so in the result when it knows it missed its last look.

## Directories

Codex install writes no subagent role. Pre-release builds of 1.0 wrote a proxy role, `agents/relay-<target>.toml` beside `config.toml`, for each enabled target of another family; `install codex` and `uninstall codex` remove the ones relay wrote (`planOldRoles` in `src/hosts/codex.ts`: a file whose first line is relay's ownership marker, judged against the per-field hashes on its second; saved first; install takes one the person changed only with `--force`), wherever the installation record says they were, and leave any other file of that name alone. A native Codex subagent thread an agent starts itself still gets a relay server of its own, which has no context and so is a root session, but no person is in its conversation: Codex marks its calls `thread_source: "subagent"` in `_meta["x-codex-turn-metadata"]`, and relay refuses an allowance and a grant from one (`subagentRefusal` in `src/core/caller.ts`; a denial is taken).

- `~/.local/state/relay/` (control): `relay.db`, and per run the prompts, logs, transcripts and reviews. Private to the user; launched agents' sandboxes deny writes to it.
- `~/.local/share/relay/worktrees/<run>/<job>/`: write jobs' worktrees, on branches `relay/<job>` of the user's repository.
- `~/.config/relay/config.json`: optional settings, validated strictly.
